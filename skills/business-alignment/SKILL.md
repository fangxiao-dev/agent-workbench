# Business Alignment

把「我们需要、但只有别人知道或能决定」的东西，写成对方最省力就能回应的材料，并把回应可追溯地交还。

## 1. 先查

动手前找已有答案：业务文档、规则、确认记录、`docs/principal/`（只读）。查得到就直接用；对当前决定没影响的不问。

## 2. 确认意图

先判断是哪一类，判断不了只问用户一句：「这次是想问清楚、让对方拍板、汇报已做好的，还是给技术 / agent 对齐？」

| 意图 | 对方 | 格式与范式 | 必须有 | 不要有 | 回来后 |
|---|---|---|---|---|---|
| **探索**：需求不明朗，可能多轮 | 业务方提供事实 | HTML `deck.html` | 真实场景下的开放问题；第二轮起「上次已确认」 | 把工程方案包装成唯一选项 | 写进来源并标「待确认」，再开下一轮 |
| **拍板**：已有推荐，只差点头 | 业务方做决定 | HTML：题多用 `questionnaire.html`，夹在讲解里用 `deck.html` 确认项 | 稳定题号、具体推荐值、题号↔来源对照 | 开放长问题 | 写进规则文档，记确认人、范围、日期 |
| **汇报**：一个版本已做完 | 老板 / 客户理解并提意见 | HTML `deck.html` | 总览放第一页、按角色与场景讲、产品真实原文、每页意见 | 题号、同意按钮 | 意见只作为修改输入，变成修改清单 |
| **技术对齐** | 技术人员或 agent | Markdown `tech-brief.md` | 已定 / 待你确认 / 请你查、稳定题号 | 界面示意、保存导出 | 直接回填文档或交还调用方 |

一份材料以主意图定骨架，可借其他意图的积木（例如探索讲解里插几个确认项）。范式、积木和公共约定见 [examples/](examples/README.md)、[blocks.md](examples/blocks.md)。

## 3. 只问用户发送本身

发给谁（角色、专业程度、关系），回来后要能决定或知道什么。不让用户先列题目：从这份清单倒推缺口，每项都要被一题或一页覆盖，没覆盖就补，用不上就删。

## 4. 写给业务方

- 写「什么情况下，谁现在做什么；例外怎么处理」，按 `/plain-language` 写，不出现字段、接口、状态机。
- 分清事实（开放问、要真实例子）、偏好（给对比场景选）、授权（记确认人、范围、日期）。
- 常理或现有系统就能定的、要非技术读者判断技术参数的、别处已有答案的，不问，直接写成结论。
- 法规、税务、法律类标「需先问顾问」，答复不当作合规结论。
- 不展示工程影响分析，那部分留在决策记录里。

## 5. 发出前

- 在浏览器里点一遍：意见、选择、翻页或筛选、导出、清空。
- 业务方材料：只把材料和收件人描述交给一个新 subagent，问它每页每题脱离上下文能否看懂、是否过长、是否该问这个人；改动大就再审一轮。技术对齐省掉这步。

## 6. 收回与交还

- 按题号回填来源条目；材料本身不是事实源。未答、含糊、冲突的保持待确认，必要时聚焦追问一轮。
- 交还调用方（通常是 `principal-engineer`）：得到的事实、确认人、范围、尚存分歧、受影响的设计假设。异步材料发出后，在调用方产物里留下材料路径和「等待中」。是否写入 `docs/principal/` 由 PE 决定。
- `grilling` 遇到业务事实缺口可转来，答复回来后回到它未完成的 frontier。

一次性多方案 UI 原型交 `prototype`，挂在真实应用壳里的预览交 `preview-design`。
