# Business Alignment

把「开发者不知道、业务方知道」的差距，变成对方能凭真实工作回答的问题，并把答复可追溯地交还。形式不预设：聊天一句话、Markdown、流程图、角色矩阵、交互 HTML 都可以，由缺口和收件人决定，调用者指定了就照做。

## 先查，再问

动手前先找已有答案：业务文档、确认记录、项目知识、`docs/principal/`（只读）。能找到可靠答案就直接用，不新增材料。问题对当前决定没有影响，也不问。

## 快速路径

缺口已经清楚、收件人和要决定的事都明确时，不必走完整流程：直接写出材料，过一遍下面的「发出前」，交付。

## 从决定倒推缺口

1. **只向用户追问发送本身**：发给谁（角色、专业程度、与用户的关系），回来后要能决定或知道什么。这两件用户总能答；不要让用户先列完整问题清单，缺口由你从业务主题里挖出来。
2. 先确认「拿到回答后，哪个工程决定会变」。优先问影响功能边界、数据责任、角色行为的，不做业务百科。
3. 问题瞄准**收件人知道而开发者不知道**的那部分。最重要的先问，异步往往只有一次机会。紧急度不同时拆成「现在答 / 以后答」。

## 分清事实、偏好、授权

- **事实**：现在实际怎么做、有没有既定规则或外部要求。用开放问题、真实案例或材料佐证问。
- **偏好**：两种都行，哪个更合适。给对比场景让对方选。
- **授权 / 决策**：某角色愿不愿承担一项责任、是否正式改变流程。要能记下确认人、适用范围、日期。

对方还没说现行做法之前，不要把工程方案包装成唯一的多选题。

## 让对方判断真实场景

写「什么情况下，谁现在做什么；出了例外怎么处理」，不让业务方评价状态机、字段、接口、锁。读者是业务方时按 `/plain-language` 写，不出现实现词。

> 企业已把本月工时交给税务师，之后发现一名员工填错了。现在实际怎么处理？税务师已经算完工资的话，做法会不同吗？

## 选形式

| 缺口 | 倾向的形式 |
|---|---|
| 单一规则、负责人、期限 | 聊天里一两句 |
| 正常与异常流程 | 场景描述、流程图 |
| 职责归属 | 角色操作矩阵 |
| 几个范围之间取舍 | 对比卡片、决策题 |
| 对界面和操作顺序理解不一致 | 交互 HTML 或演示 |
| 多人异步确认 | 可保存、可导出的材料 |

HTML 可承载开放问题、场景或固定选项，Markdown 也可承载决策题，两者不绑定题型。默认选最小、对方最省力的。

面向业务方的交互演示由本 skill 决定要不要做、要确认什么；需要多方案比较的一次性 UI 原型交 `prototype`，挂在真实应用壳里的预览交 `preview-design`。

[examples/](examples/README.md) 里有现成的决策问卷 HTML 和写法，是可选样例，不是模板。借用它们的稳定题号、本机保存、答复导出、改版迁移，或完全不用。

## 发出前

- **覆盖**：回来后要决定的每一项都有题覆盖；对不上就补题或删项。
- **筛题**：常理或现有系统做法就能定的不问，直接写成结论；重复的合并；要非技术收件人判断技术参数的不问，按系统现状定；答案已在别处的不问。
- **推荐**：给推荐就必须是你愿意直接落地的默认，写具体值（谁、几天、哪种）。
- **专业确认**：涉及法规、税务、法律的题明确标出，提示对方先问顾问再答，答复不当作合规结论。
- **题号**：稳定、映射回来源条目、永不复用；改版沿用旧号，删题时旧答复保留，合并题记 `from`。样例里有完整写法。
- **收件人视角审阅**：只把材料和收件人描述交给一个新 subagent，问它每题脱离上下文能否看懂、是否过长、是否该问这个人。改动实质性的再审一轮。

用于业务方的材料不展示工程影响分析，那部分留给开发者和决策记录。

## 收回答复

- 按题号把答复回填到来源条目；材料本身不是事实源，已确认的规则写进项目合适的事实源。
- **未答保持待确认**，不按推荐默认处理。冲突或含糊的答复也保持待确认，必要时做一轮聚焦追问。
- 答复里「我的意见」逐条评估后再更新来源。

## 交还

交还调用方（通常是 `principal-engineer`），说清：得到的业务事实、确认人、适用范围、证据、尚存分歧、哪些设计假设受影响。异步材料发出后，在调用方产物里留下材料路径和「等待中」，换会话后能接上。是否写入 `docs/principal/` 由 PE 决定，本 skill 不写。

`grilling` 遇到业务事实缺口可转来；答复回来后继续它未完成的 frontier。
