# Journey Walkthrough

把当前任务的验收内容做成简单 HTML，带用户按业务过程看懂操作与结果。显式调用时使用；默认整理已有材料。

## 取材

先从当前对话或用户指定位置确定项目根目录、任务目录与本次验收范围，再沿文档引用查找。相对路径以所在文档目录解析；项目配置中的路径按该配置的规则解析。不要把本机绝对路径写入本 Skill 或可分享的 HTML。

| 材料 | 从哪里拿 | 用来说明什么 |
| --- | --- | --- |
| 最新需求与决定 | 当前对话 → 当前任务的 spec / 决策文档 | 要实现的行为、范围与例外 |
| Journey | 任务计划的引用 → 项目用例索引 → 对应 E2E | 用户从哪里进入、做什么、预期结果 |
| 实际结果 | 本次验收报告 → 对应运行结果与日志 | 已通过、失败、未验证或材料不足 |
| 页面与数据证据 | 报告中的截图、视频、trace、数据回读引用 | 实际看见和确认了什么 |
| 环境与版本 | 本次运行记录、验收说明 | 结果对应哪个环境和版本，是否已经部署 |

截图和日志目录从项目配置、执行输出中读取，不假定固定目录名。优先沿引用定位，避免遍历所有历史产物。当前对话已修订的决定优先；材料冲突或版本不符时说明缺口。缺少材料仍可生成导览，相关部分明确标为待补，不补造结果。

## 组织内容

1. 读取并应用 [plain-language](../plain-language/SKILL.md) 的会话类 Core；生成新导览无需走已有文档的改写审批。若用户要求修改已有文档，沿其文档类流程执行，已有明确授权的范围直接复用。
2. 按业务过程组织 Journey，让读者知道：为什么做、从哪里进入并如何操作、预期怎样、实际验证到了什么。自然写成段落，不强制四段标题，也不逐行翻译测试代码。
3. 范围内的 Journey 都要有交代，成功、失败和未验证如实区分。说明可以充分，技术日志留到可展开的来源区。
4. 截图旁说明“看哪里、说明什么”。选择能看清目标控件与结果的截图；比较前后时尽量使用相同视口。页面表现与持久化、批量同步等结论分别引用相应证据。
5. 旧图不能代表新版；测试数据与真实业务数据要说清。保留失败和未完成事项，不把本地通过、已部署和用户确认混为一谈。

## 生成 HTML

复用 [最小骨架](assets/walkthrough.html)：白底、舒适的桌面阅读宽度、正文、截图与图注、状态标签、来源折叠区、原图放大。它是组件示例，按内容自由删减、重排或复制；目录、段落标题和章节数量均不固定。删除示例文案和占位图后再交付。

默认输出一份离线 HTML，截图用 data URI 内嵌；大型视频或附件用相对 HTML 的资源路径。输出位置遵循当前项目的产物约定，没有约定时放任务目录下的 `artifacts/journey-walkthrough.html`。来源位置用项目或任务相对路径说明；只有一起交付的附件才做相对链接。

完成后在桌面浏览器打开一次，确认实际内容可读、图片可见、放大可用即可。不做窄屏适配，不扩成额外测试流程。回复 HTML 链接及重要缺口。

只生成或更新导览；补跑验收、改产品、部署、发布分享链接需另有明确授权。整理材料本身不改变验收结论。
