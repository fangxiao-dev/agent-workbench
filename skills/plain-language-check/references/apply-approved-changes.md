# 回写已批准的说人话修改

仅在用户明确授权修改当前批次后读取。本流程把已经校准的候选安全地写回文档，不重新扫描新范围，也不替 requirement/spec 流程作合同决策。

## 1. 固定批准范围

- 当前批次未被否决的候选构成回写范围；用户对某项的批注优先于原建议。
- “同意，改掉”“未批注的都同意”等授权只作用于当前批次，不自动批准后续候选。
- 保留专业 token 的项目按校准后的中文主体表达处理，不机械全译。
- 合同决策项只有在 Owner 已明确裁决后才可回写；若仍未裁决，保持原合同并报告 blocker。

## 2. 先处理合同影响

若批准内容改变 scope、authority、验收条件、兼容承诺或 Gate：

1. 识别拥有该合同的 Decision、Spec、ADR 或其他权威文档。
2. 使用该仓库的 requirement/spec 对齐流程登记变化和 revision；语言检查不自行发明 revision 规则。
3. 将相关投影、调查输入和验收表述同步到同一结论。
4. 不以“术语统一”掩盖合同变化，也不把未决设计写成已确认事实。

纯语言项不走这条分支，直接做最小替换。

## 3. 应用改写与重命名

- 按语境逐处修改，避免全局替换破坏代码标识、历史引用或不同含义的同形词。
- 文件名只有在当前批次明确列出且用户批准时才重命名。
- 重命名后检查目标范围及仓库其他已跟踪文档中的入站链接、相对路径和旧文件名；需要包含未跟踪文件时使用仓库允许的搜索方式补查。
- 修订历史可以保留被取代的旧短语，但应明确它属于旧 revision，不能继续充当活动合同。

## 4. 验证与报告

回写后至少验证：

- 当前批次的活动文本残留为零；有意保留的专业 token 符合用户批注。
- 合同决策项在所有活动权威文档中一致，旧结论只出现在清楚标注的历史记录中。
- 本地 Markdown 链接和重命名后的入站引用有效。
- diff 只包含批准范围；项目要求的 revision binding、格式或文档检查通过。

报告时区分“当前批次已回写”“整个术语清理已 closed”和“上层任务包已 closed”。没有对应证据时不要扩大 completion claim。
