# 简单诊断汇报

把已经确认的 bug 诊断压缩成业务方一次能读懂的短报告。

## 输入边界

- 只使用当前上下文中已经确认的根因、修复方向和用户影响。
- 根因尚未确认时，直接写“尚未确认”，并说明缺少哪一项关键证据。
- 状态、验收和发布结论沿用 owning workflow，不自行升级。

## 输出

先用一句话直接说明：问题属于什么、是否为系统性问题，以及是否已排除环境或一次性数据。

然后只写三个部分：

### 根因

- 每个独立问题一条，用普通语言说明“什么逻辑导致了什么现象”。

### 建议修复

- 每个根因对应一个最小修复动作。
- 只写行为变化，不展开文件、函数、命令或调查过程。

### 修完后的效果

- 写用户能够直接观察到的结果。
- 保留仍需人工处理的真实例外。

## 简洁规则

- 每部分默认 1–3 条。
- 省略时间线、日志、代码位置、工具名、测试数量和内部术语；只有它们会改变当前决定时才保留。
- 不重复结论，不附长篇证据，不把建议写成完整 implementation plan。
