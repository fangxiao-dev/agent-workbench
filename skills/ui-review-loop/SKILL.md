# UI 评审闭环

仅当用户显式调用 `$ui-review-loop` 并指明角色时执行。普通 UI 修改不进入本流程；单人从截图直接改界面用 [`../screenshot-to-ui/SKILL.md`](../screenshot-to-ui/SKILL.md)。

两个角色：

- **实施主控（A）**：懂业务，提供截图与功能背景，裁决哪些意见接受，派修，确认业务未被改坏。
- **UI 评审者（B）**：独立看图，给出界面意见，最后对改后截图收口。B 不派修、不改业务判定，也不替代代码审查。

调用时由调用方给出：角色、产品原则文档路径、当轮评审／验收文档路径、产品专属约束（语言、尺寸、领域语义等）、模型与通信方式。B 若以 subagent 启动，A 必须写明它可读哪些材料、是否继承上下文；不要假定隔离会自动成立。

先读本文的"共用约定"，再只执行自己角色那一节。

## 共用约定

**三类文档**，评审与验收双向链接，不另建状态机或台账：

| 文档 | 模板 | 生命周期 |
|---|---|---|
| 产品原则 | [`templates/principles.md`](templates/principles.md) | 长期；放产品仓库，按项目现有文档路由，纳入版本管理 |
| 当轮评审 | [`templates/review.md`](templates/review.md) | 每轮一份；派修前定稿，此后只读 |
| 当轮验收 | [`templates/acceptance.md`](templates/acceptance.md) | 实施后开始，可多轮更新 |

截图与每轮报告可放 ignored 输出目录；正式原则和有用的脱敏结论纳入版本管理。

**编号贯穿**：评审里的意见编号在验收里沿用，不重编。

**证据配对**：改前／改后分别记录图片路径、对象、视口、语言和受验版本，再逐项说明是否一致及可比较范围；不是同一对象时只比较布局，不做像素级结论。关键区域须在截图内清晰可读；瞬时反馈在同次操作后的同一页面上下文取证。

**判断等级**：每条关于实现的说法标为 *观察*（截图可见）、*推测*（未核实）或 *已核实*（读过代码或数据）。

**UI 优先**：产品逻辑仍在打磨时，优先给不依赖逻辑的界面改法；涉及计数、完成条件、权限、学习规则等的意见单独标"涉及逻辑"，由 A 判断，不混入视觉修补。

**原则升级**：B 只能在评审里写"建议新增原则"；Owner 确认后由 A 写入产品原则文档。单轮意见不自动成为原则。

**功能与视觉分别下结论**：两类结论均使用通过／退回／待核实。退回须指出违反的验收点，证据不足则标待核实并列出缺口；说明无图原因不自动构成视觉通过。功能通过不等于视觉通过，B 看图通过也不等于业务正确。

## 实施主控（A）

1. **准备输入。** 按组整理：截图路径、核心功能、代码大致范围、已知不作数项（历史问题已修、旧文案已移除等）。写入评审文档各组"输入"节。
   完成标准：B 不需要追问就能看懂每张图在干什么。
2. **收集意见，按批裁决。** 相关界面全部看完后再统一裁决，不逐图修补。对 B 的每条意见标 接受／部分接受／不做；接受的必须落到具体截图、区域、代码位置、修改内容和验收点，不做的写理由。不要只摘抄原则。
   完成标准：每条意见都有标注，每条接受项都能直接派修。
3. **处理微调。** B 的一轮微调后定稿评审文档。事实纠错不算新一轮；仍有产品取舍或实质分歧时交 Owner。
4. **派修。** 由 A 派修，复用现有的派工与验收流程（如 [`../dispatcher/SKILL.md`](../dispatcher/SKILL.md)、[`../run-acceptance/SKILL.md`](../run-acceptance/SKILL.md)）；代码审查用独立 reviewer，不以 B 的截图意见替代。
5. **交付收口材料。** 实施后在验收文档列出每个编号的实际改动、改前／改后截图（满足证据配对）、实现版本与代码路径／行号，交给 B。A 确认实现符合批准的业务边界；纯 UI 项确认业务行为未变，给出功能结论。
   完成标准：每个接受项均可定位改动和证据；缺证项明确标为待核实。
6. **处理退回与补证。** 在验收文档追加 A 的裁决、负责人、修复版本及复验结果；原意见沿用编号，新发现使用未占用编号并关联原组。B 复核视觉，A 复核功能，只复验受影响项，保留此前有效结论。下一批改进记录去向，不扩入本轮。
   完成标准：本轮接受项均有两类结论；退回或待核实项尚未关闭时，明确待办与负责人，不写全部通过。

## UI 评审者（B）

1. **读原则，独立看图。** 先读产品原则和此前各轮裁决，避免重提已否决的意见；不看 A 对本组的倾向。只有需要判断实现时才读代码。
2. **写独立意见。** 每条写入评审文档"独立意见"节，字段固定：编号、截图／区域、问题、建议、纯 UI／涉及逻辑、观察／推测／已核实、改动量估计。先写跨图的共性问题，再写单图问题。可附"建议新增原则"。
   完成标准：组内每张图都看过，每条意见字段齐全。
3. **微调。** 只回应 A 的裁决：纠正事实、指出实施说明里会让视觉走样的含糊处（如"可发现""对齐"没有具体做法）。默认一轮。
4. **对图收口。** 按验收文档逐编号对照改后截图与验收点，按共用结论规则标通过／退回／待核实。新发现分三类：本轮遗漏、修复回归、下一批改进；本轮之外的问题不阻断本轮。
   完成标准：每个编号都有结论，新发现均已分类。
