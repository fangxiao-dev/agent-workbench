# 决策模式

适用：你已经能给出默认做法，只差对方拍板（业务方、Owner、客户）。目标是让对方逐题点选，拿回结构化结论，而不是散文。

## 每道题的结构

- **稳定题号**：映射回来源条目（需求编号、规则编号、待办编号）。题号永不复用，删题后也不把号给新题。
- **问题**：一个决定一题，不写复合问句。
- **为什么问**：一两句现状与影响，让对方知道答错会怎样。
- **我们的推荐**：可直接执行的默认做法，写具体值（谁、几天、哪种）。对方不回复时就按它执行，所以推荐必须是你愿意落地的做法。
- **固定选项**：同意推荐 / 未来再做 / 不做 / 我的意见。“我的意见”留空不算作答；再点一次已选项即取消。
- **需专业人士确认**（可选标记）：法规、税务、法律类结论，提示对方先问顾问再答，不当作系统给出的合规结论。

Markdown 写法的最小示例：

```markdown
### Q-001 新订单默认由谁审核？

_为什么问：审核人决定订单多快能处理，也决定谁对错误负责。_

**我们的推荐：** 默认由各门店负责人审核；金额较大的再交给总负责人。

- [ ] 同意推荐　- [ ] 未来再做　- [ ] 不做　- [ ] 我的意见：
```

## 题号 ↔ 来源对照（发出前必须有）

发出前产出一份对照：每个题号对应哪个来源条目（需求、规则、待办编号），以及该题被筛掉或合并时的去向。写在来源文档里，或放在问卷旁的 sidecar 文件（如 `<问卷名>.mapping.md`）。HTML 问卷每题同时填 `source` 字段，导出时会一并输出。回填按这份对照执行。

## 发出前筛题

逐题过一遍，满足任一条就不问，直接写成结论记进来源文档：

- 凭常理或现有系统做法就能定（例如文件大小、格式沿用系统现有上限）；
- 与另一题实质重复：合并为一题，合并题记下 `from: [旧题号]`；
- 要非技术收件人判断技术参数：参照系统现有做法定，不交给对方；
- 答案已在其他已定结论里。

读者是业务方时，按 `/plain-language`（`../../plain-language/SKILL.md`）写：业务语言，不出现字段、接口、状态机等实现词。

## 排序

- 按主题分章；章内最影响后续决定的题在前。
- 答复紧急度不同时拆成两部分：“现在答”在前，“以后答”（例如后续阶段的功能）在后，并在说明区写清先答哪部分、大约要多久。

## 回收闭环

1. 导出的答复每行带题号（HTML 同时带来源）。
2. 拿到答复后按题号与对照回填来源文档：同意推荐 → 来源条目改为已定；未来再做 / 不做 → 按含义调整范围；我的意见 → 逐条评估后更新，并在需要时回问。
3. 问卷本身不作为结论的事实源；结论只写在来源文档里。

## 改版

- 修订同主题问卷时沿用原题号与原 `storeKey`（HTML），并同步更新题号 ↔ 来源对照。
- 题号不复用；新题用新号。
- 删题：对方之前的答复保留在导出末尾（“旧版问卷里已删除或合并的题”）。
- 合并题：新题标 `from: [旧题号]`，页面上显示对方在旧题里的回答。
- 选项值改名时用迁移表把旧值映射到新值（HTML 模板的 `legacyChoices`），已答内容一律保留。
