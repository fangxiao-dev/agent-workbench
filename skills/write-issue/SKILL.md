# 编写 Issue

让每个 Issue 保持一份当前事实和最小时间线。正文应足以让人或 agent 立刻理解当前工作；评论只保留协作事件。

## 工作流

1. 写入前阅读当前正文、相关评论、关联 Issue 或 PR，以及仓库的 Issue 约定。区分当前事实、已被替代的计划和历史证据。
2. 按下方内容归属规则决定信息应放在哪里。不要因为担心覆盖正文就改发评论；GitHub 保留正文编辑历史。
3. 创建或重写正文，使首屏说明目标、当前状态、剩余工作和关闭条件。链接详细事实来源，不复制它们。
4. 只有在记录允许的协作事件时才添加评论。评论必须自包含、标明事件类型，且不得重复正文。
5. 当关闭条件满足，或 Issue 被明确判定为重复、拒绝或已被替代时关闭它。适用时指向后继事项；不要把已过时的 Issue 长期开着当档案。
6. 以首次接手的 agent 视角重读渲染结果，删除过时方案、重复状态、复制的日志，以及对权威来源含糊的表述。

完成标准：默认阅读路径只存在一个明确的当前状态；每条保留评论都有持久协作价值；实现证据可以通过链接找到。

## 内容归属

| 内容 | 放置位置 |
| --- | --- |
| 目标、范围、当前状态、已冻结决策、验收和下一道门 | Issue 正文 |
| 持久的设计、合同、调研或运行手册 | 仓库文档，并在正文中链接 |
| 代码改动、审查讨论、检查和测试结果 | PR、commit 或检查产物；链接而不是复制 |
| Owner、优先级、阶段、日期和流程状态 | Assignee、label、milestone、Issue field 或 Project |
| 可独立负责和关闭的工作 | Sub-issue；父 Issue 保持为汇总项 |
| 不可逆的协作事件 | Issue 评论 |

## 正文合同

只使用实际承载信息的章节，优先采用以下顺序：

```markdown
# 目标

[该 Issue 要达成的业务结果。]

## 当前状态

[现在已知什么、已完成什么、还剩什么，以及 Issue 是否可以关闭。]

## 范围

- 范围内：...
- 不在范围内：...

## 决策或要求

- ...

## 验收与关闭条件

- ...

## 权威来源与依赖

- [权威文档、PR、父项、子项或 blocker](...)
```

小 Issue 可以收敛为简短说明和验收标准。Epic 将详细执行留在 sub-issue，将持久设计留在仓库文档。

当前事实变化时直接原地重写当前状态章节。删除主路径中已被替代的表述；只有旧选择确实能避免未来误判时，才保留简短的“已替代”说明。

## 评论白名单

只为以下事件发布评论：

- `DECISION`：协作者共同作出的重要决定，或已改变既定方向。
- `BLOCKER`：必须等待他人或外部变化才能继续的条件。
- `EVIDENCE`：无法从仓库重建的生产、事故、合规或外部系统证据。
- `HANDOFF`：责任或执行阶段移交给另一位 owner。
- `CLOSURE`：关闭的简要理由和证据。

不要发布百分比、常规进度、命令输出、文件清单、AI 工作日志，或已由正文、字段、commit、PR 或检查表示的事实。

如果一次重要的正文重写需要通知活跃协作者，可以用一条短评论说明正文现为权威来源，并指出被替代的方向；通知不是新正文的第二份副本。

## 清理历史

不要为了压缩时间线而抹去有意义的人类决策。用户明确授权清理既有 Issue 时，先把当前事实收敛到正文，再最小化过时、已解决或机器生成的评论。只有评论完全没有建设性、错误、重复，或涉及敏感信息且仓库政策允许时，才删除评论。

## 安全与最终汇报

创建、编辑、评论、关闭、重新打开、打 label、分配 assignee 或最小化 Issue 都属于远程修改。只执行用户明确授权的操作，并准确汇报变更了哪些 Issue 字段或评论。
