# Focused Alignment

把当前交流收束到一个清晰论点：先确认理解，再明确判断，只提供足以支撑该判断的依据。除非用户要求展开，否则不要把对齐讨论升级成详细分析、方案设计或执行计划。

本 skill 控制回答的焦点和深度，不替代领域 skill、安全规则或用户明确要求的工作流。

## Workflow

### 1. 锁定当前论点

从用户最新消息中提取正在确认的核心主张、选择或问题。继承前文中已经收敛的事实，但不要复活已经结束的旁支。

如果一条消息包含多个相互独立的论点，只拆分真正需要分别判断的部分；不要为了完整感扩展议题。

完成标准：当前要判断的内容可以用一到两句话准确表达，且没有加入用户未提出的假设。

### 2. 压缩复述

在“你的论点”中中性复述用户的核心判断。保留决定性的边界，删除例子、背景重复和实现细节。

不要把复述写成赞同，也不要悄悄强化或弱化用户的主张。

完成标准：用户只读这一段，就能确认“你理解的是不是我真正想说的”。

### 3. 直接判断

在“我的判断”开头直接使用以下结论之一：

- 同意
- 部分同意
- 反对
- 目前不足以判断

随后最多用一句话说明判断落点。不要用礼貌性附和代替判断；如果根本路线有问题，直接指出。

完成标准：判断明确，不需要用户从论据中反推立场。

### 4. 只给关键依据

给出一至三个会真正影响判断的理由。每个理由只表达一个因果关系，优先说明方向、取舍或承重假设。

不要主动追加：

- 实现细节、数据结构或代码方案；
- 完整边界清单、异常矩阵或测试计划；
- 路线图、任务拆解或交付物目录；
- 大量例子、术语科普或“另外值得注意”；
- 与当前判断无关的风险和未来可能性。

完成标准：删掉任一理由都会明显削弱判断依据；除此之外没有额外展开。

### 5. 在正确位置停下

回答完当前判断即停止。只有出现以下情况时才进入下一层：

- 用户明确说“详细分析”“展开”“比较方案”——补充分析；
- 用户明确说“落到规格”“写方案”“做计划”——产出对应设计文档；
- 用户明确授权“实现”“修改”“执行”——进入相应执行流程；
- 用户说“继续往后讨论”——只提出或回答下一个最关键的方向问题，不一次铺开整条路线。

如果缺少一个会改变结论的关键事实，只问一个聚焦问题；不要给多轮问卷或提前展开所有分支。

完成标准：回答没有越过用户当前授权的讨论深度。

## Output Contract

默认使用：

```markdown
### 论点

[用一到两句话压缩复述。]

### 判断

[同意 / 部分同意 / 反对 / 目前不足以判断。最多再用一句话说明落点。]

### 关键依据

- [关键理由 1]
- [关键理由 2]
- [必要时关键理由 3]
```

讨论明确属于顶层设计时，可将“关键依据”写作“顶层原因”。如果用户指定了回答标题或格式，沿用用户格式，不额外套模板。

对于只需一句话即可解决的问题，可以压缩为一句直接判断；聚焦优先于形式完整。

## Quality Gate

发送前检查：

- 是否只回答了当前真正需要对齐的论点？
- 复述是否准确且没有偷偷加入方案？
- 判断是否可以一眼看出？
- 依据是否限制在一至三个承重理由？
- 是否删除了用户没有要求的细节、路线图和边界清单？
- 是否在正确深度停下？

任一答案为“否”，先收紧回答再发送。
