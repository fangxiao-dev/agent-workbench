Impl-Package 体系

它由两部分咬合而成:一套不会烂的文档结构,和一条可伸缩的开发流程。大改动多走几步,小改动少走几步。

四个它真正解决的问题

↔

按需伸缩,不做无用功

小改动只走「规格 + 计划」;复杂改动才长出验收票和执行图。没有一刀切的重流程。

♻

文档不会烂

每次关闭时把长期知识归档进「常青文档」,旧过程退成 git 历史。不再有几十份没人维护的文档。

◎

一份东西一个主人

每类产出只有一个负责的 skill、一个事实源,禁止两处维护同一状态。冲突时有固定裁决顺序。

⇄

自动接力,断链自动退回

各阶段靠共享前缀互相识别接力;缺了上游产物就自动退回去补,而不是硬着头皮往下猜。

第一部分

目录层级与文档维护

先看「真相住在哪、怎么不烂」——这是整个体系稳定的地基,每次开发最后都汇回这里。

为什么要换

从「文档越堆越烂」到「变更是事件、真相常青」

对比最早那套 func-design + impl-plan——每改一次就写一份设计加一份计划,永久堆在仓库里,最终堆到近百份、规则散落、无人维护。新体系换的是这套的根子。

文档的骨架

常青四层：让真相有固定的家

每次改动是「事件」,常青文档是「当前快照」,回刷就是把新事件压实进快照。四层各答一个问题,互不替代,靠固定文件名保障纪律。

产品级意图为什么做、给用户什么价值 · 顶层 PRD / CONTEXT
模块级意图这个模块为何存在 · module-knowledge/<模块>/prd.md
模块级契约当前怎么行为:接口/状态/边界/失败 · module-knowledge/<模块>/spec.md
变更时设计这一次为什么、怎么改 · implementations/<package-id>/
第二部分

开发流程:6 步开发 ＋ 1 步交接

做一次改动怎么走这条流水线。6 步把改动做出来,第 7 步(交接)把学到的知识汇回第一部分的常青层——两部分在这里咬合。

它怎么运转

一条主线，两处按需长出

七个阶段串成一条线,每步有唯一负责的 skill 和产出。切票和排图只有需要时才长出来(灰色虚线);缺了上游就自动退回。

1

对齐与调研

必经
把需求和仓库现状,变成一个可决策的方向。
req-align · Design 门design.md
触发来了新需求 / 需求变更,动手前第一步
2

写规格 Spec

必经
八节当前合同:行为、状态、边界、失败恢复、验收。它维护 D/S revision,不保存执行拓扑。
req-align · Spec 门spec.md
触发Design 门通过后,同一 skill 接着过 Spec 门
3

Attempt 计划 ＋ 按需切票

必经
计划声明本次 Attempt / D-S-P revision / Composition,保存执行策略、验证选择与 append-only Execution Record。≥2 个独立验收切片时才切票。
impl-planningplan.mdto-ticketstickets=true 才切tickets/
触发Spec 通过要落地;是否切票由当前 plan 的 tickets 决定
4

排执行图 DAG

按需 · earn 才走
需要多任务并行、或有 seam 要协调时,才把计划拆成可并行的任务和依赖图。
create-task-dagdag.md
触发当前 attempt plan 判定 dag=true
5

执行

必经
恢复现场 → 确定下一步 → 执行 → 证据写入 plan Execution Record → findings 分流 → gate ledger 新判决。
dev-with-trackprogress · Execution Record · gate.md
触发上游就绪;跨 session 续上也走这里
6

审查

1 恒查 · 2 按需
只有 code-review 每次都跑;另两个按风险信号触发——小改动可能一个都不触发。结论喂给 gate 决定能不能关门。
code-review恒查module-review契约变化时safety-review碰安全路径时
+1

回刷交接

两部分的桥
写 terminal gate entry 前完成轻量登记(把长期知识记进 _pending、truth pointer 与必要 stub),不用当场压实常青文档。真正的压实由定期 backfill 任务做;watermark 与无主 commit 扫描负责发现意外 capture gap。
backfill-stable-docs_pending.md定期 report / apply · 兜底
触发关门时登记;压实与兜底由定期任务做
断链时自动退回上游,而不是硬猜
  • 执行时发现缺计划 → 退回 impl-planning 补
  • 输入太宽、还没切片 → 退回 to-tickets 先切,不自己乱切
  • 组合和现有产物对不上 → 退回 req-align 重过 Spec 门
  • 只有单张票却要跨票协调 → 要计划 + 相关票子集,不擅自推断
同一套体系,四种情况

同一个「库存模块」，四种大小的需求

最能说明伸缩力的,是拿同一个模块的四种大小需求,看体系自动走出四条深浅完全不同的路。判定只问两个是非题——要不要切票、要不要排图——体量是结果,不是预先分档。(例子为演示,不必真实)

S
微改动
tickets=F · dag=F
需求库存列表加一个「最近盘点时间」只读列。
对齐→Spec→计划→执行→关门
好在哪 · 不被迫走重流程,不产生任何多余文件。规格+计划直接落地,十几分钟收工。
M
中等 · 能分别验收
tickets=T · dag=F
需求做「低库存预警」:阈值设置界面 + 触发计算 + 通知邮件——三块能分别验收。
对齐→Spec→计划→切 3 票→逐票执行→关门
好在哪 · 三个切片能分别验收、分别交付,不用等全做完;计划不塞任务细节,每张票是自己的验收事实源。
L
复杂 · 并行 ＋ 协调
tickets=T · dag=T
需求「多仓库库存」重构:数据迁移 + 读模型 + 多个页面 + 跨切片 seam,要多人并行。
对齐→Spec→计划→切票→排执行图→并行执行→关门
好在哪 · 多人并行有明确 ownership 和 seam 协调,不互相踩;执行图恢复「拓扑」、进度账本恢复「状态」,断了也能续。
D
执行拧巴 · 不值得切票
tickets=F · dag=T
需求重写「库存计算引擎」内部:一次交付,但任务之间依赖复杂。
对齐→Spec→计划→排执行图→执行→关门
好在哪 · 复杂的执行依赖被显式画出来、按序推进,但不被迫造几张没意义的验收票。验收语义留在规格里。
