Impl-Package 体系

它由两部分咬合而成:一套不会烂的文档结构,和一条可伸缩的开发流程。六步主流程保持一致,只有真正需要时才增加 tickets 或 DAG。

按需伸缩,不做无用功

小改动不额外生成 tickets 或 DAG;复杂改动才按验收切片和执行依赖扩展。没有一刀切的重流程。

♻

文档不会烂

每次关门先 capture 值得保留的知识;常青文档的整理可由后续获授权的 backfill 完成。

◎

一份东西一个主人

每类产出只有一个负责的 skill、一个事实源,禁止两处维护同一状态。冲突时有固定裁决顺序。

⇄

自动接力,断链自动退回

各阶段靠共享前缀互相识别接力;缺了上游产物就自动退回去补,而不是硬着头皮往下猜。

第一部分

目录层级与文档维护

先看「真相住在哪、怎么不烂」——这是整个体系稳定的地基。每次开发关门时先登记 durable delta,后续再按授权把它压实进这里。

为什么要换

从「文档越堆越烂」到「变更是事件、真相常青」

对比最早那套 func-design + impl-plan——每改一次就写一份设计加一份计划,永久堆在仓库里,最终堆到近百份、规则散落、无人维护。新体系换的是这套的根子。

文档的骨架

常青四层：让真相有固定的家

每次改动是「事件」,常青文档是「当前快照」。gate 内 capture 记录待保留增量;backfill 是 gate 后独立的 compaction,可以延期、批量或周期执行。四层按“端到端价值 → 模块贡献 → 可验证行为 → 本次变化”逐层下钻,只链接、不复制。

产品 / Journey 意图端到端 journey 为什么存在、谁参与、最终得到什么结果 · 顶层 PRD / CONTEXT
模块级意图该模块为 journey 贡献什么、负责和不负责什么 · module-knowledge/<模块>/prd.md
模块级契约当前怎么行为;跨模块规则由一个主模块拥有,依赖模块只引用 · module-knowledge/<模块>/spec.md
变更时设计本次跨模块怎么改、影响哪些 journey / module anchor、如何迁移和协调 seam · implementations/<package-id>/
跨模块 journey 怎么放
  • 一个 journey 可以跨多个模块,但端到端 intent 只有一个顶层 owner。
  • 每个模块只写自己的价值贡献;跨模块 rule/seam 只由一个 primary module spec 拥有,其他模块链接过去。
  • implementation package 只记录“这次改变了什么”和 canonical anchor 的预期 delta,不复制整条 journey 或长期合同。
第二部分

开发流程:6 步主流程

6 步把改动做出来并完成 gate。durable-delta capture 是 terminal gate 的关门条件;真正更新常青文档的 backfill 位于主流程之后,按需提示和授权执行。

它怎么运转

一条主线，两处按需长出

六个阶段串成一条主线,每步有唯一负责的 skill 和产出。切票和排图只有需要时才长出来(灰色虚线);缺了上游就自动退回。

审查与 Gate 关闭

1 恒查 · 2 按需
code-review 恒查;小改动可能不触发额外的 module-review 或 safety-review。terminal gate entry 写入前必须 capture durable delta 或 none + reason,完成 _pending、truth pointer 与必要 stub;不要求当场更新常青正文。
code-review恒查module-review契约变化时safety-review碰安全路径时
Gate 后可选维护:提示 Backfill,但不自动执行
  • agent 可以提醒存在待 backfill 内容;owner 可以现在做、以后做或暂不做。
  • 不执行不会重新打开 gate,也不阻塞本次交付或任务 closed。
  • report 只在用户明确要求、已有维护计划或周期任务上下文中运行;apply 还需要 owner 批准具体 report item。
  • watermark、gate 漏登与无主 commit 扫描用于后续发现 capture gap,不属于每次关门的必经步骤。
断链时自动退回上游,而不是硬猜
  • 执行时发现缺计划 → 退回 impl-planning 补
  • 输入太宽、还没切片 → 退回 to-tickets 先切,不自己乱切
  • 组合和现有产物对不上 → 退回 req-align 重过 Spec 门
  • 只有单张票却要跨票协调 → 要计划 + 相关票子集,不擅自推断
同一套体系,四种执行组合

可以主动说“按 S / M / L / D 模式做”

字母是便于下发的执行组合,不是任务大小评级。agent 会展开为两个判断——要不要拆成多个可独立验收切片、要不要显式执行依赖图——并校验实际需求是否匹配。匹配就采用;冲突时先解释建议和 artifact 影响,由 owner 决定,不会静默改模式。

主动指定示例
  • “这个需求按 M 做”表示希望拆成多个可独立验收切片,但不建立执行依赖图。
  • 如果实际只有一个验收结果,agent 会建议改为 S;确认前不会为了服从字母制造 tickets。
  • 如果已经存在必须协调的并行 seam,agent 会说明为什么需要 L 或 D;确认前不会删除必要 DAG。
S
直接执行
单一验收 · 不切票 · 不排图
需求库存列表加一个「最近盘点时间」只读列。
对齐→Spec→计划→执行→Capture 后关门
好在哪 · 不被迫走重流程,不产生任何多余文件。规格+计划直接落地,十几分钟收工。
M
分片验收
多个独立验收 · 不排图
需求做「低库存预警」:阈值设置界面 + 触发计算 + 通知邮件——三块能分别验收。
对齐→Spec→计划→切 3 票→逐票执行→Capture 后关门
好在哪 · 三个切片能分别验收、分别交付,不用等全做完;计划不塞任务细节,每张票是自己的验收事实源。
L
分片验收 ＋ 协调执行
多个独立验收 · 显式执行图
需求「多仓库库存」重构:数据迁移 + 读模型 + 多个页面 + 跨切片 seam,要多人并行。
对齐→Spec→计划→切票→排执行图→并行执行→Capture 后关门
好在哪 · 多人并行有明确 ownership 和 seam 协调,不互相踩;执行图恢复「拓扑」、进度账本恢复「状态」,断了也能续。
D
单次验收 ＋ 协调执行
单一验收 · 显式执行图
需求重写「库存计算引擎」内部:一次交付,但任务之间依赖复杂。
对齐→Spec→计划→排执行图→执行→Capture 后关门
好在哪 · 复杂的执行依赖被显式画出来、按序推进,但不被迫造几张没意义的验收票。验收语义留在规格里。

以上四种 composition 都在 gate 内完成 capture；gate 后是否 backfill 不属于需求规模判定，也不阻塞本次任务完成。
