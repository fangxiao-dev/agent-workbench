# Run Acceptance

用户调用本 Skill 即同意本轮主控与验收者 session 按本流程相互通信。本 Skill 是“怎么走查”的唯一手册；Spec 的 Journey 只定每条旅程的取证方式。

整包验收的角色分工：

- **主控**：守验收依据，分诊验收者上报的问题，核对截图并判定通过与否，派修复 worker 和独立 reviewer，串行集成到验收分支，最终收口。
- **验收者**：独立 session 或子代理，也称走查者。独占验收现场：起环境、造数据，逐步走查并截图，每走通一条旅程提交一次，交结果包，复测集成后的修复；复测默认续用原验收者（SendMessage 或 resume），原验收者的现场或上下文不可用才换人。
- **修复 worker**：由主控派出的 subagent，一个不相交的问题域一个，各自独立 worktree。
- **独立 reviewer**：由主控派出的 subagent，审修复代码；整包终审、证据存疑时判证据是否 PASS。
- **业务复审者**：由主控在旅程走通后派出的 subagent，每次只看一条旅程。它只读该旅程的 Journey、设计文档和截图，不读代码，站在每一步的角色视角找业务上说不通的地方。合同见 [references/semantic-reviewer.md](references/semantic-reviewer.md)。
- **Owner**：只裁决依据本身定不了的产品取舍和范围变更，以及须本人验的三类步骤（见[走查记录模板](assets/walkthrough-record.md)）。

验收、修复、多个修复之间三者并行。确定本 session 的角色后读取对应参考：

- 主控 → [references/controller.md](references/controller.md)
- 验收者 → [references/verifier.md](references/verifier.md)

| 分诊问题或判定结论 | [分诊](references/controller.md#2-分诊)、[判 PASS](references/controller.md#5-判-pass)，并核对下文「验收依据」「证据」 |

## 验收依据

- **合同内**：已批准的方案或合同（Decision、Spec、PRD、AC、journey 等）。每条要求都要验到，标准不因实现缺失而降低，也不因验收者的推断而增加。
- **合同外的既有能力**：固定一个基线版本（如部署分支的具体 SHA）。外围行为按基线判断“本来就有/本来就没有”，基线没有的能力记录下来，不扩展实现。
- **已批准且与合同一致的 journey**：它就是通过标准，结果包直接引用它的步骤编号。只为它没覆盖的合同要求补专项验证。journey 与合同冲突时按合同修订 journey，批准材料之间互相冲突才交 Owner。
- **模糊或冲突**：主控先查合同原文和基线代码；仍然定不了，才把具体场景交 Owner。

## 所有权

- **验收现场**（运行中的服务、浏览器、验收数据库数据、临时配置）只由验收者写。主控和 worker 对现场只读，诊断结论以建议形式交给验收者执行。
- **验收分支**只由主控写，用 merge 或 cherry-pick 集成通过复核的修复；验收者只往证据目录提交走查记录与截图。
- **共享文档**（journey、覆盖表）同一时刻一个维护者。另一方要改时先声明接手，改完交还。
- **共享运行状态**（如 Impl-Package 的 `state.json`）串行登记：并发产出的文件各自唯一命名，登记命令依次执行。
- **受验 HEAD** 每轮锁定；现场与集成分支用不同工作目录，代码只经集成窗口进入现场。
- **修复 worker** 各用独立 worktree；需要可变运行资源（数据库等）时用隔离实例。

## 通信

事件驱动。过程日志留在证据目录，只在这些节点跨 session 发消息：

1. 结果包（验收者 → 主控）
2. 问题或阻塞（验收者 → 主控），注明是否影响其他旅程；同类失败连续两次的上报格式见[走查](references/verifier.md#2-走查旅程)
3. 咨询：只读诊断、入口位置、测试数据准备方法（验收者 → 主控）
4. 依据或范围变化、复核回执（主控 → 验收者）
5. 集成窗口握手（双向）

### 结果包

引用不复述，例外才展开：

- **位置**：journey 步骤编号或覆盖表行，受验 HEAD
- **候选结论**：PASS / FAIL / BLOCKED / INCONCLUSIVE
- **证据位置**：走查记录与截图的精确定位，或已有工具输出的定位，附本次断言需要的对象与版本标识
- **例外**（只在出现时写）：与 journey 的偏差（条件、数据、操作不同）、证据证明不了的部分、FAIL 时的实际与预期、现场是否保留

证据完整覆盖 journey 通过标准时，结果包就是位置、候选结论加证据位置一行。

### 集成窗口

1. 主控：说明哪些修复已过复核待集成，并按实际影响说明现场需要什么：不受影响、停写、停服重启，或含迁移。
2. 验收者走到安全点，按需执行：停服时只停自己启动的进程树并确认端口释放；有迁移时先备份并记录迁移状态。回复“可集成”。
3. 主控集成，回复新 HEAD、迁移文件与回退方式（如有）、复测入口，以及哪些既有结论受影响。
4. 原验收者核对 HEAD，需要时重启并通过健康检查，从足以证明因果链的起点复测原失败场景。

多个已过复核的修复尽量合进同一个窗口。

## 变体走查

Spec 有 `### Journey 变体` 时适用，各入口类型相同。

- **选取**：必验变体全部走；有变体的 Journey 至少走一个，都非必验时由主控选，列进覆盖表。
- **走法**：按变体的前置准备好账号和数据，以变体身份走到被验步骤；“完成”类继续到依赖其结果的下游步，“部分”“拒绝”类截下表现即可。
- **证据**：本期只写走查记录与截图，不登记 journey-step evidence，runId 与主路径分开。
- **判定**：按变体的预期与可观察表现判定，偏离按[分诊](references/controller.md#2-分诊)当缺陷处理。
- **沿用**：与主路径同一原则（见「证据」的版本漂移），理由写在走查记录里；证据始终按现行合同判定，变体依赖的预期改了，旧记录就不能直接沿用。

## 证据

- **取证方式**：页面步按 Journey 的“取证：”行取证。`浏览器走查`（默认）用执行 agent 自带的内置浏览器工具逐步操作并截图，登记走查截图加走查人；`Playwright（理由：…）` 只覆盖理由点名的精确测量步（响应时间、延迟阈值、动画时长），登记 trace。取证方式在建 Journey 时定，失败后沿用原方式排查；要改方式走 Spec 修订。内置浏览器做不到的单步（原生确认框被取消、下载不落盘、截图拍不全）可改用 Playwright 补位，这不算改取证方式、不走修订，但每步在走查记录写明原因，其余步仍走查。
- **分层对应**：页面承诺用真实页面的截图；写入、工具调用、权限和内部状态用接口、数据库或运行日志证据。结果相似、编号相同、HTTP 200、后台造出的数据，都只证明它们自己那一层。
- **证据配对**：按断言核对对象、适用身份或范围、版本或采集时点，以及原始工具调用定位。先确认这些条件再比较结果；文件名相同不代表请求相同，后来的状态不能倒推为先前的状态。
- **条件先成立**：对照前确认业务条件确实一致。条件不成立的样本标为无效并保留，不计入结果。
- **数据隔离**：无关场景用独立数据组，前面场景留下的状态不进入当前场景的命中路径；合同要求连续验证的场景（上一步产生、下一步复用）保留前序状态。
- **最小输出**：优先复用项目的只读、脱敏入口；查询或解析时先投影本次判定所需字段，再输出到工具结果或证据摘要，遵循项目的日志边界。其余大对象保留在原存储中。
- **版本漂移（默认按影响范围复测，不全量重走）**：只有非运行时改动（文档、`.md`、`.agents/`、`.claude/`）时自动沿用。有运行时改动时主控看 diff 定影响范围：受影响的步骤在最终 HEAD 上从“足以证明因果链的最近起点”重走（该步依赖的前序状态需要重建时，从产生该状态的那一步起）；未受影响的步骤与旅程用 `evidence carry-forward` 写明理由沿用。只有两种情况整条旅程从第 1 步重走：改动波及该旅程的前置数据或全局行为（夹具、迁移、权限模型、时钟），或合同明确要求该旅程整条连续验证且改动落在其链路上。中途修过数据或代码的 run 不整体作废，只把受影响段按上述规则重走。
- **复验路由**：前提是该旅程在本包内至少完整走过一次、判为通过，并且已登记进 evidence 索引（没有登记，`evidence impact` 判不出受影响步骤，也不能走 R1/R2）。之后由主控按 diff 给每个受影响的步骤指定 R1（文案、格式）、R2（状态显隐）或 R3（因果链，从最近起点重走）；分类表与复测清单格式见 [controller.md](references/controller.md#2a-复验路由)。拿不准走更重的路由；改动涉及共享函数或全局行为时不能走 R1。证据登记多写一个字段 `route: R1 | R2 | R3`。
- **只追加**：证据文件用唯一文件名，写入后不覆盖。原始产物（截图、API/MCP 返回、数据库查询、临时脚本）一律写项目被 git 忽略的输出目录下按 run 分的子目录（例如 `output/qa/<runId>/`；QA 产物统一放主工作区的 `output/qa`，用 `git rev-parse --path-format=absolute --git-common-dir` 的父目录推出，不论在哪个 worktree 里都一样，不写死绝对路径），不提交；截图照常每一步都拍，只是不提交：全部放该目录，一张都不进 git；仓库只提交走查记录（结论、关键数值、截图的本机路径）和文件/接口步的 1 个关键返回；页面步的证据登记直接指向本地截图路径（`output/qa/<runId>/…`），其余指向走查记录。截图是自用的，提交会让仓库历史无限增长。项目另有约定时以项目为准。

## 收口

整包 PASS 需要同时满足：

- 覆盖表中每条合同要求都有结论和对应层级的证据；
- 「变体走查」选取的每个变体有完整走查记录、按预期通过、在最终 HEAD 或按沿用原则留痕（runtime 不识别执行者，由主控在此核对）；
- 已确认的缺陷都已修复、复核、集成并复测；
- 每条旅程都有业务复审记录：判为本包修的项已修复，补拍后已经复看；登记为后续的项已有去向；
- 无效样本、证据缺口、范围调整、Owner 决策都有处置；
- 终审通过：Impl-Package 包走它的 terminal review，其他情况由独立 reviewer 审最终 diff；
- 临时配置恢复原样，自有进程清理，验收数据和证据保留。

“验收结束”和“验收通过”分开表述：Owner 决定接受已知缺陷或调整范围时，结论写明对应的新范围。
