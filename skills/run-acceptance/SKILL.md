# Run Acceptance

用户调用本 Skill 即同意本轮总控与验收者 session 按本流程相互通信。

整包验收的角色分工：

- **总控 session**：守验收依据，分诊问题，派修复 worker 和独立 reviewer，串行集成到验收分支，最终收口。
- **验收者 session**：独占验收现场，按 journey 走真实路径取证，交结果包，复测集成后的修复。
- **修复 worker**：由总控派出的 subagent，一个不相交的问题域一个，各自独立 worktree。
- **独立 reviewer**：由总控派出的 subagent，审修复代码，也判验收证据是否 PASS。验收者交的结论都是候选，PASS 以 reviewer 回执为准。
- **Owner**：只裁决依据本身定不了的产品取舍和范围变更。

验收、修复、多个修复之间三者并行。确定本 session 的角色后读取对应参考：

- 总控 → [references/controller.md](references/controller.md)
- 验收者 → [references/verifier.md](references/verifier.md)

## 验收依据

- **合同内**：已批准的方案或合同（Decision、Spec、PRD、AC、journey 等）。每条要求都要验到，标准不因实现缺失而降低，也不因验收者的推断而增加。
- **合同外的既有能力**：固定一个基线版本（如部署分支的具体 SHA）。外围行为按基线判断"本来就有/本来就没有"，基线没有的能力记录下来，不扩展实现。
- **已批准且与合同一致的 journey**：它就是通过标准，结果包直接引用它的步骤编号。只为它没覆盖的合同要求补专项验证。执行用的脚本可以补测试路径，产品要求以合同为准；journey 与合同冲突时按合同修订 journey，批准材料之间互相冲突才交 Owner。
- **模糊或冲突**：总控先查合同原文和基线代码；仍然定不了，才把具体场景交 Owner。

## 所有权

- **验收现场**（运行中的服务、浏览器、验收数据库数据、临时配置）只由验收者写。总控和 worker 对现场只读，诊断结论以建议形式交给验收者执行。
- **验收分支**只由总控写，用 merge 或 cherry-pick 集成通过复核的修复。
- **共享文档**（journey、覆盖表）同一时刻一个维护者。另一方要改时先声明接手，改完交还。
- **修复 worker** 各用独立 worktree；需要可变运行资源（数据库等）时用隔离实例。

## 通信

事件驱动。过程日志留在证据目录，只在这些节点跨 session 发消息：

1. 结果包（验收者 → 总控）
2. 问题或阻塞（验收者 → 总控），注明是否影响其他旅程
3. 咨询：只读诊断、入口位置、测试数据准备方法（验收者 → 总控）
4. 依据或范围变化、复核回执（总控 → 验收者）
5. 集成窗口握手（双向）

### 结果包

引用不复述，例外才展开：

- **位置**：journey 步骤编号或覆盖表行，受验 HEAD
- **候选结论**：PASS / FAIL / BLOCKED / INCONCLUSIVE
- **证据位置**：文件或已有工具输出的精确定位，附本次断言需要的对象与版本标识
- **例外**（只在出现时写）：与 journey 的偏差（条件、数据、操作不同）、证据证明不了的部分、FAIL 时的实际与预期、现场是否保留

证据完整覆盖 journey 通过标准时，结果包就是位置、候选结论加证据位置一行。

### 集成窗口

1. 总控：说明哪些修复已过复核待集成，并按实际影响说明现场需要什么：不受影响、停写、停服重启，或含迁移。
2. 验收者走到安全点，按需执行：停服时只停自己启动的进程树并确认端口释放；有迁移时先备份并记录迁移状态。回复"可集成"。
3. 总控集成，回复新 HEAD、迁移文件与回退方式（如有）、复测入口，以及哪些既有结论受影响。
4. 验收者核对 HEAD，需要时重启并通过健康检查，从足以证明因果链的起点复测原失败场景。

多个已过复核的修复尽量合进同一个窗口。

## 证据

- **分层对应**：页面承诺用真实页面的视觉证据；写入、工具调用、权限和内部状态用接口、数据库或 trace 证据。结果相似、编号相同、HTTP 200、后台造出的数据，都只证明它们自己那一层。
- **证据配对**：按断言核对对象、适用身份或范围、版本或采集时点，以及原始工具调用定位。先确认这些条件再比较结果；文件名相同不代表请求相同，后来的状态不能倒推为先前的状态。
- **条件先成立**：对照前确认业务条件确实一致。条件不成立的样本标为无效并保留，不计入结果。
- **数据隔离**：无关场景用独立数据组，前面场景留下的状态不进入当前场景的命中路径；合同要求连续验证的场景（上一步产生、下一步复用）保留前序状态。
- **最小输出**：优先复用项目的只读、脱敏入口；查询或解析时先投影本次判定所需字段，再输出到工具结果或证据摘要，遵循项目的日志边界。其余大对象保留在原存储中。
- **只追加**：证据文件用唯一文件名，写入后不覆盖。原始证据放在不进 git 的目录，仓库里只放脱敏汇总。

## 收口

整包 PASS 需要同时满足：

- 覆盖表中每条合同要求都有结论和对应层级的证据；
- 已确认的缺陷都已修复、复核、集成并复测；
- 无效样本、证据缺口、范围调整、Owner 决策都有处置；
- 终审通过：Impl-Package 包走它的 terminal review，其他情况由独立 reviewer 审最终 diff；
- 临时配置恢复原样，自有进程清理，验收数据和证据保留。

"验收结束"和"验收通过"分开表述：Owner 决定接受已知缺陷或调整范围时，结论写明对应的新范围。
