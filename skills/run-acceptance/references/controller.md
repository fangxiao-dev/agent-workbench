# 总控

总控守依据、做裁决、调度修复和复核、串行集成。页面操作和现场写入归验收者，修复实现归 worker。

## 1. 锁定依据并启动验收者

- 启动、会话续接或上下文压缩后，先自行读取本 skill 的 [SKILL.md](../SKILL.md) 和本文件，再核对当前未关闭项。
- 锁定：合同位置、验收分支与 HEAD、外部基线 SHA、环境边界（可用的数据库、账号、外部服务，以及哪些操作需要 Owner 批准）。
- 将本轮用户补充约束纳入交接与委派 brief；约束变化时同步给受影响的执行者，按用户原意更新执行范围。
- 建覆盖表：每条合同要求 → journey 步骤或专项验证 → 证据层级 → 当前结果。已有 journey 覆盖的要求只填引用；表的重点是 journey 之外的要求（后台、权限、并发、回填、开关等）。
- 先找已有的验收搭档：核对双方会话标识、工作区、通信授权和进度位置，读取进度后接着推进。没有可用搭档且已获用户授权时，才用宿主的新会话工具启动验收者。启动或续接时要求验收者自行读取本 skill 的 `SKILL.md` 和 `references/verifier.md`；交接写明角色、skill 路径、工作区与 HEAD、依据与 journey 位置、环境边界与已获授权、咨询通道（本会话标识）、首批旅程顺序。交接只写验收者无法自己查到的信息。

完成标准：验收者已核对锚点，开始首个旅程或从进度处继续。

## 2. 分诊

收到问题报告先核实，再按类型处理：

| 判断 | 处理 |
|---|---|
| 违反明确合同 | 定义修复任务，派 worker |
| 符合合同 / 非问题 | 给出依据，验收者继续 |
| 样本、操作或环境前提不成立 | 修正前提后重验，样本标无效 |
| 证据不足 | 指定最小补证动作 |
| journey 要求超出合同 | 修订 journey 和覆盖表，实现不动 |
| 基线本来没有的能力 | 记录为合同外，实现不动 |
| 合同模糊或需要新增产品行为 | 交 Owner |

修复任务可以包含诊断：现象和合同边界清楚就能派，不必先查完根因。修复自身引入的回归归该修复任务处理。

交 Owner 时先讲场景和对使用者的影响，再给选项；选项之间要真的互斥。

## 3. 派修复

按 [dispatcher](../../dispatcher/SKILL.md) 派发、复用、消费 worker 并安排代码增量复核；本场景只补这几点：

- 一个可独立交付的问题域一个 worker；同一根因的多个表现归同一个 worker。
- brief 带上：复现步骤、预期、合同依据、证据路径，并写明验收现场只读。
- worker 上下文和 worktree 分开判断：沿用 worker 理解的同时，可以换一个干净的 worktree。
- 依赖真实数据库行为的修复，在隔离数据库实例上跑回归后再进集成。

代码增量复核通过后才进集成窗口。

## 4. 集成

按 SKILL.md 的集成窗口执行。解决冲突时改动了已复核的代码，就对改动部分补审。通知验收者时列出受影响需要重验的既有结论；未受影响的证据继续有效。

## 5. 判 PASS

先按 SKILL.md 的「证据」核对结果包的配对与前提。缺位置、候选结论或可定位证据时，只补该缺口；已有工具输出可以精确定位时，直接引用。

齐全后通过 [Dispatcher](../../dispatcher/SKILL.md#reviewer-executor) 选定独立 reviewer，给它 [reviewer 执行合同](../../reviewer/SKILL.md)及本次 brief：journey 步骤与通过标准、受验 HEAD、证据定位、偏差与边界、本轮补充约束。reviewer 直接执行审查，候选结论由总控采信。同一旅程的多个子场景可以合并成一次复核。

reviewer 回执（PASS、FAIL 或补证项）转给验收者记入索引。

## 6. 持续推进

每次被唤醒（新消息、worker 返回、用户询问）先核对所有在途项的实际状态：哪些 worker 还在运行，每个修复停在哪一步，验收者在等什么。已经停止但没完成的立即续派。每个未关闭项都要有负责人和下一动作。

向 Owner 汇报时先给结论，再按旅程列状态。

## 7. 收口

按 SKILL.md 的收口条件逐项核对，更新覆盖表的最终状态，通知验收者清理现场，并登记项目要求的 Gate 或验收记录。

同时按 Dispatcher 的生命周期清理已消费的临时 handoff。最终回报分别列明恢复、已清理、继续保留的资源及残留；仍有待处理项时说明其 owner 和下一动作。
