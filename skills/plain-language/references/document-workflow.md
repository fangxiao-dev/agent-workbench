# 文档 Plain Language 工作流

仅在处理已有文本、文件名或项目文档时读取。按“分析 → 用户确认 → apply → 验证”的顺序执行；确认是文档主路径中的检查点，不是独立模式。

## 1. 固定范围与原意

- 记录目标文本或绝对路径、目标读者、原文要解决的问题和用户明确排除的内容。
- 仓库文件同时记录分支、HEAD、worktree 状态、目标文件总数和与本次范围重叠的现有修改；保留用户已有改动。
- 扫描正文、标题和范围内的文件名。用户给出的已知问题只用于校准，不重复计入新候选。

完成条件：每个目标都能说明“写给谁、要表达什么、哪些内容不能改变”。

## 2. 识别需要改写的表达

先保留原文、大小写、连字符、中英文混排形式、文件和行号，再判断表达是否阻碍理解。需要判断自创术语、中文硬译、中英混搭、标题或文件名时，读取 [`plain-language-examples.md`](plain-language-examples.md)。

一个候选通常至少同时出现两个信号：

1. 多个抽象名词堆叠，却没有明确对象或动作。
2. 大小写、缩写或连字符制造了固定专名感，但没有稳定外部含义。
3. 读者无法判断它描述的对象、动作、责任边界或验收结果。
4. 使用普通中文、已有技术术语或“对象 + 动作 + 结果”可以完整表达。

将候选分为三类：

- **直接改写**：普通表达可以完整说清楚，且不会改变事实或合同。
- **保留 token 并说明**：专业 token 本身精确，改写它周围的主体、动作和边界。
- **需要决定**：改动会改变 scope、authority、验收条件、兼容承诺或 Gate；给出隐藏选择和影响范围。

常见技术术语、明确的产品/模块/字段/API/命令名、skill 名称和用户已认可的项目术语，不因长度或英文形式单独列为问题。

完成条件：每个候选都有原文证据、具体疑点、分类和不改变原意的改写方向。

## 3. 给出确认批次

默认每批最多 20 项。每项给出原文、位置、处理类型、具体疑点和建议表达；“需要决定”项改为具体问题，并说明不同选择影响什么。

```markdown
| # | 原文 | 位置 | 处理 | 疑点与建议表达 |
|---:|---|---|---|---|
| 1 | `...` | `path:line` | 直接改写 | ... |
```

同时用一两句话复述目标读者和原文意图，让用户能够先纠正理解，再确认当前批次。给出批次后暂停，保持目标文件不变；用户的批注优先于初稿。用户明确要求只检查时，以该批次作为交付结果结束。

完成条件：数量可对账，目标文件未改变，用户可以明确确认、否决或修正每项及整体原意。

## 4. Apply 当前确认批次

- 只处理用户确认的当前批次和批注，不顺手扩大扫描范围。
- 按语境逐处修改，避免全局替换破坏代码标识、历史引用或不同含义的同形词。
- 文件名只有在当前批次列出且用户确认时才重命名；同步检查目标范围和其他 tracked 文档中的入站链接、相对路径和旧文件名。
- 修订历史可以保留被取代的旧表达，但要明确它属于旧 revision，不能继续充当活动合同。

“需要决定”项只有在用户明确选择具体含义后才进入 apply。若选择改变合同，先识别拥有该合同的 Decision、Spec、ADR 或其他权威文档，使用仓库现有 requirement/spec 流程登记变化，再同步必要投影。其余已确认的普通语言项可以继续处理。

完成条件：diff 只包含当前确认批次；每项批注已落实；没有以语言修改掩盖合同变化。

## 5. 验证与报告

至少验证：

- 当前批次的活动文本残留为零；有意保留的 token 符合用户批注。
- 改写后的主体、动作、条件和结果能够准确复述原意。
- 合同项在活动权威文档中一致，旧结论只出现在清楚标注的历史记录中。
- 本地 Markdown 链接和重命名后的入站引用有效。
- diff 只包含确认范围；仓库要求的 revision binding、格式或文档检查通过。

报告当前批次处理量、已 apply 数量、未决数量和验证结果。区分“当前批次已 apply”“整个文档改写已收口”和“上层任务已收口”，只陈述证据支持的阶段。

完成条件：每项修改都有同一 revision 的直接验证证据，未决内容和剩余批次数量明确。
