# Plain Language

让目标读者第一次阅读就能理解结论、对象、动作、条件和结果，不必先破解临时术语或抽象名词组合。Plain language 的目标是降低理解成本，不是降低内容的专业性。

## Core

当前上下文第一次加载本 skill 时，完整读取 [`references/plain-language-examples.md`](references/plain-language-examples.md)。这些实例是 Core 的共享校准材料，用来把下面的原则落实到具体表达；当前上下文已经加载过时直接复用，不重复读取。

所有调用都遵守以下规则：

1. **保留原意**：保持事实、条件、例外、责任、置信程度和 `必须 / 可以 / 禁止` 等语义强度。
2. **写清关系**：优先写明谁或什么在什么条件下做什么，以及会产生什么结果；用具体对象和动作代替抽象名词堆叠。
3. **使用熟悉表达**：普通词可以完整表达时，使用普通词；标题式大小写、缩写、隐喻和自创术语应提供真实对象与动作。
4. **保留精确 token**：产品名、模块名、字段、API、命令、skill 名称以及 `session`、`identity` 等必要专业 token 可以保留，并在上下文中说明作用。
5. **暴露实质选择**：表达背后固定了 scope、authority、验收条件、兼容承诺或 Gate 时，指出需要决定的内容及影响；语言改写不代替 Owner 作决定。

Plain language 不以字数最少、全部翻译成中文或删除技术细节为标准。完成判断是：目标读者不需要猜测术语含义，就能准确复述结论与下一步。

## Router

按处理对象选择一条路径：

- **会话类**：目标是当前回答或对话中的一段表达。
- **文档类**：目标是已有文本、文档、文件名或一组仓库文件。

用户同时给出多个目标时，以明确要求修改或解释的对象为主；其余内容只作为上下文。不要把 first shot、重述、检查或回写扩张成新的 Router。

## 会话类

1. 确定用户当前要理解、判断或执行的事项。
2. 新问题直接按 Core 组织第一次回答；用户指出上一段不清楚时，用新的表达重述同一结论。
3. 先给能够独立阅读的结论，再补充当前决定所需的依据。
4. 重述时保留原有条件、例外和不确定性；确需增加新信息时，将“重述”和“补充”明确分开。
5. 交付答案本身，不输出术语扫描表，也不讲解本 skill 的内部流程。

完成条件：回答能够一次读懂，且没有为了易读而改变原意或技术边界。

## 文档类

处理已有文本、文件或项目文档时，完整读取 [`references/document-workflow.md`](references/document-workflow.md) 并按其中顺序执行。会话类不读取这份文档修改指导。

文档路径固定为：分析目标、读者、原意和改写范围 → 向用户给出当前批次并等待确认 → apply 当前确认批次 → 验证并报告。用户明确要求只检查时，在给出分析结果后结束。

完成条件：确认前目标文件保持不变；确认后的 diff 只包含当前批次；改写后的活动文本更容易理解，且事实、合同含义、链接和必要专业 token 保持一致。

## 输出边界

- 会话类交付清楚的回答或重述。
- 文档类在确认前交付可核对的改写批次，在确认后交付实际修改与验证结果。
- 未决合同项交付具体决策问题和影响范围；已有明确 Owner 决定时，按该决定改写拥有合同的权威文本及其必要投影。
