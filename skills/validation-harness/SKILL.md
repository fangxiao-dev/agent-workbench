# Validation Harness

让一次端到端验证可以**从零重放**：同一条命令建出准备状态，每次运行拿到自己的业务条件和新对象，起点与过程都留有证据。本 skill 定义这些性质并教怎么审计；具体命令、账号和数据由项目自己的 QA 入口提供。

典型失败：验收重开一张发票，把它当成"刚收到建议"的中间态，实际后续步骤早已改过它。合成文件、截图、DB 证据都在，却没有办法重建每一步的起点状态。

## 七个性质

每条给出目标形态和一句自检。

1. **声明式准备**：一条幂等命令从零建出准备状态（角色账号、权限、种子账套与主数据），重复执行结果相同。自检：换一台干净环境，只跑这条命令，能不能走到第 1 步？
2. **运行隔离**：每次运行有自己的业务条件或命名空间（唯一票号、供应商、业务键、前缀），运行之间不共享可变对象。自检：两次运行并行，会不会读到彼此的数据？
3. **前置检查**：第 1 步之前断言前置条件（例如这个业务键下没有历史记忆、账号权限到位），输出随运行保存。自检：前置不成立时，是在第 1 步前报错，还是走到一半才发现？
4. **新鲜对象**：每一步操作本次运行里创建的对象。要回到某个起点，就重新走到那一步创建一个，不去重开后续步骤改过的对象。自检：本步输入对象的 ID 是否只出现在本次运行？
5. **清理边界**：写明运行后拆掉什么（临时账号、会话、测试租户数据）、留下什么（证据与产出记录）。自检：清理后证据还在、环境可再次准备吗？
6. **可观测**：trace、截图、只读的 inspector/DB/API 回读按 run id 保存在项目或 package 内，不放系统 Temp。自检：事后能否只凭 run id 还原每步看到的东西？
7. **归属分工**：项目的 QA skill 或脚本提供具体命令、账号、数据；本 skill 只管性质与审计。项目没有入口时，先按下面的流程补最小的一份。

## 流程

1. **盘点入口**：找项目已有的环境启动、种子、测试身份、登录、DB/导出查看方式，对照七个性质标出缺口。
2. **最小补齐**：复用现有登录和 fixture，只建第一条窄路径需要的部分；后续路径随用随补。
3. **双跑验证重放**：用不同 run id 连续跑两次，确认两次互不影响、前置检查都通过、证据各自完整。
4. **交付命令**：把 setup / precheck / cleanup 命令和隔离方式记给调用方。impl-package 的 plan 里对应 `Harness setup`、`Harness precheck`、`Harness cleanup`、`Harness isolation` 四行；独立使用时写进项目的 QA 说明。

## 审计输出

按七个性质逐条给出：满足 / 缺口 / 建议的最小补法，并附证据（命令输出或文件路径）。缺口排序以"是否让下次运行得到不同起点"为先。
