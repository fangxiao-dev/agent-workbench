# Challenge The Core

**承重假设**是以陈述句出现、从未被论证过的选择：换掉它，已完成和计划中的工作要**全部重做**。

本 skill 只做一件事：把承重假设还原成选择，摆出真正不同的替代品，然后停。

## 校准：什么算、什么不算

**开始扫描前先读完本节。** 判据一句话说得清，实际扫描时却极易失准——技术选型和执行偏好会被误判成承重假设，而最隐蔽的 B 类会被整个漏掉。实测：不带校准时抓不到关键假设，补上之后才抓到。

### 这些不是承重假设

- 「用 Postgres 而不是 MySQL」——若已被论证过，它是已作出的选择。本 skill 只翻**从未被表述为选择**的东西。
- 「按钮放左边」——换掉它只需局部调整，blast radius 不够。
- 「先写测试再写实现」——除非它决定了整个承载结构，否则属于执行偏好。

判据始终只有一条：**换掉它，是不是全部重做。**

## 边界

靠排除定义，三条都是硬边界：

- **不深化。** 追问某个选择的各个方面、把模糊概念想透，是 `/impl-package:grilling` 的职责。这里问的是「为什么是 X 而不是 Y」，不是「X 的第三步怎么办」。
- **不裁决。** 选哪个、为什么、记在哪里，由 owner 承担。
- **不拆解。** 线数、任务拆分、集成节奏都是下游的事。

一句话：**它不让人想得更深，它让人看见自己本来没在选的地方其实在选。**

### 何时不用

纯修复、证据订正、局部可逆调整没有承重假设可翻——直接说明并退出，不要为了凑数把执行偏好包装成承重假设。

## 步骤

材料由 owner 提供，不要自己去找、也不要要求补齐。就着手上的东西做，缺什么在最后说明。

### 1. 抓承重假设

承重假设藏在两处，都要扫。

**A · 事情被描述的方式。** 在材料里找**以陈述句出现、通篇没有被论证过**的组织性选择。典型形态是「帮我按 X 把 Y 做了」里的那个 X，或一份文档从标题起就把 X 当作既定事实。**只找这一类词，不要顺着材料的逻辑往下走**——写成文字之后假设已被固化，顺着读只会读到它的自洽性。

**B · 已写下的约束的合取。** 有一类承重假设不在任何人的表述里：每条约束单看都正确、也确实该写，但**加起来把某个量锁死了**。没有任何一句话可以指认它，只能用一个动作逼出来——把散落在各处的「唯一 / 独占 / 单写 / 必须经过 / forward-only / 串行 / 共享同一个」条款全部拉到一起，然后问：

> **这组约束加起来，把什么锁成了 1？**

再问实际要的是几。两个数对不上，那就是一个已经生效的承重假设。

对每个候选套承重判据：**如果它是错的，什么会全部重做？** 答得出「全部重做」的才是承重假设；答「局部调整」的丢掉。

**完成标准：** 产出 1–3 个承重假设，每个都写明它一旦为假会连带作废什么。抓出五个以上说明判据用松了——那是 `/impl-package:grilling` 的粒度，回到「校准」节重筛。

### 2. 为每个承重假设摆替代品

每个承重假设配 3–4 个**根本不同**的替代方案。三条硬约束，任一不满足就重新生成，不要在原方案上打补丁：

- **单句概括测试** —— 若所有候选能被同一句话概括，它们就不是候选，是同一个方案的变体。
- **至少一个直接违反原假设** —— 桌上必须有「不按 owner 说的做」那一项。这是强制跳出框架的机制，不可省略。
- **每个候选写出「它成立的前提」** —— 本 skill 的支点。owner 不需要记得检查前提，读表时会自己撞见「A 的前提是底座已存在」，然后想起这次任务就是换底座。

### 3. 具体到能被想象

抽象描述无法判断，具体形态才行。每个候选补齐：第一周实际做什么、第一次汇合/验证在什么时候、三周后长什么样。

**完成标准：** 每个候选都能让 owner 在脑中放一遍，而不是只看到一个名词。

### 4. 中立呈现，然后停

**不给推荐，不排序，不暗示倾向。** 这条反直觉，必须守住：owner 的价值在于「一眼看出哪个契合」，而这个判断一旦被推荐锚定就失效了。设计师摆三稿时不会说「我建议第二个」。

owner 表态**之后**才可以应邀补充意见。表态之前，只呈现事实与前提。

呈现格式：一个承重假设一张表，行是候选，列是 `候选 / 成立前提 / 第一波 / 第一次汇合 / 完成后`。全部一次给出，等一次批量回复。

## 输出

owner 的选择 + 被否候选及原因，交回 owner。本 skill 不写任何持久文档。

## 必读案例

## 案例：各自正确的约束，但漏了关键路径

**任务表述：** 「帮我把这个 Lark → Supabase 迁移按纵切一条条切好。」

这个任务里有两个承重假设，一个写在表述里，一个谁都没说过。

**写在表述里的：`按纵切`。** 以陈述句进入，任务包文档从标题起就把它当既定事实，全文没有一处论证过为什么按业务域切。

**谁都没说过的：单通道不会成为关键路径。** 它由三处各自正确的条款合取而成：

| 出处 | 原话 | 单看对不对 |
| --- | --- | --- |
| 决策 | Test 资源由迁移环境**独占**，理由写着**保持单写 authority** | 对，环境隔离必需 |
| 规格 | 最终编号与共享 Test apply 由**父包单写管理**；证据链 **forward-only**，本地跑通不算数 | 对，防分叉防假绿 |
| 计划 | 四条纵切并行 | 对，分工合理 |

把前两行拉到一起问「**锁成了 1？**」——同时能推进 schema 的线数 = **1**。再问计划要几 = **4**。

**判据核验：** 换掉它，四个任务包、三百多个提交的组织结构全部作废 → 承重。

**摆出替代品后会是：**

| 候选 | 成立前提 | 第一周 | 第一次汇合 | 三周后 |
| --- | --- | --- | --- | --- |
| A 中央父包单写基础，四包交付纵切 | **中央通道能及时供给 seam，串行 promotion 成本可控** | 四线各自开 draft | 父包统一集成 | 单一 canonical history |
| B 基础升格为同级包，另设轻量发布包 | 基础、业务迁移、发布的生命周期彼此独立 | 抽离基础与切换所有权 | 基础 gate 被四包共同消费 | 各自拥有清晰终点 |
| C 各业务包拥有本域 schema 与 migration ownership，中央只管兼容与版本清单 | 领域边界稳定，跨域兼容可自动验证 | 明确每域 migration 归属 | 用兼容合同汇合，不进共享单队列 | 各域独立可验证 |
| D 取消固定域拆分，改按风险波次组织 | 读路径、事务写路径、外部副作用的验证差异大于领域差异 | 把工作映射到三类风险波 | 第一波完成后再启动下一波 | 每波自带组合证据 |

owner 读到候选 A 的成立前提那一格，会立刻认出它正是后来被违反的那一条。

**实际结果：** 假设未被检验，四条线并行六周，96% 的产出从未汇合，72% 的阻塞是在等流程而非等技术能力。

**要点：** 这类假设**没有出处可引**——它不在任何一句话里，谁也无法被指责写错了什么。只能靠把「唯一 / 独占 / 单写 / forward-only」这类词全部拉到一起，它最容易漏，也最值钱。

- 「按钮放左边」——换掉它只需局部调整，blast radius 不够。

判据始终只有一条：**换掉它，是不是全部重做。**
