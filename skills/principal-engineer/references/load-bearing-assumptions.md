# 承重假设

**承重假设**是以陈述句出现、从未被论证过的选择：换掉它，已完成和计划中的工作要**全部重做**。

判据只有一条：**换掉它，是不是全部重做。** 已被论证过的技术选型、换掉只需局部调整的（按钮位置）、执行偏好（先写测试）都不算。

## 去哪找

**A · 事情被描述的方式。** 「按 X 做 Y」里的 X，或一份文档从标题起就当作既定事实的组织性选择。只找这类表述，不顺着材料的逻辑往下读——顺着读只会读到它的自洽性。

**B · 已写下的约束的合取。** 每条约束单看都对，加起来却把某个量锁死。把散落的「唯一 / 独占 / 单写 / 必须经过 / forward-only / 串行 / 共享同一个」条款拉到一起，问：**这组约束加起来，把什么锁成了 1？** 再问实际要的是几；对不上，就是一个已经生效的承重假设。B 类没有出处可引，最容易漏。

通常 1–3 个；找出五个以上说明判据用松了，那是 `grilling` 的粒度。

## 找到之后

给出 2–3 个根本不同的替代方案（不能被同一句话概括，至少一个直接违反原假设），每个写清它成立的前提——Owner 往往读到前提就认出哪条不成立。形式不限，按问题挑最清楚的写法；然后回到主流程给判断。

## 例子

「帮我把 Lark → Supabase 迁移按纵切四条线并行。」表述里的 `按纵切` 从未被论证；另外，决策里「Test 环境独占、单写」加规格里「父包单写、forward-only」，合起来能同时推进 schema 的线数是 1，计划却要 4。替代方案如：中央单写基础 + 四包交付（前提：中央通道供给跟得上）、各域自管 migration 只靠兼容合同汇合、改按风险波次组织。实际未检验，四线并行六周大部分产出从未汇合。
