# Engineering Probe

把影响范围、架构或技术责任的未验证假设，变成成本相称、能区分结论的小实验，把证据交还决策方。面向技术人员：一条查询、一组模拟请求、一个故障注入脚本、一条关键链路的 Spike。

## 值不值得做

三条同时成立才考虑：

1. 有一个会影响系统范围、架构或技术责任的未知量；
2. 不同的观察结果会导向不同决策；
3. 找得到成本与决策风险相称的验证办法。

「现有数据库在目标订单量下够不够」值得；「新框架是不是更优雅」没有决策标准，不值得。已有日志、监控、执行计划或可信数据够判断，就直接用，不造实验。不是每个需求的前置关卡。

## 分界

- 查资料、官方事实 → `research`
- 已经坏了或变慢了，要诊断 → `diagnosing-bugs`
- 可重放的验收环境、种子数据 → `validation-harness`
- UI 或状态模型的一次性原型 → `prototype`；面向业务方的演示 → `business-alignment`

本 skill 只做「为了一个待决策取舍而取技术证据」。负载目标、可接受等待、业务后果这类前提缺失时，退回 `principal-engineer` / `business-alignment` 确认，不自己编。

## 怎么做

1. **改写成能被证据区分的假设**，并写出两种结果各导向什么选择。例：在预期并发和目标延迟下，现有执行方式能完成吗？能 → 暂不加队列；不能 → 定位瓶颈再评估。先查 `docs/principal/`（只读）有没有可用证据。
2. **选最便宜且区分力够的手段**，从现有信息起逐级加码，不是固定步骤：看已有日志、指标、代码、配置 → 隔离环境小规模测量或复现 → 脚本模拟负载、超时、重试、乱序、资源不足 → 只覆盖关键链路的 Spike → 必要时提高真实性。一条执行计划能解决的，不先搭压测。
3. **先想哪些因素会改变结论**：数据分布、外部 API 限流、并发形态、状态共享、故障恢复、重试语义、资源限制。无法复现生产条件时，说明哪些观察仍有效、哪些只是趋势。mock 响应测出的吞吐不是端到端容量。
4. **跑最小实验，够区分就停。** 没有区分力再决定是否补一轮；不为完整 benchmark 报告扩范围。

默认在隔离环境操作，脚本可丢弃、可复现。碰共享环境（Staging、线上）、产生真实费用或修改外部状态之前，先取得 Owner 同意；只读查看不受限。

## 输出

短报告，每项一两句：

```text
待决策问题
实验前假设与改变决策的阈值
环境与真实性边界（必填：哪些条件与生产不同，结论因此只在什么范围内成立）
方法（如何复现）
关键观察
能支持的结论
仍需判断的条件
```

关键数字、环境和真实性边界直接写进结论，不依赖临时脚本仍然存在，也不把决策指向脚本。没得出有效结论就说明原因，不硬给推荐。结论要能直接用于「现在做 / 延后做 / 改 scope」。

## 记忆

本 skill 不写 `docs/principal/`，临时脚本也不进记忆。结果交给调用方；是否收录由 `principal-engineer` 决定。被其他 skill 直接调用时，结果留在调用方产物里。

只有反复证明有用的实验才考虑沉淀成回归测试或长期设施。不预先建统一的混沌工程或压测平台。
