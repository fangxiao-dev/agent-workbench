THThread Harness
角色 控制流 四条硬规则 沟通渠道 脚本与账本 边界
A visual field guide for long-running multi-thread work

让系统卡住时，会叫人。

Thread Harness 是一套给“一个主控 thread + 多条子 thread 长时间并行”使用的控制流约定。它关注的不是怎么把线程开出来，而是：谁负责推进整体、谁负责生产共享 seam、何时上报、何时派活、何时叫醒 Owner。

1 Controller + N Children Append-only Ledger Fail-closed Stall Detection 当前 wait_threads 上限：8 个 child

核心心智模型

把“工作是否真的推进”从模型的短期记忆里拿出来：Git HEAD、rollout、registry 是地面真相；子线无法被外部观察的状态，必须通过回报写入账本。

最终目标：减少“大家都在等，但没有人负责造那个中间产物”的静默死锁。

先看全景：谁和谁发生什么关系？

Owner 负责授权和 Owner 级决策；Controller 负责让整体推进；Package Child 完成明确任务包；Foundation Child 专门生产跨线共享的 seam。artifact 沿 seam 流向消费者，状态和异常沿回报通道回到 Controller。

Owner 决策与授权 主控控制流 任务分派与观察 共享 seam 与交付

四个关键角色

严格说，skill 定义的是三个 thread 角色；Owner 是系统外的决策者，但没有 Owner 的授权与决策，上面的控制流就不完整。

SYSTEM OWNER

Owner · 决策者

知道业务目标、结束判据和不可越过的边界。

  • 开主控并写 goal
  • 亲手授权是否允许创建子任务
  • 处理 Owner 级 pending decision
  • 确认 effort 档位，盯首个停滞信号
不能被 broker 自行替代
ROLE C

Controller · 主控

系统的推进责任人，不直接写业务代码。

  • 维护路由，轮询全部 children
  • 读取账本，判断 idle / changed / stall
  • 缺 seam 就派 Foundation 线
  • 三轮无 committed progress 必须行动或升级
负责“整体有没有前进”
ROLE A

Package Child · 任务包子线

负责一个明确任务包，开发方式由其他执行 skill 定义。

  • 按自己的任务包推进实现
  • HEAD 变化、转 waiting、Owner 阻塞时主动回报
  • 只把共享 seam 问题上报给主控
  • 等上游时必须引用 seam:id
产出业务任务包
ROLE B

Foundation Child · 基座子线

没有自己的任务包，专门生产被多条线依赖的共享 seam。

  • 由主控指派 seam 和交付物
  • “保持待命”是非法指令
  • 空闲时要下一个 seam，或报告交付
  • 交付时登记 producer、consumers、artifact
生产共享契约 / artifact
最容易搞反的一点：“大家都在等跨域契约”不是外部阻塞，而是主控尚未安排生产者。Controller 手里有 create_thread，可以派一条 Foundation 线去造它——当然，前提是 Owner 已明确授权。

执行层辅助：$call-grok 在哪里参与？

call-grok 参与的是实现与调查过程，不是 Harness 的调度闭环。它通常由 Package Child 或 Foundation Child 调用，作为独立 CLI 进程只返回结论；子线仍然负责把结论落到自己的任务、commit、seam 登记和 H1/H2 回报上。

impl / investigate优先用 call-grok，回收结论，减少主线被实现过程占满上下文。
review不走 call-grok，走 $do-review 的既有 review tracks。
acceptance不外包，由当前 session 自己验收，避免判断失真。
边界：call-grok 不是 registry child，不参与 wait_threads 轮询，也不负责账本、停滞判断或 Owner 决策；它只缩短“做实现/调查”这段过程。

主控每一轮怎么跑？

这是一条固定控制回路。最重要的是顺序：先拿到当前 session id，再用固定 poll 片段观察，随后由磁盘脚本判断，最后才做派活或升级。

01 · ROUTE

读 Registry

获取全部 child 的 current_session_id。不凭记忆使用旧 ID，避免子线换 session 后每轮失效。

02 · POLL

固定 wait

对全部 children 调 wait_threads，至少等待 180 秒，并打印固定、有界的 projection。

03 · SYNC

同步地面真相

ledger.py sync 从主控 rollout 读 projection，从 registry worktree 读 Git HEAD，合成紧凑摘要。

04 · CHECK

判定停滞

stall-check 检查 pending decision 和连续无 committed progress 的轮数。

05 · ROUTE

派活或升级

闲线派任务；有 Owner 决策立即上报；三轮无推进只能 dispatch 或 escalate。

inactiveStatus → idle_nodes有线程闲着，是“该派活”的信号，不是“没有变化”。
MUST_ESCALATEdecisions.jsonl 有 pending，立即叫醒 Owner，本轮结束。
ROUND INVALID / SYNC STALE本轮数据无效或 rollout 未就绪；修复/重跑，不能静默复用旧数据。

四条硬规则：系统的护栏

其余内容是建议和工作方法，真正必须守住的是 H1–H4。每一条都对应一次真实的失效模式。

H1 · REPORT

触发就回报

HEAD 变了、状态从 working 转 waiting、出现 Owner 级阻塞，任一发生都要写账本并给主控发消息。不要等主控来问。

H2 · LEDGER

状态变更即追加

进度不能只留在上下文里，因为 compaction 会清掉它。JSONL 账本只追加新事实，不改写旧行。

H3 · STALL

三轮无提交，二选一

连续 3 轮所有 node 的 Git HEAD 无变化：必须派新工作，或向 Owner 报告并结束 loop。禁止“继续等待”。

H4 · SEAM

等待必须有生产者

任何 awaiting_seam 都要写 seam:id，且 seam 必须登记 producer。等一个没人负责造的东西，是错误状态。

H3 的精确含义：没有 committed progress，不等于所有线程都停止。即使某条线正在工作但尚未 commit，主控仍要给其他空闲线派活，或上报 Owner。

沟通渠道：消息、观察、路由、账本各司其职

Thread Harness 不把所有信息都塞进消息里。消息是即时沟通，registry 是“谁对应哪个 session”，ledger 是可恢复的事实账本，Git/rollout 是不依赖模型自述的观察源。

渠道 / 载体方向用途关键边界
create_threadController → Child创建任务包线或 Foundation 线，派出新的工作单元。不是主控自授权动作；Owner 必须在 goal 或对话中明确授权。
wait_threadsController → 全部 children按固定 poll contract 等待首个可行动变化，并拿回有限投影。当前单次最多 8 个 target；不包含 Controller 自己。
send_message_to_threadChild ↔ ControllerH1 触发时主动回报；主控也用它传达派活、决策和边界。主动回报不能只依赖主控拉取，因为拉取机制不可靠。
read_threadController → 指定 child当 500 字符摘要不够时，按需读取某条线全文。默认 poll 有界，避免把所有长文本灌进主控上下文。
Registry JSONController / broker 维护绑定稳定 node_id、当前 session、topic、worktree、branch。它是路由元数据，不是审批账本、密钥仓库或实现证据仓库。
Git HEADsync 读取判断是否有真实的代码提交推进。不能用 Desktop turn id 代替；turn 变化不等于工作产出。
rollout JSONLsync 读取读取主控刚打印的 poll projection，并统计派发调用痕迹。“没打印的东西”不在 rollout 里；脚本必须打印固定 projection。

脚本与账本：一个负责路由，一个负责控制流

可以把整个体系看成两层：owner-thread-broker 解决“谁是谁、消息发到哪里、授权边界是什么”；ledger.py 解决“现在发生了什么、是否停滞、下一步必须做什么”。

组件 / 命令它负责什么在整体控制流中的位置
owner-thread-broker维护 coordination group 的 registry；处理 session handoff、worktree/branch 路由和 Owner 授权边界。先于消息发送定位当前 session；不把审批混进路由文件。
ledger.py init创建运行时目录和空账本。协调组启动时执行。
$call-grok作为独立 CLI 辅助实现或调查，只回收结论，不承接协调责任。由 Package / Foundation Child 在执行层按需调用；不进入 registry、poll 或 ledger。
ledger.py sync读取 rollout projection，校验 poll 契约；读取 registry worktree 的 Git HEAD；合并 progress 并输出摘要。每轮 poll 之后的事实同步层。
ledger.py report子线主动写入自己的 state、waiting_on、note。H1/H2 的子线回报入口。
ledger.py seam登记 seam 的 producer、consumers、交付 artifact。让“等待什么”与“谁生产”形成可追踪关系。
ledger.py decide提出或回答 Owner 级决策。pending 时阻断普通轮询，优先上报。
ledger.py stall-check根据 pending decision 和 stall streak 给出退出码。0 正常、2 必须行动、3 必须升级。
ledger.py act把 H3 二选一的实际选择记下来：dispatch 或 escalate。防止主控口头上说“有动作”，账本却没有证据。
ledger.py status只读账本和 registry，恢复最新 state、seam、decision、stall 状态。主控换 session 接手时的恢复入口。
selftest.py用隔离 fixture 回归验证 sync 自检、状态合并、停滞和退出码优先级。脚本修改后的安全网，不触碰生产运行时。
progress.jsonl

进度事实

Git HEAD / turn / status 来自 poll；state / waiting_on / last_report 来自 child report。两类事实合成当前状态，不能互相覆盖。

seams.jsonl

共享产物归属

记录 seam 的生产者、消费者、assigned/delivered 状态和 artifact 指针。没有 producer 的 seam 就没有真正的等待闭环。

decisions.jsonl

Owner 决策队列

记录谁提出了什么 Owner 级问题、阻塞哪些 node、当前是否 pending。pending 会优先触发升级。

acts.jsonl + sync-state.json

动作与运行游标

acts.jsonl 记录 MUST_ACT 后选择了 dispatch 还是 escalate；sync-state.json 保存 offset、序号、停滞和 dispatch 计数。

地面真相优先

能从 Git、rollout、registry 直接读到的事实，不依赖模型主动报告：真实推进看 Git HEAD，派发痕迹看 rollout，轮询覆盖看实际 ids 集合。

模型只补充不可观察状态

子线是否在等待哪个 seam，外部无法直接知道，所以由子线通过 H1/H2 report 写入；主控用 never_reported、stale_reports 识别漏报或过期报告。

它解决的失败模式是什么？

!

主控把自己当成“只调度、不负责产出的人”，于是缺失的共享契约被误判成外部阻塞。

!

子线把等待状态留在上下文里，compaction 后没人知道它为什么停着。

!

把 inactiveStatus 当成“没有变化”，错过了“这条线闲了，该派活”的信号。

!

用 turn id 代替 Git HEAD，导致“只产生对话、不产生提交”也被算成进展。

Before · 静默死锁

多条线等待一个没有 owner 的 seam → Foundation 线被要求待命 → 主控继续轮询 → 没有明确的停滞上限 → Owner 很久都收不到需要决策的消息。

After · 显式控制回路

等待必须绑定 seam:id 和 producer；闲线进入 idle_nodes；三轮没有 committed progress 就触发 MUST_ACT；pending decision 立即变成 MUST_ESCALATE。

当前边界：它不是魔法

子线 ≤ 8

当前 poll contract 依赖单次 wait_threads 最多 8 个 target。超过 8 条线的分片与跨片合并尚未纳入本设计。

子线没有持久 goal

create_thread 只能给初始 prompt，不能为子线设置持久 goal。因此 H1/H2 仍依赖子线回报，主控要观察漏报。

防退化，不防恶意伪造

projection 自检主要防长跑压力下逐步简化；rollout 不能完全证明模型实际传给工具的参数，主动 decoy 仍是结构性限制。

H4 分阶段

第一阶段先登记并暴露无主 seam 数量；更严格的 producer 校验属于后续阶段，schema 先一次写全。

docs 不等于 code progress

dispatch 计数只在 code 级 HEAD 推进后清零，避免“提交一份阻塞说明文档”伪装成真正交付。

Owner 仍不可缺席

系统可以把需要人的时刻变得响亮，但不能替 Owner 做不可逆的授权、所有权和外部影响决策。
