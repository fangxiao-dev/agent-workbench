# req-discover：正式需求对齐之前的探索

日期：2026-10-27
设计依据：Owner 已确认独立需求探索 Skill 与 req-align 按需衔接的方案，并指定名称为 `req-discover`。实现与验证结果以交付报告为准。

## 背景：有材料归档位置，还需要探索方法

现有 req-align 将需求收敛为 Decision 和 Spec：前者说明为什么做、选择什么方向，后者定义系统行为及共享合同。它已允许引用 `investigations/<topic>.md`，并规定正式文档必须自足，调查材料默认没有合同权威。

Owner 会把正式对齐之前的调研材料放入 investigations，但此前没有专门设计“怎样理解这些材料、发现缺口、决定下一步查什么”的方法。直接起草容易将候选想法写成确定承诺，或为了形成完整方案过早猜测；持续调查而没有目标，又容易无限展开。

Matt Pocock 的 [wayfinder](https://github.com/mattpocock/skills/blob/59db609eb1e18aaf59b63284d0e52255aff0c63c/skills/engineering/wayfinder/SKILL.md)提供了启示：先明确探索终点，把当前能提出的问题与尚未看清的区域分开，随着事实和决策逐步展开地图。这里吸收的是探索方法，而非它的 Issue 管理和调度体系。本 Skill 是本地自建能力，不复制上游正文。

## 为什么独立成 Skill

探索可以在尚无任务包、尚未选择产品方向时单独进行，也可能跨多个会话。它的交付是有依据的认识，而非正式合同。独立入口允许用户说“先看这些材料，把问题研究清楚”，无需同时进入 Decision/Spec 流程。

req-align 继续作为正式对齐入口，内部 Decision/Spec 分工保持原样。材料混杂、目标不清、关键事实冲突或缺乏方向比较依据时，才调用 req-discover；信息充分时直接走现有流程。单个明确事实问题由 research 处理，不必启动整轮探索。

## 能力边界

| 能力 | 拥有的职责 | 结果 |
| --- | --- | --- |
| req-discover | 理解材料、选择值得探索的问题、综合证据和选项 | 当前认识、关键未知及下一项决策的依据 |
| research | 回答有边界的事实问题 | 可追溯的事实与证据缺口 |
| grilling | 与用户澄清重要取舍 | 用户确认的选择，或仍需用户回答的问题 |
| prototype | 用可回收样例帮助判断具体行为或形状 | 原型与反馈；不证明生产系统已经具备能力 |
| Dispatcher | 必要时安排调查与原型工作 | 有边界的委派及可核对返回 |
| req-align | 吸收已接受的结论，形成或修订 Decision/Spec | 自足的正式方向和行为合同 |

req-discover 允许用户直接调用和模型按需调用。它不拥有任务包、实施状态或 Gate；进入正式对齐后，原有合同检查继续生效。已有 Decision/Spec 是当前承诺，探索只能提出变更建议，不能用新材料静默覆盖。

## 探索怎么推进

先确定本次需要弄清的目标和已有范围，再理解材料中的事实、已确认承诺、约束、候选方案、未知和冲突。材料多时先建立全貌，再深读会改变判断的部分；这些分类是思考工具，不要求每份文件填写表格。

优先解决会改变方向、可行性或重要边界的问题。事实可查就调查，存在真实取舍就与 Owner 讨论，需要具体反馈才制作获授权的原型。已能准确描述但等待前置答案的问题保持可见；尚不能准确描述的区域暂时保留粗略认识。新答案出现后重新检查相关问题，不把所有未知一次性拆成任务。

达到当前目标所需的事实已经足够、可行方向能够比较时，可以把真实取舍交给用户或 req-align。关键事实仍缺失时如实报告缺口及其影响。任何时候都不能把“可以讨论方向”误报为“Spec 已满足实施条件”。当前目标外的未来问题与局部实现选择不要求提前穷尽。

## 产物与恢复

短探索在会话中交付。用户要求留档、明确在 investigations 中持续探索，或需要跨会话恢复时，按项目文档约定维护一份主题探索摘要，链接原始材料；保留输入文件，沿用已有主题摘要，避免并列多份当前认识。

摘要说明目标、可靠事实与来源、候选方向及理由、当前未知与冲突、下一步。仅在恢复有价值时记录尚未看清和明确排除的范围。结构随材料调整，不增加状态机、统计、认领协议或固定模板。

续接时先读摘要，再核对影响当前问题的来源是否仍有效。正式结论由 Decision/Spec 自足吸收，探索摘要保留依据而不成为第二份产品合同。目录不唯一时澄清位置；缺少归档约定时先在会话中交付，仅在实际需要留档时确定目的地。

## 接入、验证与后续优化

首版主流程位于 [req-discover](../../skills/req-discover/SKILL.md)；[req-align](../../plugin-marketplace/plugins/impl-package/skills/req-align/SKILL.md)仅增加正式主路径前的条件调用。已进入正式阶段后发现缺口，沿用原有未知项和 Gate 处理，不用探索入口绕过既有约束。通过宿主发现独立 Skill；源码仓库提供定位链接，插件缓存不假设跨目录链接仍存在。

验证关注：混杂材料不会提前变成合同；成熟需求跳过探索；明确问题直接 research；重要 SaaS 未知不被猜测补齐；局部阻塞不阻止独立调查；跨会话摘要可恢复；原型和外部副作用遵循已有授权。静态检查只证明结构与引用正确，行为通过有限场景演练验证，两类证据分别报告。

后续把本 Skill、req-align 调用点和项目 investigations 的实际使用作为一个整体优化。观察它是否减少无依据的起草、遗漏和无效调查，而不以文档数量或问题数量衡量效果。它不改变此前综合优化提案中其他项目的批准或实施状态。
