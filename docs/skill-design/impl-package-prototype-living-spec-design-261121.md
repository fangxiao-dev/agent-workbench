# 原型作为活 spec：讨论记录

日期：2026-11-21　状态：讨论稿（Owner 同意方向，未实施）
来源：KaiSpan 员工助手收尾包（final sweep）结束前的复盘讨论，Owner 与主控会话。

本文记录这个想法从哪里来、为什么要做、讨论中否决了什么、还有哪些风险。实现草案放在文末，只作参考。

---

## 1. 需求从哪里来：这一包踩过的坑

员工助手收尾包从原型出发，一直做到终审和验收，过程中反复出现同一类成本。

### 1.1 原型变成了一次性草稿

当时的做法分三步：

1. 记录正确的做法，以及它跟原型有什么区别；
2. 裁决按新规则做，还是按原型做；
3. 裁决后直接实现正式页面。

结果是原型从头到尾都只是草稿。做完这一版就过期，下次再加功能，又得重新做原型，或者干脆不看原型。

### 1.2 名义上对齐，其实没有对齐

- 很多页面是有了需求之后才新建的，原型里根本没有。
- 有的页面是按 UI 需要加出来的，和原型的结构对不上。
- 所谓“功能对齐”，指的是能力清单对上了。UI、文案、交互都没有对齐。

### 1.3 人工验证全部推到了最后

想确认“业务上说不说得通”，只能等代码写完、起环境、登录、造数据，再截图。这一包里实际发生的情况：

- J4–J8 五条旅程同时冷启动隔离环境，单条约 25～30 分钟，还撞上 Docker 子网重叠、残留容器、停栈超时。
- 环境起来后，集成分支一有提交，`tsx watch` 就重启，隔离 API 随之崩溃，前后耗掉好几个小时，一步都没走成。
- 终审和业务复审到最后才发现大量“业务上说不通”的问题，例如：
  - 未授权、已撤销的客户页头仍显示绿色的“共享工作台”；
  - 概览页未选经营单元时显示 0 张、0 条，会被读成真实数据；
  - 越权页先说“未找到”，又说“可能未开通”；
  - 审计页里有开发备忘式的占位文字，还直接显示原始动作代码；
  - 封账后的提示把实时数说成“封账时的数”。

  这些问题都跟数据和后端无关，在原型阶段就能发现，修起来便宜得多。实际上它们是在环境、截图、复审都齐了之后才暴露的，修完又得补拍、复看、再跑一轮三轨终审。

### 1.4 少了一个 Oracle

原型是老板和 Owner 对齐需求时用的东西。对 Owner 来说，原型不是草稿，而是双方共同认可的“产品应该长这样”。原型一过期，就没有一个人能随时打开、不用登录就能看的业务参照。业务判断只能依赖 spec 文字加真实环境，而这两样都很贵。

## 2. 目标

- 原型随项目迭代，始终和实现对齐。做新功能或调整旧功能时，都先从原型入手，把流程打通。
- 原型成为 spec 的一部分，mock 数据也包含在内。
- 人工验证提前到每张票的开头，在 mock 上完成，不再等代码。

## 3. 讨论过程与关键取舍

### 3.1 否决：用真实应用的免登录预览模式代替原型

主控最初的倾向是：真实页面加一个预览模式，配 fixture 和由契约生成的 mock，这样只有一套页面，天然对齐。

**否决原因**：老板提新需求，是让他自己的 agent 直接改原型源码。原型就是他写需求的工具。预览模式要在工程环境里运行，他用不了。所以原型必须保持为独立的 HTML+JS。

教训：判断“该不该保留原型”之前，先问清楚原型的作者和用途是什么。原型不只是给人看的，它还是业务方的输入通道。

### 3.2 否决：原型放进业务仓库

放进业务仓库，原型和代码可以在同一个 PR 里改，最不容易漂移。

**否决原因**：Owner 明确表示暂时不让老板接触业务代码。原型用独立仓库。

### 3.3 协作模型：单一维护者

- 唯一维护者是 Owner，由他推送到 GitHub。老板只 pull，不 push。
- 老板改完，输出一个 patch 交给 Owner。Owner 在分支上审 diff、拆票。
- 这样就没有两边同时写的问题，也没有“哪个版本算数”的问题。
- 剩下的风险是老板在旧版本上改，导致 patch 冲突。对策是在原型仓库的 AGENTS.md 里写明“改之前先 pull”，由他的 agent 执行。

### 3.4 回写时机：从“包收尾”改成“每张票”

主控先提出在包收尾时把实现侧的改动回写原型，并讨论过“全部回写”还是“只回写老板会看的部分”。

**Owner 的修正**：不在包收尾时回写，而是每张票先改原型，再开始真实实现。先在 mock 上用 semantic verify 把业务语义打通。（收尾比对已按 3.10 同源方案取消，见 3.15。）

这一改动的意义：

- 原型从事后补写的文档，变成每张票的第一个交付物，不会过期；
- 原型的改动量随票摊开，不会在收尾时堆成一大坨；
- 人工验证提前到了每张票的开头。

### 3.5 原型里的 JS 逻辑

风险：原型的 JS 会自己算“能不能批”“还缺几项”“待批几条”，形成第二个规则层。这一包终审里，Track C 抓到的“前端复制业务状态判断”就是同类问题。

取舍：老板写的计算拦不住，也不该拦。约定是原型里的计算只作示意，规则以规则层为准。两边对不上时，当作需求问题问老板：是要改规则，还是原型写错了。代码不照抄原型的算法。

### 3.6 显式启用，默认关闭

原型失修比没有原型更危险，所以原型模式只在设计包时明确指定才启用，不因为“仓库里有原型”就自动生效。不是所有库都有原型；即使有，包没有指定时，也不把原型当作依据。确定性规则必须是可选的：

- 有原型：必须遵守额外的原型 spec，并同步修改 Ticket。
- 没有原型：流程和现在完全一样。

纯后端、规则、迁移、工具类的票，即使所在的包有原型，也不需要改原型。

### 3.7 必须是确定性的

Owner 的要求：流程要能保证被执行，不能靠 agent 自觉。这一包里有大量“靠自觉就会漏”的例证：

- 发给子代理的追加消息丢失过两次，4 项修复因此一直没做；
- spec、契约、代码三方都发生过漂移；
- 验收者漏收消息，空等了很久。

但业务语义对不对本身无法机械判定。所以确定性只放在三件事上：

- 判断必须发生；
- 发生的顺序正确；
- 依据的版本被钉住。

判断的内容交给 semantic reviewer。

### 3.8 原型不再自己计算：场景数据代替原型逻辑

回刷调研发现，现有原型的 JS 几乎自己算了所有业务结论（待办数、试用期、假期余额、能否发布、工资估算），基本都与规则层冲突。把计算剥离成静态 mock 风险最大：原型失去交互、mock 要穷举状态、巨型文件（`app.js` 435 KB、`employee.js` 275 KB）要重构。

结论：对齐只在命名场景上要求。场景数据基于生成契约类型与规则层结论手写即可（新功能首次走查前本就无响应可录）；mock 里的业务数字按规则层结论填写，前端不自行计算。走查录制回灌只是后续可选优化，不是前提。

### 3.9 沙盒与 Journey 原型共存

原型改为面向场景构造：依附 Journey（含变体）组织，好比从“开放沙盒世界”变成“有故事主线的世界”。但老板按页面思考，提需求靠在沙盒里随手改，所以沙盒不删，分两层：

- **Journey 原型（Oracle）**：按 Journey 和变体组织，每步是“角色 + 页面 + 场景数据 + 预期”。这是真正维护、必须与实现对齐的 spec，由 Owner 维护。
- **沙盒（草图）**：现有原型冻结为老板画板。改动只作需求输入，不算 spec，允许过期。

老板改沙盒 → 交 patch → Owner 翻译成新增或修改的 Journey/变体。这一步把原来隐含的需求澄清显式化。Journey 原型（即 3.12 的场景预览）主要服务 Owner；老板只看沙盒和交付壳子（见 3.12）。

不回刷、不重构旧原型：哪个包启用原型模式，就为它的 Journey 建 Journey 原型。前面按“回刷 170 条偏移、约 20 人日”的估算因此作废。

### 3.10 Journey 原型用真实 tsx，“先改原型”即“先在 mock 上写真实前端”

讨论过三种来源：

- 按截图手写 HTML：否决。截图只能用于验证，不能当原料，否则又造一个漂移源。
- 从沙盒原型迁移：与沙盒同技术，但长期每张票都要改两份代码再比对，成本不降，漏比的地方累积成漂移。
- **从真实 tsx 来（采用）**：只有一份代码。

取舍只看长期稳态，不看一次性迁移成本。tsx 方案的顾虑是“组件还没写就出不了原型”，换个视角即可化解——每张票的顺序变为：

1. 先定契约（DTO 形状）；
2. 前端照契约写真实 tsx，数据来自场景 mock，不接后端；
3. 在 mock 上按 Journey 和变体做 semantic verify，业务语义在此打通（即原来的“原型复审”）；
4. 后端实现，前端切真实接口；
5. 真实走查（不再单独与第 3 步截图比对，见 3.15）。

原型与实现同源，“对齐”问题消失。

代价与前提：

- 场景 mock 是长期资产，须照契约形状手写（见 3.8）。Journey 的“准备：”描述业务前提，mock 描述这些前提下的接口响应，两者用场景 ID 对应。
- 契约须先稳定，中途改契约要同时改 mock 与组件；现有 frontend/backend worker 分工已是如此。
- 老板看不懂 tsx，但他只改沙盒，不影响。
- 技术前提：场景 mock 能注入组件，并能导出成免登录、免后端的静态页。由 Probe 验证；注入方式见 3.17。

### 3.11 Probe 结果（2026-11-22，KaiSpan 税务端 J7 三场景）

结论：有条件可行。

- 真实组件 + `next dev` + fetch 级场景 mock + 固定身份，三个场景（未授权、已撤销、部分撤销）跑通，不改业务代码，页面零后端请求，不进登录页；与走查截图结构一致（文字差异来自截图之后的复审修复，不是 mock 造成的）。
- 注入点：生成 SDK 每次调用接受 `fetch`，也可全局替换 `fetch`；但 contracts 包未公开 `client`/`createClient`，且客户页骨架走裸 `fetch`，所以全局 fetch 补丁是目前最省的统一接缝。
- 鉴权：两个 dummy 环境变量 + 预置会话 cookie 即可免登录。
- 静态交付：“渲染快照 + 内联资源”约 50 行脚本即可产出可双击打开的只读页面；真正的 `next export` 要改动态路由和 next-intl，暂不需要。
- 回灌：走查时录 `/api/**` 响应、回放即可生成场景 mock；现有 journey runner 只缺录响应能力。真实响应含个人数据，只能留本地或脱敏。
- 防过期：fixture 用生成类型 `satisfies` 约束，契约改名时 `tsc` 直接报错；运行时“未 mock 的请求即失败”。

第二轮（新票从零起步，契约先行）：虚构“本月员工人数汇总”卡片，后端只写 DTO + controller 空壳（3 个文件、约 80 行，无 service/数据库），导出生成契约后前端照生成类型写 fixture 与真实卡片，两个场景渲染正常；DTO 字段改名后 fixture 类型检查报错。无硬阻碍。摩擦：每次 DTO 变更导出约 3.5 分钟（Nest 启动）。空壳约定：返回带稳定错误码的 501（如 `FEATURE_NOT_IMPLEMENTED`，并在 OpenAPI 声明 501），否则会被统一错误过滤器写成 `INTERNAL_ERROR`；前端在实现前不挂到生产页面。空壳误入生产只会对有权限用户返回 501，无写入、无泄露。

最小改造：env-gated 场景 bootstrap（生产不加载）、fixture 类型检查进 CI、未 mock 请求失败、journey runner 加响应录制（含脱敏）、快照导出脚本。

### 3.12 复用是核心目标（2026-11-24）

场景预览（即 3.10 的“真实 tsx + 场景 mock”，与老板的沙盒草图区分命名）是产品开发的一部分，不是 demo。它主要服务 Owner：开发过程中原型与规则先行，人能尽早参与验收，而不是对着大量规则文档想象界面。老板只看自己的 HTML 沙盒，以及交付时专门生成的壳子。

同一套场景 mock 一份数据、四处使用：

| 用途 | 说明 |
| --- | --- |
| 开发中人工验收 | Owner 在 mock 上确认 UI/UX 与业务语义 |
| 组件测试输入 | 作为组件测试夹具；R1 页面步允许组件测试输出作 evidence |
| Journey 准备数据 | 每套场景有稳定场景 ID，可对应多个 Journey 步骤或变体 |
| 交付给老板的壳子 | 同一组件 + 同一 mock 导出静态页，不另写 |

落地约束：

- 场景 mock 放业务仓库，挨着组件，用生成类型 `satisfies` 约束，随代码演进；
- 每套场景至少有一处实际使用（组件测试、Journey 或交付壳子），无人使用的 mock 审阅时按 finding 处理；
- 交付壳子只由导出脚本从真实组件与场景生成。

### 3.13 默认纵切，阶段可换代理（2026-11-24）

原型先行后，票内顺序天然是纵向的：定契约 → 前端在 mock 上实现 → 人看 → 后端实现 → 切真实接口。人看插在中间，拆成前后端两张票只会多一次交接。

- 纵切时同一代理在 feature 分支本地生成 client 自用、不提交，集成分支合入后统一重新生成；不需要单独的“契约票”与释放点。
- 后端多数只调用规则层、做鉴权与持久化，重逻辑不与 UI 争上下文。
- 专注度问题用“票纵切、阶段换代理”解决：前端阶段派带 UI 技能的代理，产出组件、场景 mock 与截图并落分支；人看后，后端阶段可续用或换代理，凭分支与 Ticket 接手。
- 单票装不进一个代理的上下文时，沿用现行规则在票内分批，不因此横切。只有并行能明显缩短关键路径时才横切。横切时两张票共用同一份契约与场景 mock，并指定唯一的契约维护者；需要先合契约时，才用 501 空壳作释放点。

选择标准写入 impl-planning：默认纵切，装不下就票内分批，需要并行才横切。

### 3.14 试点方式（2026-11-24）

不回头补既有包。下一个页面型任务直接启用，开包时记两项基线：第一次让 Owner 看到页面的时间点；终审中“业务上说不通”类问题的数量。验证期只在 KaiSpan 加仓库级校验（fixture 类型检查、501 卡点），证明划算后再进 impl-package 插件（默认关闭）。

### 3.15 人工检查点与一致性证明（2026-11-24）

- 默认不等 Owner：前端阶段结束后由语义审阅代理在场景预览上做 semantic verify，通过即进入后端阶段。Owner 需要先确认时，在开包时写进 plan / Ticket（`Owner 先确认: 是`），或中途直接说；只有这种票在中间硬停。
- Owner 查看方式：前端阶段结束时用导出脚本生成静态页，作为 `prototype-step` 的附件，双击即可打开，不起环境；与交付给老板的壳子同一个脚本。
- 取消 `prototype-compare`：原型与实现同源，一致性由两样已有证据证明——组件测试跑场景 mock 通过、真实 Journey 走查通过。

### 3.16 规则变化导致 mock 数值过期（2026-11-24）

生成类型只拦字段形状，拦不住数值；规则层改算法后，手写 mock 的数字不会报错。接受这个缺口，不另建机制：真实 Journey 走查会暴露差异；改规则的票同时更新受影响场景的 mock，写进改规则的检查清单。

### 3.17 Sol high 审阅后的落地调整（2026-11-24）

- **检查点前移**：`prototype-step` 在后端阶段开工前校验（dev-with-track 派后端阶段前查一次），收票（`ticket satisfy`）与 Gate 再复查。先后顺序靠“派发前必须存在有效记录”保证，不依赖 evidence 时间字段（现有 `recordedAt` 只是入账时间）。试点期由主控按此执行，插件阶段再做成卡点。
- **版本绑定与失效**：`prototype-step` 钉住一个提交，以及本票组件与场景 mock 的路径清单；这些文件在该提交之后变化即需重审，后端接线单独变化可沿用。现有 `evidence impact` 只扫套件与 Journey，插件阶段需要扩展。
- **501 卡点放在合入边界**：在 develop 必过 CI（`ci-checks.yml`）中扫描重新导出的 OpenAPI，空壳用显式标记识别，试点期即可生效；插件接入后 Gate 复用同一检查。
- **注入复用现有接缝**：优先用组件已有的 `api` prop 注入场景 mock（组件测试已是此用法），预览页沿用已有的免登录预览路由先例（如 `apps/web/app/finance-assistant/bank-reconciliation-preview`）；全局替换 `fetch` 只用于走裸 `fetch`、无法注入的地方（如税务端部分客户页）。未 mock 的请求直接失败。
- **静态快照**：next-intl 从 cookie 取语言，试点从渲染完成的页面导出无脚本、资源内联的只读快照；交互在活预览上检查，静态页供回看与交付。

### 3.18 对未启用包的兼容（2026-11-24）

目标：Plan 缺 `Prototype` 头或写 `none` 的包，流程、状态与应用行为与现在完全一致（两轮 Sol high 静态审阅）。

**引擎与证据**

- 缺头按 `none` 解析，与显式 `none` 走同一分支；`check-spec` 只读 Spec，不受影响。
- 派发前检查、`ticket satisfy`、Gate、`evidence impact` 先按模式短路，只对启用且 `场景预览: 适用` 的票执行新增校验；Gate 中的 501 复查同样只在启用时执行。
- CLI 只新增 `prototype-step` 证据类型并单独校验；旧参数、旧 state、旧证据判定与进度投影不变。
- 回归验证：取已 init、已有证据的包，缺头与显式 `none` 各一次，插件升级前后 `situation` 缺口完全一致。
- 提醒：插件升级本身不新增缺口，但业务仓库落地原型基础设施的提交，可能按现行规则触发进行中包的复验。

**技能与模板**

- dev-with-track、impl-planning、req-align、run-acceptance 中的原型内容只写成“启用时”分支；`none` 沿用现行拆票、派发、需求对齐与真实走查，模板不出现新字段。

**KaiSpan 仓库级约束（对所有包生效，属预期）**

- 501 扫描：复用 CI 现有 OpenAPI 导出步骤，只拦带显式空壳标记的 501，合法 501 放行；须覆盖现有跳过契约检查的分支。当前 develop 无声明 501 的接口，上线即零误拦。
- 场景 fixture 参与现有 `tsc` 类型检查，契约漂移对全仓库报错；这是有意的共享防漂移约束。
- 前端隔离：生产页面保留真实 `api` 注入；现有预览页（银行对账预览、工作台预览）各自开关不变；新场景 bootstrap 只从独立预览入口、在本地或测试显式启用时加载，裸 `fetch` 拦截限预览实例；验证开关关闭时普通页面与生产产物不受影响。

## 4. 风险

| 风险 | 说明 | 当前对策或态度 |
|---|---|---|
| 成本上升 | 页面型票多一次 mock 场景与一次语义复审，估计增加 20%～30% | 换回后期返工和环境冷启动的成本，判断划算；按 3.14 试点验证 |
| 实现中途发现场景预览不对 | 截断、权限边界、接口拿不到某个值，没有原型时同样会遇到，只是实现会悄悄偏离 spec，直到终审或走查才暴露。有场景预览反而让偏离必须显式发生 | 同一份组件直接改，补一次语义复审；场景 mock 同步更新 |
| mock 与契约分叉 | 两边各写一份字段 | mock 用生成类型 `satisfies` 约束，类型检查进 CI |
| mock 数值与规则层分叉 | 见 3.16 | 真实走查兜底，改规则票同步 mock |
| 老板基于旧版改沙盒 | patch 冲突 | 原型仓库 AGENTS.md 写明先 pull |
| 501 空壳进生产 | 横切时契约空壳先合入集成分支 | 两道机械卡点：develop 必过 CI 扫描 OpenAPI，仍有带空壳标记的 501 接口即拒绝合入（插件 Gate 复用）；场景 bootstrap 只在 env 开关下加载，生产构建不含 |
| 老板侧 agent 不稳定 | 能否每次都按约定输出 patch | 未验证 |
