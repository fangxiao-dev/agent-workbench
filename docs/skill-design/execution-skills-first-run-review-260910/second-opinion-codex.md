# 对执行 Skill 首次实战复盘的独立审核意见

日期：2026-09-10。审核基线：`3672f78`。本文只提出审核意见，不批准或实施 Skill/runtime 修改。

**结论：原报告适合作为问题线索集，尚不适合作为十项改造的直接依据。** 它抓到了重复记账、验收边界遗漏、等待期间漏掉可推进工作等值得处理的问题；但把事件次数当作浪费、把不同种类的审查混为一谈，并存在删除状态和变更授权的事实错误。建议先纠正归因，再优先处理证据登记成本与下游验收边界；暂不据此新增通用 hook 或全 lane 提交门槛。

## 1. 审核范围与方法

- 用户给出的 Claude plans 文件实际是调研派发计划。真正的审核对象是 [首次实战复盘](report.md)，以及它引用的两份设计和对应 Git 变更。
- 主控阅读报告、定向核对设计、现役规则和运行代码；两名 `luna-worker` 分别负责原始 rollout 抽查与规则/提交核查。没有由主控通读巨量日志，也没有把原计划中的派发指令当作用户的新指令执行。
- 下文区分三个层次：源码/历史可直接证实的事实、报告所述但未独立复核的运行事件、由事实推导的候选建议。原报告的“抽查行号命中”不等于时间归因和方案有效性也已得到验证。
- 审核不是五个 session 的全量重做；未独立验证的分钟数、并发比例和“只有两轮有价值”等判断不作为本文的收益承诺。

## 2. 需要先纠正的审核结论

### R1 · P1：只改一句 evidence 规则，解决不了运行时的重复登记

原报告 §4 建议 1 主张“已消费结果引用 receipt 即可”，并把成本估为改一句话、收益列为最高。这同时混合了两个问题：是否还需要证明 acceptance，以及已经证明的事实如何低成本保存。

现役 [`engine.py`](../../../plugin-marketplace/plugins/impl-package/scripts/impl_package_runtime/engine.py) 的 `_evidence_coverage_for`（664 行起）遍历 Ticket 的全部 claim，要求相同 revision、environment 的有效 supporting 记录；`ticket satisfy` 和 Gate 继续调用覆盖检查。`command_evidence_add`（1160 行起）按单 claim 接收记录，前后校验状态并刷新投影。

因此，仅放宽 Skill 文案会让主控与 CLI 发生冲突，最终仍可能绕回补登记。“已被消费”也不自动证明错误分支、并发约束或清理结果均满足 acceptance。

**修正建议：保留验收要求，先减少同一事实的重复表达和持久化成本。** 先确认现有 artifact 可以覆盖哪些 claim、哪些只是 revision 变化后重复挂接；再判断是否需要批量登记或复用已有有效映射。具体运行时改法仍需有界设计与性能测量，不能估为一句文字修改。

### R2 · P1：命令次数和等待时长，不能直接换算为可省时间

原报告 §3.2 将 `git status`、`diff --check`、全量测试、镜像构建一起归为“重复检查”，但这些操作的成本和输入变化完全不同。即使 Git HEAD 相同，未提交代码、依赖、配置、数据库状态或测试数据也可能变化。

**原日志抽查已经找到反例。** B3 五次全量 pytest 对应结果依次为 `2059 passed / 534 failed`、`2562 passed / 21 failed`、全绿、一个失败、全绿；中间有提交和修复。次数成立，但“纯重跑至少 20 分钟”不能成立为已证实结论。见附录 E2。

§3.3 的主控 wait 时长也可能与 worker 的有效工作重叠。证明存在可消除的串行，需要指出当时具体哪项工作已授权、依赖满足、资源兼容且值得提前执行，而不只是主控在等。

**修正建议：保留次数统计，撤回未经逐事件核实的“纯重跑至少多少分钟”“绝对收益最大”等排序。** 每种成本抽取代表事件，补齐输入是否变化、是否修复前次失败、是否产生新判断，以及可行替代路径。无需新增长期台账。

### R3 · P1：四轨 initial 太重，不等于所有 delta review 都应延后

原报告把 A2 用户反对对 INCOMPLETE 返回运行完整四轨，解释成“每个代码 return 当次独立审查”被实战否定。

原日志 A2 L1220 的定向复核确认，用户仍保留真实缺陷审查、修复后单 reviewer 和最终 terminal-final；纠正的是未完整纵切立即运行四轨 initial 的做法。见附录 E1。

但这是不同层次：[`dispatcher/SKILL.md`](../../../skills/dispatcher/SKILL.md) 第 4 步要求独立 delta review；[`do-review/SKILL.md`](../../../plugin-marketplace/plugins/impl-package/skills/do-review/SKILL.md) 定义 formal initial、finding-closure 和 terminal-final，48–49 行已经规定 named finding closure 只用一名 reviewer。现役 terminal-final 也允许符合条件的轨复用已有 PASS。

**修正建议：明确缩小的是 formal review 的范围和拓扑，还是要改变所有代码增量的审查时机。** 后者是额外决策，不能从反对四轨直接推导。已知未完成范围、证据缺口和真实实现缺陷应分开处理，这个方向合理。

七轮终审持续找到真实问题，也不能单独证明“终审太早”：候选因审查发现缺陷而变化，与启动前已经知道范围未决，是两种因果。需要核对每轮启动时有哪些已知未完成事项。

### R4 · P2：工具参数错误，没有证明旧 hook 砍错了

原报告 §2.2 自己说明没有一次损失来自 worker 返回格式错误，却仍把撤销 `SubagentStop` 判为“唯一真正砍错了”。原 [T10 决策](../impl-package-astra-thinning-decisions-260906.md) 239–252 行分别解释了三种撤销机制，不能与新提议的主控调用前校验互换。

路径拼错、patch 上下文失配、API 参数错误、文档标题不合规也不是一个校验器能低成本统一解决的问题。已有工具/CLI 拒绝非法参数，本身可能正是保护生效。

**修正建议：撤回“砍错了”的定性。** 如某种错误反复出现，优先改其实际入口、帮助示例或错误反馈；新 `PreToolUse` 只能作为独立候选，需证明比现有反馈更早、更便宜且不会重复维护 schema。

### R5 · P2：等待前注入投影值得试，但不能承诺解决机会发现

原报告建议在等待/中断前注入 runnable/withheld/in_flight。已有 capsule 确实可作为复用方向；但“读过规则仍违规”只能证明该次规则未落实，不能证明新增触发点必然有效。

[联合提案的最终实施记录](../dispatcher-dev-with-track-sdd-consolidation-proposal-260908.md) 第 7 行明确：程序只展示可从业务事实推导的动作，不承诺覆盖主控发现的全部工作。投影不能凭空发现尚未纳入 package 的关联 Issue。因此 B3 用户提醒查看其他任务，并不自动等价于“多 render 一次就能解决”。

**修正建议：分开验证已知候选被忽略、未知候选未被发现、无合理依据中断 worker 三种问题。** 注入点可以做小范围行为验证，未验证前不列为收益最大的实施项。

### R6 · P2：统一所有 lane 的 HEAD，会扩大串行范围

原报告建议 10 要求多 lane 同一基线，且任一 return 未消费/审查前限制提交。现役 [资源隔离规则](../../../skills/dispatcher/references/resource-isolation.md) 18–22 行按实际读写影响隔离或排序；`do-review` 已固定单个 ReviewRun 的不可变输入。

**修正建议：固定每次验证/审查实际消费的输入，只排序会改变他人读取结果或验证依据的操作。** 一次共享工作树的输入漂移，不足以支持所有 lane 共用提交门槛。

### R7 · P2：删除状态、授权历史和计数存在明确错误

| 原报告判断 | 可核实事实 | 应如何改写 |

## 3. 我认为更值得保留的洞见

### 先减少一次事实要维护多少份表示

重复 evidence、ER、claim、报告可能共享同一个根因：一次真实验证完成后，主控仍需把事实改写成多份载体。继续加“少记账”的文案，可能只是把不一致留给主控承担。

更有价值的问题是：哪些载体承担独立决策，哪些只是在抄同一结果？前者保留；后者优先引用现有结果或从权威记录生成。这个方向比“已消费就免验收”更准确，也能追到实际 CLI 成本。

### 排除下游功能改造，不等于排除兼容性验收

原报告的 training 边界案例值得保留，但未必需要固定矩阵。立项时对改变的字段、引用或接口，沿现有消费者走到一个能观察结果的终态，明确“要改哪里”和“要证明没破坏哪里”。

例如 training 实现可以不在本次修改范围，但新 DatasetVersion 能否继续进入既有训练链，仍可能属于必要兼容性验收。这比增加更多 Ticket/claim 更直接。

### 先分清规则缺失、规则未执行和宿主未加载

报告中的 session 跨越了规则变更：`e150587`、`8d21780` 在 09-09 17:05 才提交，`11f64bf` 在报告提交前约 15 分钟落地。仓库提交时间也不等于运行 session 已读取该内容；standalone junction 与 plugin 安装缓存的生效方式不同。

所以每个“规则没落实”的强结论，应关联该事件实际读到的规则，至少对关键事件核实。已存在的 closure 单 reviewer、delta 恢复、backfill 兼容路径，不宜再次包装成新设计；应先定位为何现场没用上。

### 审查发现密度，比审查人数更能说明问题

41/82 次派发是审查，不等于一半成本被浪费。若终审连续暴露事务、崩溃恢复、传播等真实缺陷，更值得检查这些不变量为何没有进入实现自证，以及修复是否遗漏同类调用路径。

减少重复审查可以做，但应区分“同一个 finding 换名字反复出现”和“新增有效缺陷”。前者提示归并或根因修复不足；后者说明审查仍在产生价值。

## 4. 我的推荐方案：先做四项有界改进

**我推荐：先改 evidence 的批量写入，再补下游验收边界，随后明确增量审查与正式审查的衔接，最后用真实事件验证等待/中断行为。** 前三项形成具体改进，第四项决定是否值得进一步做 hook。不把 Claude 的十条建议打包实施。

三个可选方向中，“只加强 Skill 文案”最省改动，但碰不到 evidence 的运行成本；“全面加 hook、门槛和新台账”覆盖面大，却缺乏收益证据。我选择中间方案：在已确认成本的实际入口动手，复用现有流程与状态。它符合已有 rubric 对少流程、单一职责、保留独立 delta review 的确认偏好；因此过滤通用候选登记、固定下游矩阵、全局提交门槛这几类扩张方案。

### 第一项：一次提交一批 evidence，保留原有验收含义

**改哪里：** evidence CLI 及其现有运行实现；dev-with-track 只同步入口用法。

**推荐行为：** 沿现有 evidence 登记入口增加批量输入。同一次消费已经得到的多条记录，由主控一次提交：读取并校验当前状态，在内存中应用整批记录，校验最终状态，持久化一次并刷新投影一次。单条调用兼容保留，单条与批量复用同一条记录校验逻辑。实际代码设计须沿现有写入、失败恢复和并发约束完成，不另建 writer 或队列。

整批存在非法 claim、坏 artifact 或不满足当前记录合同的输入时，不写入任何新记录；完全相同的记录重试保持幂等。satisfy/Gate 对 claim、revision、environment 的要求保持原有含义。一个 artifact 可以支撑它实际覆盖的多条 claim，但不能因此假定覆盖全部 acceptance。

**为什么先做：** 已核实逐条入口重复执行状态校验和投影更新；这是一处可集中消除的成本，不依赖“模型以后少做点”的承诺。暂不顺手设计跨 revision 的自动证据继承，那会引入另一项证据有效性决策。

**验证：** 用同一组真实形状的记录比较逐条与批量结果，确认 evidence 与 Gate 判断一致；覆盖中途坏记录不部分写入、重复提交幂等；比较完整状态校验和投影刷新次数、耗时。预期减少重复工作，具体节省分钟数以实测报告。

### 第二项：把“改动范围”和“兼容性验收范围”分开写清

**改哪里：** req-align 现有 contract-impact 方法及其行为样例，不同时扩张 Plan/Ticket 流程。

**推荐行为：** 当修改 schema、引用、lineage 或公开接口时，沿既有消费者追到一个能观察结果的业务终态。在现有 Spec/contract-design 中写清：本次修改哪些生产者或消费者；哪些未改消费者仍须验证兼容。沿用现有材料表达，不新增固定矩阵、独立文档或 approval。

例如“training 不在修改范围”可以成立，但不能据此自动排除“新 DatasetVersion 仍能被既有 training 消费”的验收。也不要求穷举所有下游：只跟进受本次变更影响的既有路径。

**为什么第二：** 它能在实施前暴露走错验收终点的问题，避免先花时间搭出一条与本次承诺不对应的 live journey。

**验证：** 以 LabelingProfile→DatasetVersion→既有 training 作为一个回归样例，再用一个下游不受影响的反例验证不扩大范围。合格结果应选对兼容性终点，同时不凭空增加 training 实施 Ticket。

### 第三项：明确 delta review 的轻量入口，停止把所有 return 升成正式四轨

**改哪里：** Dispatcher 与 do-review 的现有交接处，正式 requirement 仍由 dev-with-track 判断。

**推荐行为：** 保留每个代码 return 的独立 delta review。没有额外 formal requirement 的增量，由一名独立 reviewer 检查固定增量及直接受影响路径；需要正式审查时使用已有 do-review admission，不额外叠一套同范围轻量审查。已有审查能同时满足两项要求时，复用其真实结果与关联。

消费返回时，明确区分已知未实现范围、验收证据缺口和真实实现缺陷：前者继续实施，证据缺口保留相应 acceptance pending，真实缺陷按影响安排修复。named finding closure 沿用现有单 reviewer；formal terminal-final 沿用既有 coverage 与 PASS 复用规则。

已知仍会改变实现或合同的事项未闭合时，不启动完整 terminal-final；审查发现新缺陷后仍允许修复和必要复核，不设置人为轮数目标。这里收窄的是已知无效的启动时机，不是承诺一次终审通过。

**为什么第三：** 它保留早期发现根因的能力，同时减少把“尚未做完”反复审成 finding 的成本。轻量 delta reviewer 的入口是候选细化，尚不是已批准的新合同。

**验证：** 用三个有界场景验证路由：INCOMPLETE 增量且存在已知剩余范围；只修命名 finding；候选稳定且触及安全边界。分别检查没有遗漏增量审查、没有重复四轨 closure、最终仍具有完整适用 coverage。

### 第四项：先验证等待决策，再决定是否需要 hook

**改哪里：** Dispatcher 现有行为评测样例，首轮不新增 runtime hook。

**推荐行为：** 将本轮真实事件压缩成三个可复跑场景：worker 运行较久但边界可信；存在可提前处理的独立工作；确实没有值得推进的独立工作。沿用当前五步循环判断，不增加每次 wait 必填的解释或候选台账。

**验证：** 第一类应继续等待或请原 worker 汇总，不因时长机械中断；第二类应推进具体独立工作；第三类应正常等待，不为了并发制造任务。先固定当前 Skill 内容做基线复跑，确认问题在当前规则下仍能复现。

如果当前材料仍反复失败，再只对失败的动作比较“动作前短提示”和“额外投影注入”两种做法，检查宿主是否支持、提示是否包含真实新增信息。有效才实施；无效就放弃该方案。这里的评测是明确的第四项交付，不是无限期观察。

### 本轮不纳入的改动

- 不恢复旧 fact、候选清单或 bookkeeper；没有独立必要性证据。
- 不新增通用参数校验 hook；对重复出现的具体入口错误分别修反馈或用法。
- 不强制所有 lane 同 HEAD，也不强制所有检查只跑一次；继续按实际输入变化与资源冲突安排。
- 不再新增 backfill 的全局不阻塞口号；现有局部依赖规则和真实前置关系足以表达。
- 不把“本地完整复制所有 CI”设成统一发布前置；保留项目实际 required checks，针对确证遗漏修其入口。
