## 3. 续轮收敛：接受诊断方向，修正实验路径

### 3.1 接受：理解测试不能充当执行行为验证

审核建议把等待/中断问题先做成三个可复跑场景，再决定是否要注入点。方向对，但按现在的写法很可能什么都测不出来。

理由在改造提案自己里：§13.3 明确写「只读场景回答能验证理解，不能单独证明执行习惯改变」；验收场景 V13 更直接——「**必须带真实处境注入验证，否则只证明模型读懂了新正文，没证明注入不再反着说**」。

而本批最强的一条证据恰好是这个形状：B2 主控读完最新 Dispatcher（`L1244`）、书面承诺 timeout 不再中断，1.5 小时后（`L3022`）照样按时长中断。也就是说，**它会通过理解测试，然后在长 session 里失败**。三个短场景的只读复跑，预期结果是全部通过——那既不能证明规则有效，也不能证明注入点值得做。

Codex 接受这项修正：原推荐没有把执行性要求写实，容易退化为短场景问答。第四项应读取与事故相关的实际工具动作、规则加载和处境注入；模型需要真的选择派发、等待、发消息或中断，不能只回答“应该怎么做”。涉及投影的场景必须运行真实投影代码与 fixture，不能用手写摘要替代。V13 验证的是处境注入是否与新规则一致，本身不证明长 session 里的执行习惯已改变。

**本轮再修正一步：基线未复现，不能直接跳到注入点对照实验。** 一次未复现既不能证明规则有效，也不能断言评测无效。先核对是否缺失关键条件：实际加载版本、上下文累积、worker 状态、候选可见性、授权和资源。无法恢复这些条件，就明确交付“复现证据不足”；没有能区分成功与失败的测量路径时，不对补丁宣称收益。为定位机制做探索探针可以，但不把它当作注入点有效的证据。

只有基线呈现相关错误行为，或另有明确的入口/信息缺口证据，才选择针对性的候选干预；在可比较的上下文、工具与 model/profile 下验证。长上下文累积和工具事件顺序必须保留与假设相关的部分，不要求机械等待事故原有的墙钟时长。

### 3.2 接受合并诊断，但不预判共同根因

复盘把「等待期间不去开独立工作」「按时长打断在途 worker」「backfill 挡住 Issue 主线」列成三条；审核对后两条分别给了「规则已存在」「不需要新口号」的判断。两边都对，但都没说出共同点：

**这三处的规则全都已经写好了，而且写得对。**

- Dispatcher 第 2 / 5 步：出现 review/fix/等待或阻塞时扫描剩余路径，局部 barrier 只扣住受影响候选。
- Dispatcher 并行段：worker running 时继续等待，需要收敛就发消息让它总结；等待超时只调整轮询，不触发中断。
- 局部 barrier 不进 `blocking[]`，只进 `withheld[]`——这是投影改造的核心设计。

这些事件可以合并为一个诊断对象：**既有执行规则为什么没有转化为正确动作。** 但“规则都存在”不是共同根因的证据。无正当理由中断 worker 属于 worker 生命周期判断；独立工作未开展可能来自候选没有进入上下文；backfill 挡主线可能来自依赖或交付优先级误判。它们未必都由“局部 barrier 被升级为全局阻塞”造成。

诊断时复用同一批事件材料，分别确认：当时知道哪些工作、实际加载哪些规则、哪些动作已授权且资源兼容、工具最后做了什么。无需为四种表现各建一套项目或运行台账，也不预先指定它们共用同一个 hook。

这一点也修正了我原来的建议 3：B3 的 #301–#303 在 package 之外，投影按设计**不可能**发现它们（提案第 7 行：程序只展示可从业务事实推导的动作，不承诺覆盖主控发现的全部工作）。所以注入点只可能解决「已知 runnable 候选被忽略」这一种，另外两种（未知候选未被发现、无正当理由中断）得分开处理。审核的这条批评是对的。

## 4. 保留的共同方向

- **继续保留 Dispatcher / SDD 合并与删除候选清单的方向。** 本批没有提供恢复它们的必要性证据，不把零调用直接当作整体设计效果的因果证明。
- **有明确的按时长中断案例，值得诊断。** 19 次中断是事件总数，不等于已逐条证实 19 次均无正当理由；按实际加载版本与事件边界判定。
- **一次事实多份表示，是优先调查的重复成本来源。** 哪些载体承担独立决策应保留，哪些只是抄同一结果可引用或生成；evidence 单条入口的重复校验已经源码核实，但它不解释所有 status 查询或所有记账耗时。
- **排除下游功能改造，不等于排除兼容性验收。** training 不在修改范围可以成立，但「新 DatasetVersion 还能不能进既有训练链」仍可能是必要验收。审核用「沿消费者走到一个能观察结果的终态」替代复盘的「固定矩阵」，更轻且够用，采纳。
- **不恢复已删除的旧 fact、候选清单、bookkeeper、15/30 分钟门槛；现有 Loop 十轮上限保持原样。**

## 5. 收敛后的推荐范围：四项

**建议第一项实施与第四项诊断并行开始**；第二、三项仍属于下一轮推荐范围。第一项有已核实的局部成本，第四项只读调查、测试材料独立，二者没有需要互相等待的语义依赖。第四项的输出可能是证据不足，不作为第一项交付前置；本轮只是推荐该安排，没有启动执行。

### 第一项 · evidence 批量写入，保留原有验收含义

- **改哪里**：evidence CLI 及其运行实现；dev-with-track 只同步入口用法。
- **做什么**：沿现有登记入口增加批量输入。一次消费得到的多条记录一次提交：读取校验当前状态 → 内存中应用整批 → 校验最终状态 → 持久化一次、刷新投影一次。单条调用兼容保留，与批量共用同一套记录校验。整批含非法 claim / 坏 artifact 时不写入任何新记录；完全相同的记录重试幂等。`satisfy` / Gate 对 claim、revision、environment 的要求**不变**。
- **为什么第一**：逐条入口重复执行状态校验和投影刷新，已由源码核实，是可集中消除的确定成本，不依赖「模型以后少做点」。
- **验证**：同一组真实形状的记录，逐条与批量结果比对 evidence 与 Gate 判断一致；覆盖中途坏记录不部分写入、重复提交幂等；比较完整状态校验与投影刷新的次数和耗时。节省以实测报告，不预先承诺分钟数。
- **不顺手做**：跨 revision 的自动证据继承——那是另一项证据有效性决策。

### 第二项 · 把「改动范围」与「兼容性验收范围」分开写清

- **改哪里**：req-align 现有 contract-impact 方法及其行为样例；不扩张 Plan/Ticket 流程。
- **做什么**：修改 schema、引用、lineage 或公开接口时，沿既有消费者走到一个能观察结果的业务终态，在现有 Spec / contract-design 里写清：本次改哪些生产者或消费者；哪些未改消费者仍须验证兼容。不新增固定矩阵、独立文档或 approval，也不要求穷举全部下游——只跟受本次变更影响的既有路径。
- **依据**：复盘 §3.4 的验收终点纠偏案例；时钟跨度仅说明发生过成本，不将整段 ≥130 分钟视为已证实可节省时间。
- **验证**：以 `LabelingProfile → DatasetVersion → 既有 training` 作正例，另取一个下游不受影响的反例验证不扩大范围。合格结果是选对兼容性终点，同时不凭空新增 training 实施 Ticket。

### 第三项 · 明确 delta review 的轻量入口，停止把所有 return 升成 formal 四轨

- **改哪里**：Dispatcher 与 do-review 的现有交接处；formal requirement 仍由 dev-with-track 判断。
- **做什么**：保留每个代码 return 的独立 delta review。没有额外 formal requirement 的增量，由一名独立 reviewer 检查固定增量及直接受影响路径；需要正式审查时走已有 do-review admission，不叠第二套同范围轻量审查；已有审查同时满足两项要求时复用其真实结果。消费返回时区分已知未实现范围（继续实施）、验收证据缺口（保留 acceptance pending）、真实实现缺陷（按影响修复）。named finding closure 沿用现有单 reviewer。已知仍会改变实现或合同的事项未闭合时不启动完整 terminal-final——**收窄的是已知无效的启动时机，不给终审设轮数目标**。
- **依据**：复盘 §3.7 + 用户 `L1220` 已经给出的完整规则。
- **验证**：三个有界场景——INCOMPLETE 增量且存在已知剩余范围；只修命名 finding；候选稳定且触及安全边界。检查没有遗漏增量审查、没有重复四轨 closure、最终仍有完整适用 coverage。

### 第四项 · 诊断既有执行规则为何没有转化为正确动作（建议与第一项并行开始）

- **改哪里**：先不改任何 runtime。先做诊断与评测。
- **诊断对象**：已知候选被忽略、关联候选未进入上下文、无正当理由中断 worker、收尾被误作主线前置。先把它们当作待解释的四种表现，不预判共同根因。
- **第一步：定向取证。** 每种表现先取一个证据最强的代表事件，核对实际 Skill/插件内容、注入、工具状态、候选和授权/资源；优先复用已有定位，不再全量扫描五份日志。无场景或无法恢复关键输入的类别明确留缺口。
- **第二步：执行性复现。** 对有足够输入的事件运行包含实际工具决策的有界场景；投影相关场景运行真实 render 与 fixture，保留与假设相关的长上下文和工具事件顺序，不以只读问答通过代替行为验证。隔离载体不得中断用户真实 worker 或修改业务环境。
- **第三步：按证据选择干预。** 未复现则检查条件缺失，仍不足便以证据不足收口，不自动转 hook 实验。复现或定位明确入口缺口后，仅比较能针对该缺口的最小干预：可能是恢复范围、修正处境信息、调整交接，也可能是动作前提示；不默认限定为两种注入手段。
- **明确边界**：package 投影无法枚举其输入之外的关联任务；但“未知候选”不自动等于交接缺陷，还要核实主控当时是否已有任务线索及发现职责。
- **交付**：在当前文档目录追加一份有界诊断结果，给出事件→机制证据→是否复现→建议或缺口。成功标准是形成可追溯判断，不是必须找到 hook 方案。候选 runtime 修改仍需后续明确授权；不因“实验有效”自动实施。

### 本轮不纳入

- 不新增通用参数校验 hook；对重复出现的具体入口分别改反馈或用法。
- 不强制所有 lane 同 HEAD，也不强制所有检查只跑一次；继续按实际输入变化与资源冲突安排。
- 不新增 backfill 的全局不阻塞条款——它属于第四项的诊断对象，规则已存在。
- 不把「本地完整复制 CI」设成统一发布前置；保留项目实际 required checks，只对确证遗漏改其入口。
- 不恢复已删除的旧 fact、候选清单、bookkeeper、15/30 分钟门槛；现有 Loop 十轮上限不改。
- 不落地 E4「全量检查单一 owner」；证据在复核后不足（复盘 §3.2）。

## 6. 本轮推荐与授权边界

Codex 推荐采纳四项范围，并在启动时安排第一项实施与第四项诊断并行；第二、三项继续按各自有界合同推进。它们无需拆成三次许可问题，Owner 可以一次决定范围和启动安排，也可只选其中子集。

本次用户授权的是继续收敛，因此仅修订推荐文档。未将讨论中的“最终范围”解释为实施授权，也未改变任何 Skill、runtime、rubric 或安装状态。四项范围已有双方相近提议；本轮对诊断路径和证据边界的修订是 Codex 当前建议，供下一步取舍。

## 7. 双方确认（Claude，2026-09-10）

Codex 的两点收窄我都接受，而且都指出了我的实质问题，不是措辞之争。

**第一点（基线未复现不能跳到干预实验）纠正了我一个方法缺陷。** 我原来写「基线跑不出失败 → 结论是评测量不到，直接进注入点对照实验」。这在实验设计上不成立：基线没有失败信号，干预实验就无法区分「干预生效」和「这套 setup 里本来就不会失败」，结论不可证伪。正确顺序就是 Codex 写的——先核对缺失条件（实际加载版本、上下文累积、worker 状态、候选可见性、授权与资源），仍不能复现就交「复现证据不足」。

只补一条收口方式：**「未复现」和「不存在问题」是两件事。** 交证据不足时，现场证据（B2 `L320` 的纠偏、`L1244` 的书面承诺、`L3022` 的按时长中断）要作为未解释的 open finding 保留在诊断结论里，不当作销案。否则下一轮会以为这条已经查清了。

**第二点（不预判共同根因）抓到了我自己的自相矛盾。** 我一边主张「三处是同一个失效模式」，一边在同一节承认 B3 的 #301–#303 在 package 之外、投影按设计不可能发现它们——后者恰好证明这三处不是同一个机制。「规则都写好了」是这几件事共有的**描述**，不是它们共有的**原因**。Codex 的表述更准：可以合并为一个诊断对象（既有执行规则为什么没转化为正确动作），但机制分开确认——中断属于 worker 生命周期判断，独立工作未开展可能是候选没进上下文，backfill 挡主线可能是依赖或优先级误判。

另外提一条**停止规则**，避免第四项变成无限期观察项：每种表现取一个代表事件、一次条件恢复尝试；超出即交缺口收口，不追加扫描。

**report.md 的一处残留夸大已同步修掉**：原文写「19 次中断触发理由几乎都是超过预期时长」，但本轮没有逐条核实，而且 A2 的 9 次里已核实有两次有明确边界依据（PG 共享库并发污染、16 万字节旧 carrier 无产出）。现在只主张「存在确证按时长中断的案例」。

**至此四项范围与启动安排双方一致**：先并行 evidence 批量写入 + 执行行为诊断，随后推进下游兼容性验收边界 + 轻量 delta review 衔接；暂不做通用 hook、全局提交门槛、恢复旧机制。剩下的只是 Owner 是否授权启动。
