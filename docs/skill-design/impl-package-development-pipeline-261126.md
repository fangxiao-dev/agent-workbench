# 实施包开发 Pipeline：讨论记录

状态：推荐方案待整体确认；本文区分已确认方向与推荐方案。

日期：2026-11-26

## 背景与目标

实施包主控需要同时记住 Ticket 依赖、派发与返回、审阅组循环、修复复验、验证和 Gate。现有工具已经能确定性地记录和检查一部分事实，但流程分散在 `dev-with-track`、`do-review`、package engine 与其他工具里，主控仍容易遗漏步骤。目标是提供一条统一的开发流程状态机，按实施包和 Ticket 帮主控持续看清可做事项与流程欠项，降低对 Plan 和多份 Skill 的反复阅读。

## 已确认的方向

1. **范围**：pipeline 服务实施包，从设计和 Plan 已批准、准备执行时接入；普通小任务直接做，无须上 pipeline。一个设计文件、一个 Plan 和一张 Ticket 组成的小包也适用。
2. **统一流程**：小包与大包共享同一条 pipeline，不建立各自独立的流程；区别来自实际 Ticket 数量、依赖、工作和审阅要求。
3. **职责**：pipeline 管流程状态、步骤顺序和可机器核对的前置条件，不替主控、执行者或审阅者判断内容正确性，也不把一条 PASS 机械地等同于判断本身正确。
4. **Ticket 粒度和依赖**：按 Ticket 跟踪工作，消费实施包已有的依赖关系与固定结构；不同 Ticket 可并行推进，具体安排仍由主控判断。Plan 应逐步减去可由通用流程提供的重复步骤，保留本包独有交付、依赖、验收和特殊约束。
5. **派发与审阅的粒度独立**：主控可以一批返回就审，也可以把多个返回组合后审；最终需要覆盖应审的改动，中间如何组合由主控选择。
6. **跨 Ticket 审阅**：一个审阅批次可以覆盖多张 Ticket 的返回；一张 Ticket 的返回也可分属不同审阅批次。需能追溯实际覆盖范围并识别欠审。
7. **本轮审阅收齐后统一处理**：保留现有规则，同一审阅批次本轮登记的各轨全部返回并关闭后，才统一分诊并安排该轮修复；意见可能重合或互补，可一起分组处理。其他无关工作可以继续。
8. **引擎职责复核**：现有 engine 可能已有流程控制，需要一起调查哪些应剥离、哪些可参考或复用，使职责更清楚。
9. **统一主控入口**：主控通过 pipeline 查看流程与登记动作，由 pipeline 接通已有工具；底层 CLI 保留给排障和恢复，恢复时重新读取事实。
10. **固定实际审阅对象**：跨 Ticket 或跨分支组合审阅时，可以使用已集成版本或隔离审阅快照；每个审阅批次固定实际存在的审阅对象，并记录所覆盖的返回。后续集成后的变化按影响判断是否需要复验。
11. **允许补登记**：发现改动找不到派发或返回记录时，标为归属待确认，暂不计入有效审阅覆盖；主控核对 diff、来源和已有审阅证据后可补登记并安排必要审阅。只限制受影响的收口，独立工作继续；前期流程可以适当宽松，避免被登记要求卡死。
12. **代理身份与模型路由**：记录角色、负责范围、宿主返回的 agent/session ID、主控填写的模型名称和推理强度、派发和返回关系以及与审阅组的关系，便于按原角色续用。主控填写的是本次派发所选配置，不冒充对底层实际执行模型的独立证明；缺失信息允许补登记。
13. **模型选择与提醒**：派发前，pipeline 根据适用模型路由规则和 Owner 本次明确要求，向主控推荐并提示模型与推理强度；主控自行选择调用方式，并填写本次使用的模型名称和推理强度。填写既保留记录，也提醒主控核对选择；不增加派发后强制模型核验。
14. **代理续用与替代**：默认推荐续用原实现者或原审阅者；代理不可用或上下文不可信时，主控可安排替代者，记录原因、新旧关系与必要交接依据。审阅者需保持独立；新组确认继续遵守现有新组规则。
15. **审阅后改动**：pipeline 对比固定审阅对象与新版本，标出需要判断影响的范围；负责人决定复用或复验并记录依据。新增或无法归属的改动保持待审；最终包级终审按现有规则覆盖最终实现版本。
16. **Ticket 状态归属**：Ticket 验收状态继续由现有 package engine 管理，pipeline 消费并展示其状态；不为 pipeline 另造一套 Ticket 完成条件或验收状态。审阅流程的记录与覆盖需求仍保留，具体如何与现有 engine 接通待设计。
17. **进行中的包接入**：从当前真实进度接入，读取已有 Attempt、Ticket、trail、审阅与证据；可靠关联的沿用，缺失部分待核实并可补登记。不能证明的部分不自动算完成，只限制受影响的收口；无需重做有可靠依据的工作。支持的历史格式以现有引擎实际能力为基础，具体兼容策略待设计。
18. **Plan 瘦身原则**：Plan 保留本包特有的依赖、共享资源、特殊集成顺序、验证入口和特殊风险；通用流程由 pipeline 提供。现有强制字段逐项核对，确属重复通用流程的才考虑删除并同步调整校验。
19. **流程骨架**：包级主线协调 Ticket 推进与整包收口；Ticket 级消费现有依赖和状态，安排工作与审阅；审阅循环接入已有 do-review 轮次状态。多票与多个审阅批次可以并行。
20. **从根部剪枝**：讨论或新增流程规则、状态、字段和门禁前，先判断该问题能否通过明确现有职责、复用现有状态或删除重复流程从根上解决；只有解决实际遗漏所必需的部分才继续下钻。遇到细节分支持续膨胀时回到整体目标和主线收窄，而不是不断增加状态与例外。
21. **组件职责方向**：开发 pipeline 是主控流程入口，统领包级、Ticket 级和审阅循环；package engine 保持 Ticket、依赖、证据和 Gate 事实与校验；do-review 保留审阅方法、审阅轨和现有轮次规则；dispatcher 负责实际派发、续用、返回和资源协调。`dev-with-track` 的跨阶段管理与 `situation` 的下一步流程判断逐步归入统一 pipeline；具体归并方式及现有独立调用路径仍需核实。
22. **统一流程定义**：参考 kickoff，开发 pipeline 使用一份统一流程定义描述包级主线和阶段调用的能力；审阅循环引用现有审阅状态机，不重复定义其轮次、finding 和换组规则。流程定义须支持多 Ticket、多审阅批次并行；不预先限定文件格式或复制 kickoff 的线性模型。
23. **独立审阅入口**：`do-review` 仍可在实施包外独立用于 PR 或代码审阅；实施包通过 pipeline 接入同一套审阅能力。
24. **状态自动更新，行动由主控决定**：已有步骤完成后，pipeline 消费已有权威记录，自动更新当前状态并展示可选下一步，主控无需为同步状态额外执行 `advance`。是否以及何时执行下一步由主控决定；实际派发、分诊和内容判断由相应负责人执行并登记。信息缺失时标待确认并允许补登记，不推断已完成。
25. **必须接通的审阅流程**：审阅轮次与分诊结果要接通；组合审阅要能够关联多个真实执行返回。两项均纳入本次 pipeline 方案，沿用上述现有状态与内容判断边界。
26. **每包属性与持久化**：参考 kickoff，将共享流程定义与每个实施包的运行属性分开；本包模型路由、agent 池等需要跨会话保留的信息由 pipeline 恢复和使用，其他类似属性也遵循相同原则。已有权威记录继续复用，具体文件或存储方式待核实后选择，不重复维护 Ticket 等状态。

## 工作术语

- **Attempt**：实施包的一次执行与 Gate 生命周期；包级终审与最终验证属于整包收口。
- **Ticket**：包内可独立跟踪的交付与验收单位；依赖有 `implementation`、`acceptance`、`release` 类型。
- **执行返回**：一次已派发工作的结果；可能包含可归因的改动和验证结果，单次返回不能自动代表整票完成。
- **审阅批次**：主控选定的一组待审改动及其固定审阅范围；可包含多个执行返回及多张 Ticket。
- **审阅组／轮次**：审阅批次内由现有 review 规则管理的审阅与 finding 闭环。这里的归属关系和正式字段尚待核对现有 ReviewRun 模型，暂不预设存储结构。

## 流程草图（待逐项确认）

```text
包级：接入 / 恢复 → Ticket 并行推进 → 整包终审及问题闭环
     → 确认最终实现版本 → 最终 Journey / Required Suites → Gate

票级：按依赖安排工作 → 消费执行返回 → 按需组合审阅与验证 → 满足 Ticket 验收

审阅：固定实际范围 → 开轮并收齐各轨 → 关轮并统一分诊
     → 修复 → 复验 → 按现有规则换组确认 / 收敛
```

票级工作不必全部处于同一阶段；测试与审阅可以并行，审阅期间返回的新改动不自动纳入已固定的范围。流程图是讨论草图，具体过门条件、状态反转、审阅组适用范围和 Gate 先后仍需逐项核实。

## 统一流程定义与运行视图

### 流程定义

流程定义是主控的流程地图：声明包级主线、阶段需要调用的能力和阶段之间的衔接，供 pipeline 输出当前可做事项和提醒。它不承载每个包的 Ticket 图或业务合同；这些继续从已批准的实施包读取。审阅的组、轮次和 finding 规则继续由现有审阅状态机表达，流程定义只指向这项能力，不复制其转移表。

当前包级主线：

```text
接入 / 恢复 → 推进 Ticket → 包级终审及问题闭环
           → 最终版本验证 → Gate → 收尾
```

`推进 Ticket` 中有多条并行工作，Ticket 的验收状态和依赖由 package engine 提供；审阅批次可跨 Ticket，作为独立进行中的审阅流程展示。包内每次集成后按现行 Journey 验收规则走查当前可达路径，后续变更按影响范围复测或沿用证据；这些渐进走查帮助发现问题，最终版本仍需终审闭环后取得最终证据。主控在可做事项中选择工作和代理；dispatcher 负责派发及返回；pipeline 串联各能力并提示实际欠项。包内工作集成与合入目标分支分别展示：目标分支遵循现有默认 gate-before-merge 和已批准的例外；该主线不要求所有 Ticket 同步进入同一阶段。

### 状态从哪里来

| 信息 | 来源和职责 |
| --- | --- |
| Ticket 状态、依赖、证据和 Gate | package engine 和其现有权威记录；pipeline 消费结果，不重定义验收。 |
| 审阅范围、组、轮次和 finding | 现有 review ledger / rounds 及相关记录；pipeline 接入审阅状态与下一步，不复制审阅转移规则。 |
| 派发、执行返回和代理身份 | 已有 dispatcher／trail 回执及必要的代理记录；缺失且无法推导的事实按需补登记，具体存储待设计。 |
| 主控当前工作视图 | 由已有事实和统一流程推导；区分可安排、进行中、待判断与局部阻塞，不能用静态建议代替主控判断。 |

确实不能从原有记录恢复的关联（例如跨 Ticket 审阅所覆盖的返回、可续用 agent 的身份）需要先核对现有字段，再决定最小补充；不能假设现有字段已覆盖全部宿主。

### 每包配置与其他持久化

参考 kickoff 的共享 `pipeline.json` 与每包 `kickoff-state.json` 分工，开发 pipeline 也区分**共享流程定义**与**每包运行属性**。共享定义描述通用阶段和能力；每包属性保存该包实际选择并需要跨会话恢复的配置。推荐使用同一套入口管理，但不预设必须创建独立状态文件：先检查现有 package state、trail 和 review 记录的实际合同，已有权威记录直接使用；只为无法由已有记录可靠恢复的属性补充包内持久化，并保证每项事实只有一个权威来源。

每包属性至少覆盖模型路由建议（按职责的模型名称和推理强度）和 agent 池（角色、范围、宿主返回的 agent/session ID 与主控填写的本次配置），供派发前提示和后续续用。用户明确指定优先；其次使用该包已登记配置，再参考实际可用的既有默认规则。不能假定各宿主都能自动读取会话记忆；获取不到时主控填写，记录后由该包后续恢复。模型/强度是自填配置，不作派发后强制核验。

同理，包级流程选项、派发及审阅之间不可推导的关联，应按实际需求登记并恢复；审阅轮次、Ticket 状态、依赖、证据与 Gate 若已有权威记录，就引用原记录，不再复制一套。包配置可由主控在工作中调整，新的推荐使用更新后的值；历史派发保留当时填写的配置，不因修改默认值而改写。不同包的属性互不覆盖；新增属性和具体存储形状须在核实现有能力后确定，不预先要求每次任务重新填写一套通用信息。

### 状态自动更新

pipeline 在查看状态、消费返回或恢复时读取现有事实，自动更新哪些步骤已满足及可选下一步；不要求主控再额外标记一个与已有事实重复的阶段。主控根据情况决定是否以及何时执行下一步；自动更新状态不代表自动派发、审阅、分诊或作内容判断。实际行动及其结果由相应负责人执行并登记，不得从缺失记录推断步骤完成。

例如审阅轮次的各轨结果登记完毕、该轮按既有规则关闭后，pipeline 显示“待主控统一分诊”；原实现者返回修复且已有记录后，显示“待原审阅组复验”。审阅过程和 Ticket 状态仍来自各自已有的工具；其他不受影响的 Ticket 可并行推进。

### 运行示例

1. 主控接入获批的包，pipeline 展示 Ticket 状态、依赖、已登记代理与现有审阅事项。
2. T01 和 T02 可推进，主控选择并通过 dispatcher 派发。每个真实返回关联到其 Ticket 和执行者；主控可以将两张票的返回组合成一次审阅。
3. 该审阅批次固定实际已集成版本或隔离快照，开轮并等待已登记审阅轨；收齐关轮后才统一分诊。审阅未完成期间其他无关 Ticket 继续。
4. 修复和复验按现有审阅循环推进，主控优先续用原实现者和审阅者；测试可以并行。pipeline 展示审阅状态、原角色及待办。
5. package engine 根据其现有合同提供 Ticket 和 Gate 状态；pipeline 按包级主线引导最终审阅与验证。已有进行中的包按真实事实恢复，缺失信息标注并可补登记。

此例只描述流程衔接，不替代 Ticket 验收规则，也不声称当前 CLI 已支持整条示例。

## 最小闭环与现有能力归并（方案草案）

主控只需要一个入口完成四类动作：接入或恢复实施包、查看当前工作视图、选择并执行实际工作、登记已有结果或补登记。pipeline 每次依据当前权威事实更新状态和候选；实际是否继续、派谁、如何分诊由主控决定。这里是操作职责，不预设具体 CLI 命令或宿主接口。

围绕该闭环，现有内容的建议归并如下：

1. **一份流程定义**：提供包级主线与调用的能力；以现有 `situations.yaml` 的动作、依赖与阻塞判断为输入梳理，删去重复主线，而不是新增另一套与原表并行的判断。
2. **一次事实读取与状态推导**：复用 `situation.py` 已有的状态快照和候选推导能力；pipeline 将 Ticket、审阅及代理事实组成主控视图。其内部职责与接口可按归并需要调整，不预设原文件整体保留或删除。
3. **审阅循环沿用原能力**：pipeline 衔接 `do-review` 及 `review_rounds.py`，取得当前组、轮次和欠项，不复制审阅组状态机；包外独立审阅继续使用相同能力。
4. **状态写入复用原入口**：Ticket、evidence、Gate 继续调用 package engine；派发和返回复用 dispatcher／trail。`cmd_trail.py` 的派发准入当前依赖 `situation.dispatch_admission`，归并时须使其继续消费同一流程判断并保持现有约束。
5. **清理主控入口**：将 `dev-with-track` 中与 pipeline 重复的跨步骤流程从原入口移出；业务判断、package 合同和实际需要的审阅方法仍有明确归属。是否保留旧入口或以何种方式兼容，待核对实际调用后决定。

### 已识别的接缝

- **组合审阅需要调整现有记录合同**：当前 `cmd_trail.py` 的 review dispatch 以单个 `reviews` 返回 ID 绑定 `code_delta`，并校验 dispatch subject 与该返回相同；不能直接认为它已经支持一次审阅覆盖多张 Ticket 的多个返回。需要在统一流程接入时扩展或重新组织该关联，同时保留可归因性；具体形状待设计。
- **agent ID 与模型记录需要补齐**：现有 trail 有 worker 和 receipt，部分审阅脚本另存 session ID，但尚未确认统一覆盖所有宿主；先复用可获得的身份与模型事实，缺项允许补登记，不推断未知字段。
- **已有包从实际状态恢复**：消费既有 package state、trail 与 review 记录；不可可靠关联的部分明确标待确认。恢复不自行宣称审阅或验收通过，独立工作继续。

落地后的最小验证应覆盖：两张 Ticket 并行、多个返回跨 Ticket 组合审阅、同轮收齐后分诊与复验、agent 续用与缺失身份补录，以及恢复已有包时状态自动更新。还须核对现有依赖准入和 Gate 合同保持有效。以上是设计验证目标，尚未执行。

## 推荐方案（待用户整体确认）

### 1. 一个入口、一个流程判断来源

推荐在现有 `impl-package` 中建设开发 pipeline，沿用 `dev-with-track` 的实施包入口，入口内部切到统一流程定义与流程服务；`dev-loop` 的包外轻量开发用法继续存在，包内流程部分不再另发明第二条主线。`do-review` 的包外审阅入口仍可直接使用同一审阅能力。具体文件名不是对外合同，实施前核对所有调用者和宿主入口。

统一流程定义只描述包级主线、各节点对接的能力及必要流程约束，Ticket 图取自已批准的 package，审阅组转移来自已有审阅状态机。多票和多审阅批次同时运行，不用一个可变的全局阶段强制串行。现有 `situations.yaml` / `situation.py` 中属于流程推导的规则归并为该流程判断的唯一来源；已有 `dispatch_admission` 的调用仍连接到同一判断，迁移期间不得一份用于展示、另一份用于实际准入。

### 2. 实际工作方式

主控通过统一入口完成接入或恢复、查看状态、选择并安排工作、登记结果或补登记。入口应支持人可读视图和结构化输出；命令名称和参数由实现设计确定。每次读取或完成一次成功操作后，从权威事实重新计算包级及各 Ticket 的状态、在途工作、审阅组下一步和局部阻塞。状态自动更新；真实行动由主控决定，工具不会因为状态变化而自行派人、作业务判断或执行 Gate。

视图区分可安排、进行中、待主控判断、局部阻塞及信息待确认，并给出涉及的 Ticket、审阅批次和可续用代理。优先复用现有 situation 的 `blocking`、`runnable`、`withheld`、`in_flight`、`manual` 和 `undetermined`，避免另造同义状态。它是流程辅助，不声称枚举了主控可发现的全部业务工作；缺失、读失败和不适用保持可区分，不把 unknown 当作完成。主控可以并行选择互不阻塞的工作。

CLI 写入成功后刷新视图；会话进入、恢复、外部发生不明变化或写入失败时重新读取权威事实。现有 SessionStart Capsule 只提供可能被截断的恢复摘要，并非实时订阅；初版不为自动更新另建后台常驻服务。候选和提示基于读取时的快照，真实派发记录继续检查最新准入；主控判断实际授权和资源。

### 3. 事实所有权与记录

- package engine 继续是 Ticket、依赖、evidence 和 Gate 的语义入口；pipeline 读取与调用，不维护平行的 Ticket 完成状态。
- review ledger 与 rounds 继续负责固定审阅对象、轨道、组、轮次和 finding；pipeline 读取并衔接这些状态。包级 terminal-final 及其现有 coverage 事实仍须按现有合同登记，不能把局部复验当终审。
- dispatcher 和既有 trail 继续记录真实派发及返回；新增跨 Ticket 审阅覆盖关联和可续用代理信息时，优先扩展现有事实，不复制已能可靠推导的状态。主控填写本次选择的模型名称与推理强度，记录角色和宿主可提供的 agent/session ID；缺失信息允许补登记。该填写是自报的派发配置，不作派发后的强制核验，也不冒充底层实际模型的独立证明。现有 `worker`、`candidate_id`、`dispatch_id` 和 receipt 不能一概等同于可恢复的宿主 agent ID。
- 流程状态视图由这些事实推导。若确有无法从现有记录恢复的关联，只保存该关联本身及必要来源，不保存另一份独立事实副本。

### 4. 组合审阅和后续修复

主控从真实返回中选择一个或多个组成审阅批次，允许跨 Ticket；固定实际送审对象（已集成版本或隔离快照）及本次覆盖的返回。建议复用现有 ReviewRun，在现有 trail 中追加与真实派发、ReviewRun 和多个 return 的关联；每个 return 的 Ticket、delta 和消费标识从原记录取得，不另造一组可能相互矛盾的事实。旧单返回 `reviews` 记录继续可读并沿用。补登记时不伪造原事件的时间或 receipt，重复相同关联应幂等，冲突需报告。

当前 `situation.py` 的待派审推导和 `dispatch_audit.py` 也按单返回匹配；要同步调整这些消费者，避免组合审阅已真实派发但仍显示每条返回都未派审。已有代码返回时，统一入口在消费返回的同一流程中复用现有 `review.dispatch_pending` 登记待审，允许主控等待其他返回后合并派审；实际组合派审后，既有视图按关联消除对应欠项，保留各返回和独立性核对，不因等待其他票而阻塞无关工作。

已派审、审阅完成和审阅通过分别表达；仅有关联不等于通过。送审对象范围须经可检查的范围证据与主控核对，不能仅凭 return ID 或提交祖先关系直接宣称覆盖；不能证明的标待确认。组合审阅关联无论采用扩展 dispatch 还是既有 trail fact，均须被活动及归档 trail 的恢复读取和审计一致消费；现有 situation 归档读取会过滤部分 fact，须同步调整并测试轮换前后可恢复。

该批次的同轮审阅轨全部返回并关闭后，主控统一分诊并安排修复；仍按既有组内复验和新组确认规则运行。`review_rounds` 的关轮或 group status 只能反映轮次记录，不能单独证明本轮完成分诊、全部所需轨结果有效或已经收敛：pipeline 必须结合该轮实际轨道结论、canonical ledger 和已完成的 canonical summary 后才展示可换组或已收敛；信息缺失、`UNCERTAIN` 或 `INCOMPLETE` 保持未完成，不以无 finding 代替 PASS。现有 summary 以 ReviewRun、phase、head 标识，需在既有审阅记录中补充或复用足以关联具体组与轮次的标识，避免把其他轮分诊当作本轮完成；不复制一套 finding 状态机。

分诊中断恢复时先读取本组本轮的已写 finding 和 canonical ledger，再继续未完成的采信、分诊与 summary；不重新盲目执行整轮 `triage add`。在现有分诊记录上复用 canonical `findingKey` 与组／轮次关联，使相同 finding 的重复登记返回原结果，冲突则提示主控处理；不另建 finding 表。旧记录缺少可靠 key 时由主控对照并补登记，不凭相似文案自动合并。summary 完成与否仍按该轮真实记录判断，避免把部分分诊当作完成。

当正式组合审阅满足某张 Ticket 的现有 required review 要求时，主控核实审阅结论和该票实际覆盖范围并选择登记，pipeline 通过现有 `evidence add` 为该票关联可用审阅证据；同一报告可作为多票的证据来源，但按票独立核对适用审阅要求、范围、版本和未关闭 blocker。覆盖不足的票继续显示欠项；pipeline 不代替主控判断审阅内容，也不另设 Ticket 完成条件。

隔离快照的采信以**集成版本**为落点：保留真实受审的快照 SHA、ReviewRun 和原报告，主控按票核对该票的受审改动、适用合同与集成版本；核对范围及等价依据写入包内证据附件。确认等价后用当前项目仓库可解析的集成 commit 登记该票 review evidence，附件同时指回真实受审快照，不改写报告中的 reviewed-head。若内容或合同差异影响该票，或无法证明等价，该票继续待审并复验受影响范围，其他可采信的票照常推进。不能把隔离仓库独有的 SHA 直接当作项目版本，也不假定现有 carry-forward 支持非祖先快照；包级 terminal-final 仍按现有最终实现 HEAD 合同执行。

修复关联原 finding 和执行者，优先续用原执行者及原审阅者；不适合续用时记录替代及交接。后续版本变化时，根据固定审阅对象对比，提示负责人判断哪些原结论可复用、哪些需复验；未关联或未确认的改动不自动计入已审。其他独立 Ticket 和审阅批次不因此停下。

### 5. 接入、恢复与例外

新包从已批准的 Plan 和初始化后的 package 状态接入；进行中的包从当前 Attempt、Ticket、trail、review 与现有证据恢复。可靠事实沿用，缺项标待确认，主控可补登记并提供依据；不凭空补造审阅或执行结果，也不为缺少额外元数据强迫所有工作重来。旧格式以 package engine 实际支持范围为准，不暗示新增旧格式迁移支持。

实际派发成功但登记失败时，恢复流程先核对宿主回执和已有记录，再补记原派发，不重新派一个替代实例。由于普通 `trail append` 重新检查当前 Ticket 和 lease，历史派发可能因其后状态变化而被拒：在现有 trail writer 上提供仅用于**补记已发生派发事实**的恢复入口，以原 dispatch ID、证明宿主已受理的真实回执及可核实归属登记原事件；真实回执暂缺时保留待确认并允许主控补充，不用其他材料伪造 receipt。按既有记录校验同 ID 是否相同，重复幂等、冲突提示主控，不伪造发生时间或另起一个 dispatch。它不要求现在仍持有原 lease 或 Ticket 仍为当时的状态，也不启动 worker、不允许据此发起新工作；新派发仍执行现有准入。当前 Attempt 的可写与终态边界继续由现有 engine 管理。

`review.canonical_summary`、组合审阅关联及其引用的原派发／返回需同时能从活动和归档 trail 恢复；现有 situation 归档过滤需覆盖这些被统一视图消费的必要事实，并与审计使用相同历史来源。权威来源不一致或状态无法读取时，标出涉及对象、事实来源和待核实事项；只限制依赖该事实的动作，其余合法工作继续，终态声明仍遵守现有 Gate。

### 6. Plan 瘦身与迁移

Plan 继续提供本包的依赖、共享资源、特殊集成顺序、验证入口和风险；通用开发及审阅循环由 pipeline 提供。现有 `impl-planning` 已要求不复制通用 checklist；针对它仍要求的固定字段和现有 parser，先逐项找实际消费者，再移除真正重复的通用流程，不删除包内专属事实或改变已批准合同。

实施先固定现有入口及状态合同，在现有 `dev-with-track`、situation 与 writer 上优先跑通一条小包纵向链：代码返回 → 记录待派审 → 审阅收齐并关轮 → 分诊及复验 → 对适用 Ticket 登记 review evidence → 包级 Gate。以此核实确实减少主控对账，再归并流程定义与视图，补齐跨 Ticket 多返回、代理身份、恢复和现有入口，并更新 `dev-with-track`、`do-review`、`dev-loop` 及 Plan 指引。第一条链只是验证入口，最终交付仍覆盖完整推荐范围。每一步保持同一权威判断和可用入口，完成后删除被替代的重复流程。`dev-loop` 在当前仓库无已跟踪源码，实施时先核实其源码位置及授权，不能直接改用户宿主缓存或把它当作本仓库文件。

### 7. 完成标准与验证

对同一实现运行聚焦测试和隔离示例，覆盖：单 Ticket 小包完整流程及包内集成后的阶段走查；双 Ticket 依赖及并行；跨 Ticket 多返回组合审阅及逐票审阅 evidence（含隔离快照到集成版本：一票等价可采信、另一票存在差异待复验，并保留真实 reviewed-head）；等候合审时待派审记录；关轮后已登记部分 finding、summary 未写时中断恢复不重复登记，fresh group 含 `UNCERTAIN` 且无 accepted finding 不得误报收敛；修复、原组复验及新组确认；组合审阅关联与 canonical summary 跨 trail 轮换后的恢复；按包保存并恢复路由属性、实际 agent ID 与主控填写的模型／推理强度，跨包隔离、更新配置不改写旧派发及缺项补登记；原派发已成功但记账失败，且 Ticket 状态或 lease 已变化时历史补记与后续返回可关联、不重复派发，新派发仍受原有准入；模型入口不支持指定推理强度时主控如实填写；未知状态与不相关工作并行；既有单返回数据、旧审阅入口、依赖准入、包内集成与目标分支合入边界及 Gate 合同。终审闭环后在最终版本取得最终证据；测试验证流程和记录，业务判断仍由人负责。

设计验证需先静态对照已确认方向、现有规则和调用者，再用真实形状的脱敏或隔离 fixture 演练，标明哪些步骤尚未运行。具体迁移命令、跨宿主标识获取方式及受影响测试由实施计划确定，不能用示例冒充已验证事实。

## 实施前需核实的事实

以下是落实推荐方案需要取得的事实，不视作已通过验证，也不自动扩大设计范围：

- **覆盖与调用者**：核对 review ledger、trail、`situation.py`、`dispatch_audit.py` 与所有相关消费者，确定多返回关联的最小存储形状和审阅范围证据；历史单返回继续可读。已有 ReviewRun 的 base/head 不单独证明每个返回都已被实际审阅。
- **跨宿主身份**：按需核实所用宿主返回的 agent/session ID 及续用方式；拿不到时允许补录，不把代理昵称或 receipt 自动当作 ID。模型与推理强度由主控填写所选配置，不要求宿主提供底层实际值。
- **现有包与失败恢复**：以现有支持的 package 格式和当前状态为入口，验证恢复、补登记、重复记录及已真实派发但未记账的情况；不推断没有证据的历史，不擅自重派。
- **现有验收状态变化（此前 Q9）**：Ticket 完成后的代码或合同变化先沿用现有 engine 的状态及证据失效机制和主控影响判断，pipeline 消费结果；不在设计中另造一套 Ticket 状态。是否需要调整现有机制，只在真实接入暴露不足时依据影响再处理。
- **现有 Plan 消费者**：核对 `impl-planning`、parser、Gate、验收和实际样例，区分本包特有信息与重复流程；未核实前保留现有必需字段。
- **入口和测试**：核对 `dev-with-track`、包外 `do-review`、各宿主及 `dev-loop` 的实际安装来源与调用方；明确受影响的现有聚焦测试。审阅轮次可从 `skills/do-review/tests/test_review_rounds.py` 对照，其他测试入口需按实际仓库核实，不以猜测路径代替。

这些核查纳入实施计划和验证，不需要在讨论中为每个字段再作 Owner 决策。推荐方案不改变既有业务合同或 Gate，不声称当前代码已支持新流程。

### 模型路由：推荐、提醒与自填

Owner 已明确采用轻量方式：派发前提示适用的模型路由规则和本次指定要求，由主控自行选择调用方式，并填写本次使用的模型名称与推理强度。例如 Owner 指定 DeepSeek、高推理强度时，提示该要求；主控选择能指定该强度的宿主入口并填写 `DeepSeek / high`。若所选入口不能指定强度，则如实记录强度未指定或未知，主控可自行更换入口或补充说明；不把要求值冒充所选配置。填写动作帮助主控在派发时主动核对，也让后续恢复能看到所选配置与 agent ID。

该记录是主控自报的派发配置；pipeline 不增加派发后的强制模型核验，也不声称自报内容证明底层实际执行模型。缺项允许补登记；若另有可信的实际模型信息，可如实记录而不增加专门检查流程。不要把代理别名或 receipt 推断为底层模型证明。

建议聚焦验证：本次指定能出现在派发前提示；主控填写的模型、推理强度和 agent ID 可以随工作记录查看与续用；缺项可补登记。上述是拟实现能力，当前尚未实现或运行测试。
