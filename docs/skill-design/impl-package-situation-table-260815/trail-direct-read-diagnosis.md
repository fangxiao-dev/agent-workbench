## 口径和判定方法

统计对象是 rollout 中真正让主控读取或搜索目标文件的动作：`Get-Content`、目标文件上的 `Select-String`、目标文件上的 `git diff` 等。一个 PowerShell 管道中的同一次目标文件读取计一次；同一个 `exec` 调用中出现两个独立的 `Get-Content`，计两次。提示词、助手文字、patch 字符串中出现的路径，以及 `Test-Path`、`Get-Item`、`git status` 等没有读取文件内容的动作不计入。渲染器或 CLI 内部为自身工作读取 trail，也不冒算成主控直接读取。

目的不是从命令名猜，而是看读取前后的 rollout 上下文：

- 读取紧邻“写入这次结果/记录 checkpoint/dispatch 下一步”，并取得尾部 1～几行或转换成 JSON 的，归入“追加边界确认”。这类读取的共同问题是“现在最后一条是什么、下一个 `seq` 应是多少、这次追加是否接在正确位置”。这里把写后马上核对也并入同类，因为它服务于同一个追加边界。
- 读取后紧接着选择 worker、判断是否继续 polling、决定恢复/下一 seam，归入“读来判断”。大尾部读取不自动等于历史浏览；如果它是为了恢复当前上下文，也仍按判断计数。
- 读取发生在测试失败、渲染异常、坏 fact、重复 `seq`、迁移/集成阻塞或证据审计附近，归入“校验/排错”。`Select-String` 查 schema/focused 等关键词、逐行检查序号和 `git diff -- trail.jsonl` 都属于此类证据核对。

这是基于上下文的归因，不是轨迹中已有的 `purpose` 字段。因此有少量边界不确定性：`01a00f08/e400` 既可能是恢复判断也可能是迁移排错；`01a0101a/e1605` 同时服务于“调查下一步”和失败诊断；`01a010e6/e3314`、`01a011d0/e3684` 同时接近写后确认和 handoff 重新定向。这里按紧随其后的主动作归入一类。把这些边界项移动到相邻类别会改变少量分类数，但不会改变 115 次总量，也不会改变 `01a011d0` 以追加边界读取为主的结论。

`01a011d0` 的 77 次中，事件级证据可以压缩为：

- 追加边界确认 56 次：集中在 `e329,e765,e1752,e1833,e1837,e2022,e2032,e2154,e2169,e2255,e2265,e2336,e2346,e2397,e2520,e2723,e2732,e2738,e2905,e2909,e2913,e2921,e2945,e3059,e3066,e3150,e3313,e3332,e3438,e3464,e3605,e3697,e3783,e3803,e3957,e3973,e4102,e4278,e4291,e4426,e4528,e4623,e4692,e5136,e5343,e5434,e5469,e5710,e5761,e7298`。其中 `e2905,e2909,e2913,e2945,e3059,e3066` 各有两个独立的尾部读取，所以事件数少于读取数。
- 读来判断 11 次：`e167,e266,e1269,e1737,e2464,e3181,e3684,e4840,e5243,e5588,e7220`。
- 校验/排错 10 次：`e3194,e3264,e4949,e4953,e5150,e5922,e7064,e7068,e7114,e7311`。

## 全文还是局部

按命令形态，115 次可拆成：

| 读取形态 | 次数 | 说明 |
|---|---:|---|
| 全量取出/全量解析 | 12 | 没有 `-Tail`/`-First`，或把整个文件转 JSON、计数、逐行扫描 |
| `-Tail`/`-First` | 99 | 绝大多数是尾部 1～几行；少数是首尾各取一段 |
| `Select-String` 目标文件搜索 | 3 | 输出被过滤，但底层仍可能扫描全文件 |
| `git diff -- trail.jsonl` | 1 | 比较目标文件，不能视作只读最后几行 |
| **合计** | **115** | |

所以若只问“返回给主控的内容”，是 12 次全量、103 次局部/过滤/差异结果；若问“底层是否可能扫过全文”，严格说不能把后 4 次算作局部。12 次全量读取是：

- `01a00deb`：`e352,e2682,e2702` 的第一处读取、`e2723,e2728`；
- `01a0101a`：`e1053`；
- `01a011d0`：`e3264,e5150,e5922,e7064,e7068,e7114`。

其中 `e7064/e7068/e7114` 的输出用了 `Select-Object -Last`，但输入仍是没有 `-Tail` 的 `Get-Content`，因此按“读取源文件”归为全量扫描。`e147`、`01a011d0/e3194` 和 `e7311` 是内容搜索，`01a00deb/e2838` 是 diff；它们都不是安全的尾行读取。

## 为什么 `01a011d0` 是 77 次

### 不是轮换本身，而是轮换之后的高密度推进循环

在该实现包的 execution 目录中，轮换证据明确存在：

| 文件 | 大小 | 观察到的内容 |
|---|---:|---|
| `trail.001.jsonl` | 82,635 bytes | 早期归档，覆盖旧序列 |
| `trail.002.jsonl` | 829 bytes | 2 行，`seq` 30～31，包含 handoff/checkpoint |
| 当前 `trail.jsonl` | 193,404 bytes | 从 `seq` 32 开始的活动文件 |

轮换/hand-off 把活动文件切换到新的 `trail.jsonl`，但 77 次读取本身主要发生在这个活动文件上。`situation.py` 的渲染路径也只读取当前活动 trail，不把 `trail.001.jsonl`、`trail.002.jsonl` 作为主控每次读取的历史源。因此“有轮换”解释了为什么看到 archive 和新的序列起点，却不能解释 77 次直接读。

该 session 的命令参数中还出现了 55 次 `recovery checkpoint` 和 16 次 `recovery judgment`，合计 71 次状态/轨迹推进相关 CLI 调用；另有 4 次 `package validate`。这与大量 worker dispatch/return、review、repair、checkpoint 和结果追加交织在一起，形成了反复的“先看尾部/序号，再追加下一行”的循环。`e2905/e2909/e2913/e2945/e3059/e3066` 中一次主控调用就各做了两次独立尾部读取，是这个模式的直接证据。

相比其它 session，`01a011d0` 有 1,534 次 custom tool call、193 次 assistant turn、8 次 compaction；其它五个 session 分别只有 1～12 次 trail 读取，assistant turn 为 48～88 次。它还经历了多轮 review `REVISE`、修复、重新 review、迁移/集成阻塞和证据/序号审计。因而 77 次是长流程和高频状态推进的结果；轮换只是边界条件，不是数量级差异的根因。

### 统计边界提醒

上一轮统计把 `01a011d0` 截止到事件 `e7311`，所以主表严格沿用 77 和总计 115。当前 rollout 文件在该边界之后还出现了同类目标读取：`e7590`、`e7699`、`e7892` 各一次。如果把整个当前 rollout 继续计入，则该 session 是 80 次、六个 session 是 118 次；这 3 次没有混入本报告主表。`git diff --check` 也仍按上一轮规则排除，因为它只是校验命令，不是读取文件内容供主控消费。

## 渲染器缺什么，能消掉多少次

当前 `situation.py render --json` 已经提供 `digest`、`head`、选中的 action、并行匹配、`undetermined/unmatched` 以及若干派生的 `trail.*` 判断值；`sources.trail` 实际只给出 `path`、`present`、`error`。它没有把“活动 trail 当前最后一行”或可供追加的序号锚点输出给主控。

最有覆盖面的缺口是一个紧凑的追加上下文，至少包含：

```text
last_seq / next_seq
last_event: kind, subject, outcome, id/of, worker, head, ts
last_event 中的 checkpoint/next/blocker（若存在）
```

或者提供等价的结构化最后一行。这样主控为确认“最后一行、格式、当前 `seq`、下一次追加位置”而做的 66 次追加边界读取，都有可能直接从渲染结果取得；这正是本次统计中理论上可消掉最多的一组，数量是 **66 次**。它不能替代 20 次排错读取，因为排错需要原始行和具体证据；也不能自动替代全部 29 次判断读取，因为其中一些需要最近多行历史，而不是单个追加锚点。

因此，本轮诊断的最大可归因收益是：渲染器补“最后事件 + `last_seq/next_seq` 的追加上下文”，对应 66/115 次（57.4%），而不是补一个完整 trail 副本。
