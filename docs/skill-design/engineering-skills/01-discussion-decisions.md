# 工程决策 Skill 体系：需求输入与决策演变

> 讨论记录｜2026-11-20｜状态：方向已收敛，尚未进入 Skill 实现
>
> 本文记录这次讨论如何从一段视频发展为三个协作的 Skill，以及每个决定背后的理由。它不是 PRD，也不替代三份设计初稿。

## 1. 起点：需要工程直觉，而不是更快的方案生成

最初输入是一段讨论工程直觉、技术搜索与剪枝的视频，以及文章 *Technology as a Search Problem* 的启发：技术工作存在大量潜在组合，关键在于识别约束、搜索有效路径，并尽早排除没有价值的分支。

最直接的痛点出现在需求讨论阶段。面对「需要多端实时同步」「需要一个复杂 Agent」「需要处理某个罕见状态」这样的表述，Coding Agent 容易默认需求成立，直接开始拆解实现。工程负责人应先判断：这个场景真的需要支持吗？谁需要它？做到什么程度？能否改变业务约束，从源头删掉一类复杂度？

因此，最初提出的 Skill 应使用启发式语言，与开发者共同判断需求和架构责任。它不应该机械列清单，也不应该一上来就输出实现路线。

**第一阶段形成的要求：**

- 提问要有信息价值：优先追问会改变决策的事实。
- 允许挑战需求本身，考虑不做、推迟、缩小范围、改变规则。
- 将业务目标与技术代价放在同一次讨论中。
- 评估实际风险和必要约束，避免为了简化而删掉正确性要求。
- 讨论应根据问题规模收放，避免日常小改动被流程拖住。

## 2. 第一次拆分：判断与实验分别承担不同工作

随后提出第二种能力：当工程方案的边界不确定时，不必全靠讨论，可以用很小的脚本、模拟环境、压力测试、故障注入或技术切片，提前重现接近真实的条件。

这个方向与第一种能力有关，但工作形式不同。一个负责回答「值得做什么、做到哪」，另一个负责回答「目前的技术假设是否成立」。因此决定暂时拆成：

- **Engineering Judgment**：需求和架构层面的价值判断、范围选择、剪枝。
- **Engineering Probe**：用最低合理成本获取能够影响工程决策的证据。

这里明确了 Probe 的原型概念：它面向技术人员，验证容量、失败模式、系统边界或可行性。面向老板或客户的交互 HTML 原型，目的通常是沟通业务行为，属于另一种工作。

**为何拆开：** 技术验证可能涉及运行脚本、消耗资源和修改隔离环境，不应成为每次需求讨论的默认动作。它也需要独立衡量证据质量。

## 3. 第二次拆分：工程判断需要从业务方获得输入

接着出现第三个痛点：开发者可能并不熟悉业务。工程判断一旦涉及真实工作流程、审批责任、异常处理、业务取舍，就需要老板、客户、税务师或业务负责人提供信息。

因此提出 **Business Alignment**：先识别缺少什么业务知识，再决定向谁、通过什么场景和形式获取输入，最后把结果交还工程决策。

这引出了现有 `to-questionnaire`。讨论初期倾向于将它当作 Business Alignment 的下游工具。后来查看 `agent-workbench` 仓库里的实现，确认它已有值得保留的能力：

- Discovery / Decision 两类问卷；
- 稳定题号及来源映射；
- HTML 的本地保存、筛选、答复导出与旧版答复迁移；
- 从收件人视角检查问题是否能独立理解；
- 答案回填到来源材料的闭环。

同时发现限制：当前 `to-questionnaire` 把问题模式与输出载体绑得较紧，例如 Discovery 只能 Markdown、Decision 才能 HTML；固定问卷结构限制了针对业务场景定制交互形式。

**由此决定：** Business Alignment 负责发现知识缺口、组织场景和设计对齐方式；`to-questionnaire` 进一步打薄，把模板、脚本、固定布局降为可选组件和样例。调用者可以指定 Markdown、HTML、流程模拟或其他适合收件人的形式。

`to-questionnaire` 是否保留独立 Skill 入口仍可由实现阶段决定；其生成能力不再主导上层业务对齐流程。

## 4. 第三次调整：工程判断必须跨开发生命周期

之后进一步明确，第一种 Skill 不应局限于需求评审。它要出现在任何值得进行业务或技术取舍的时刻：

- PRD / Spec 之前：判断需求的价值与规模；
- 方案设计时：判断架构责任、抽象、依赖是否必要；
- 实现与 Code Review 时：遇到缺陷，先判断相应状态是否应存在，再决定修复、裁剪或重构；
- 维护和演进时：判断历史决定是否仍然成立，是否需要重新评估。

与现有 `grilling` 的关系也因此明确。仓库中的 `grilling` 擅长把设计展开为决策树，分轮处理完整 frontier，直到重要分支收敛。新 Skill 的职责更上游：判断这个问题值不值得展开、决策空间是否需要先缩小，再决定是否调用 `grilling`。

命名上，原始 `Engineering Judgment` 不够体现资深工程负责人的定位。讨论提出过 `senior` / `tech-lead` / `cto-judge` 一类名称，当前设计稿暂用 **Principal Engineer**；名称尚未被最终确认。

## 5. 最关键的增量：让判断积累在仓库里

用户随后提出，希望它「像一个人一样住在 repo 里」。这意味着它不仅处理单次讨论，还要能够记起过去为什么做或不做某件事，并将这些理由用于后续判断。

现有 PRD、ARD 等长青文档维护节奏不同，不能把每次工程讨论都写入其中。因此提出独立的仓库级 **Decision Memory**，保存有复用价值的工程取舍：

- 当时要解决什么；
- 采用了什么决定，舍弃了什么；
- 为什么；
- 决定依赖哪些条件；
- 何时需要重新考虑；
- 有哪些业务或技术证据。

这里保留一个必要区别：讨论中的建议与已经确认的项目决定不能混存。长期记忆需要识别有效状态与被取代的历史决定，同时避免每次互动都生成一份记录。

**取舍理由：** 提高跨会话的判断连续性，同时避免把 PRD / ARD 改造成高频日志，也避免旧判断长期僵化。

## 6. 当前收敛的体系

| 组件 | 工作对象 | 主要产出 |
|---|---|---|
| **Principal Engineer**（暂定名） | 任何有业务或技术取舍的节点 | 决策、scope、取舍理由、重新评估条件 |
| **Business Alignment** | 缺少可由业务方确认的信息 | 业务场景、对齐材料、确认结果与依据 |
| **Engineering Probe** | 决策依赖未经验证的技术事实 | 最小实验、观察结果、适用边界 |
| `grilling`（现有） | 需要系统展开和收敛的设计决策树 | 逐轮关闭的设计决策 |
| `to-questionnaire`（现有，拟打薄） | 外部对齐材料的生成和回收 | 可填写的问卷／HTML／其他形式 |
| **Decision Memory**（拟新增） | repo 内有复用价值的取舍 | 可检索、可修订的历史决策依据 |

> 第二轮讨论后，`to-questionnaire` 并入 Business Alignment，Decision Memory 成为 PE 在对象项目里的记忆目录，`challenge-the-core` 并入 PE，见第 9 节。

组件之间按需要协作，不构成强制流水线。Principal Engineer 是判断视角，不应成为所有开发动作的审批瓶颈。Business Alignment 与 Engineering Probe 提供两类外部证据，分别来自业务实践和技术实验。

## 7. 已有决定与仍待验证的设计选择

**讨论中已明确的方向：**

1. 三个上层 Skill 分开设计，职责为工程判断、业务对齐、技术探针。
2. 第一种能力跨开发生命周期出现，采用启发式、可收缩的判断方式。
3. `grilling` 保留独立价值，聚焦决策树展开，不与工程负责人角色合并。
4. `to-questionnaire` 进一步工具化，取消对格式和布局的强约束。
5. 工程判断在 repo 内积累决策记忆，尽量不扰动 PRD / ARD。
6. Engineering Probe 先做轻量版本，经过实际使用再扩展。

**设计阶段需要通过案例检验的选择：**

- `principal-engineer` 是否是最终名称，是否需要一个常驻入口而非单次 Skill 调用。
- Decision Memory 的最小文件结构、写入门槛、检索策略与状态更新方式。
- Business Alignment 与 `to-questionnaire` 的接口，以及保留独立入口的方式。
- Probe 如何判断实验值得做、需要多少真实性、何时直接使用已有证据。
- 与现有 repo 开发流程（包括 `AGENTS.md` 和其他 Skill）的触发关系。

## 8. 讨论依据

- 本次对话中对工程直觉、剪枝、技术搜索、业务对齐、原型验证和仓库记忆的逐轮要求。
- `agent-workbench/skills/grilling/SKILL.md`：design tree、frontier、按成熟度收缩讨论范围。
- `agent-workbench/skills/to-questionnaire/SKILL.md` 及其 `references/decision-mode.md`、`references/html-output.md`：现有问卷生成与回收机制。
- *Technology as a Search Problem*：作为设计启发；这里不将文章里的技术研究模型直接等同于软件工程的实践结论。

## 9. 第二轮讨论（2026-11-21）

对照仓库现有 Skill 审读三份初稿后，形成以下决定。

### 9.1 PE 常驻：记忆目录 + 进场规则

最初的顾虑是「Skill 无法常驻」。澄清后：Skill 不会自己醒来，但常驻可以由**项目记忆**和**可靠的进场时机**组成——记忆用 Markdown 即可，与 agent 自身的 memory 机制同构。

- PE 有自己的记忆目录，每次进场先读、决策收口时写回；它消费长青文档和 ADR，自己做笔记、分主题维护入口，类似 hands-on knowledge 的 entry-map。
- PE 不做具体代码检视，管理技术架构、业务决策等上层判断。
- 进场规则写进对象项目的 `AGENTS.md`：主控需要向 Owner 询问业务或架构层面的问题时，先进入 PE，由 Owner 与 PE 共同决策。
- PE 提供 Owner 可直接调用的入口，用于主动讨论、复盘与整理记忆。

### 9.2 记忆归属在对象项目

记忆存放在对象项目里（暂定 `docs/principal/`，随项目提交，多宿主共享）。workbench 中的 Skill 只规定固定的结构与读写路径，不存储任何项目或用户的记忆。

与 ADR 按粒度分工：难以撤销的决定写 ADR（`domain-modeling` 约定），PE 只链接；轻量的「做到哪 / 不做什么 / 何时再议」写入 PE 自己的 `decisions/`。长青文档与 ADR 是事实源，记忆冲突时以事实源为准并交 Owner 决定。

### 9.3 `challenge-the-core` 并入 PE 后删除

取其精华：承重假设的定义与判据、A/B 两类扫描（表述中的前提、约束合取「锁成了 1」）、替代方案三约束、先中立呈现。原「不裁决」改为「Owner 表态后由 PE 给判断」。案例迁入 PE 的 references，PE 落地后删除原 Skill。

### 9.4 `to-questionnaire` 不整体迁移

现有脚本与模板把模式、格式和布局规定死了。对齐形式由 Business Alignment 启发式选择、调用者决定；只保留可复用组件（稳定题号与来源映射、本机保存与导出、改版答复迁移）和现有问卷作为样例。BA 吸收后删除原 Skill。

### 9.5 仍待确定

- PE 的最终名称。
- `entry.md` 长度预算、topic 粒度与写入门槛，用真实案例校准。
- 第一个试点项目与试点案例。
