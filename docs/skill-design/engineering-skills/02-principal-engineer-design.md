# Principal Engineer｜Skill 设计初稿

> 状态：设计草案（第二轮）｜名称暂定｜文档描述职责、行为与记忆机制，不是 `SKILL.md`

## 目标

在软件开发全生命周期中提供持续的工程判断：每当需求、设计、代码或维护工作出现有意义的取舍，帮助开发者判断**值不值得做、系统需要承担什么责任、做到什么程度**。

它常驻在对象项目里：管理系统的技术架构、业务决策等上层判断，带着项目历史工作，能解释过去的决定，也能在前提变化后推翻过去的决定。它可以读代码取事实，但不输出 review 结论；缺陷诊断归 `diagnosing-bugs`，代码审查归 `review-code`。对话以启发式判断为主，根据问题规模决定展开深度。

## 常驻 = 记忆 + 可靠的进场时机

Skill 不会自己醒来，常驻由两部分组成：

1. **项目记忆**：PE 在对象项目里有自己的记忆目录，每次进场先读、决策收口时写回（见下文「项目记忆」）。
2. **进场时机**：
   - **主控转入**：对象项目的 `AGENTS.md` 写一条规则——主控需要向 Owner 询问业务或架构层面的问题时，先进入 PE；由 PE 查记忆、整理问题，与 Owner 一起决策，再写回记忆。这是最主要、也最可机械执行的入口。
   - **Owner 直接调用**：PE 提供可由 Owner 直接调用的入口，用于主动找它讨论方向、复盘历史决定或整理记忆。
   - **阶段信号**：需求讨论、Spec 形成前、架构设计、Bug triage、技术债清理和系统演进时，出现下文的触发信号也可进入。

`AGENTS.md` 规则示意（落在对象项目，不在 workbench）：

```markdown
- 需要向 Owner 确认业务规则、范围取舍或架构方向，或任务以「按 X 做 Y」下达、准备拆分并行工作时，先用 `principal-engineer`：它查阅 `docs/principal/` 中的既有判断，整理问题，与 Owner 共同决策并写回。当前宿主没有该 skill 时，直接问 Owner，并在需要时手动读 `docs/principal/entry.md`。
```

## 路由与优先级

- 进场规则只对主线对话生效。`grilling`、`req-align`、`grill-me-smartly`、Business Alignment 正在运行时，它们向 Owner 提问不再重入 PE；它们可以只读 `docs/principal/` 取既有判断。
- 分界：要进入 Spec / 实现、需要正式 Decision Gate 的，走 `req-align` 的 Decision；难以撤销、需要长期解释的架构决定写 ADR（`domain-modeling`）；PE 的 `decisions/` 只记录轻量取舍与「不做 / 何时再议」，并链接前两者，不重复记录。
- `docs/principal/` 是 Owner 批准的项目级落点，不是 req-align 意义上的第二 authority：它不定义行为契约，只保存判断依据和指针。
- 架构的系统性体检归 `architecture-review`；PE 负责具体取舍点上的判断。

## 触发信号

- 任务以「按 X 做 Y」下达、准备拆分并行工作，或决定是否另开承载单元（包、服务、worktree、仓库）；
- 某个需求显著扩大系统职责或承诺；
- 新增状态、同步机制、服务、依赖、抽象或长期接口；
- 修复一个缺陷可能需要大量补丁，或修复对象本身的价值不明；
- 两条可行路径对维护成本、正确性、交付速度有明显不同影响；
- 新证据可能使既有决策失效。

简单而明确的局部修改不需要完整讨论。它可以只给一句判断并交还执行者。调用强度由决策影响范围决定。

## 判断方式

不采用固定阶段审批。思考时优先处理以下问题，足够明确就停止。

### 先查记忆

读 `entry.md`，按当前问题定位相关 topic 和 decision，只读相关的部分。已有有效判断且前提未变时，直接引用；前提已变时，指出变化并建议修订。

### 判断问题是否值得存在

识别实际使用者、实际损失、已验证场景与假设场景。考虑「不做」的成本，以及需求是否可以删除、延后或缩小。

### 找承重假设

先读 references 里的校准与反例再扫描；不带校准时，技术选型和执行偏好会被误判，B 类会被整个漏掉。扫描只就着 Owner 提供的材料做，不顺着记忆或仓库往下找补充材料。

**承重假设**是以陈述句出现、从未被论证过的选择：换掉它，已完成和计划中的工作要**全部重做**。判据只有一条——换掉它，是不是全部重做；换掉只需局部调整的（按钮位置、执行偏好、已被论证过的技术选型）不算。

承重假设藏在两处：

- **A · 事情被描述的方式。** 「按 X 做 Y」里的 X，或一份文档从标题起就当作既定事实的组织性选择。只找这类表述，不要顺着材料的逻辑往下读——顺着读只会读到它的自洽性。
- **B · 已写下的约束的合取。** 每条约束单看都对，加起来却把某个量锁死。把散落的「唯一 / 独占 / 单写 / 必须经过 / forward-only / 串行 / 共享同一个」条款拉到一起，问：**这组约束加起来，把什么锁成了 1？** 再问实际要的是几；两个数对不上，就是一个已经生效的承重假设。

找到时（通常 1–3 个，五个以上说明判据用松了），为每个配 3–4 个**根本不同**的替代方案：

- 所有候选不能被同一句话概括，否则只是变体；
- 至少一个直接违反原假设；
- 每个候选写出「它成立的前提」，并具体到第一步做什么、何时第一次验证、完成后长什么样。

替代方案的呈现形式不固定，写清各自成立的前提即可，然后照常给判断。

纯修复、证据订正、局部可逆调整没有承重假设可翻，跳过本步。

### 判断系统需要承担的责任

确定业务对外承诺和不可破坏的约束，例如审批责任、数据正确性、权限边界、同步时效、可恢复性。提出「做到哪」的建议，而不默认把每项能力做完整。

### 用约束剪枝

寻找会大量缩小方案空间的事实。优先考虑复用、移除无价值状态、改变职责边界、简化交互契约；比较维护代价和未来更改成本。能通过调整需求消除的复杂度，应先回到需求层面讨论。

### 识别能改变结论的未知量

缺业务知识，把具体缺口交给 **Business Alignment**；缺技术证据，把可检验的假设交给 **Engineering Probe**；需要全面展开相互依赖的决策树，交给 **`grilling`**。

### 做出当前决策并写回

输出倾向、理由、明确范围和重新评估条件。能判断时直接给出建议；无法判断时说明真正阻塞结论的事实。避免把调查任务和方案列表当成结论。有复用价值的结论写回记忆。

## 不同阶段的行为示例

**需求讨论。** 提出「要实时协同购物车」时，先确认业务是否需要持续共享的可见状态，还是仅需提交结果正确。后者可能删掉实时同步机制的必要性。

**Spec 设计。** 某模块提出为未来十种策略扩展建立配置平台。先确认近期是否真有多个独立策略与不同维护人；如果没有，建议先用单一明确流程。

**拆分并行工作。** 「按业务域纵切成四条线并行」——先把「独占 / 单写 / forward-only」类约束拉到一起，确认能同时推进的线数是否真的是 4，再摆替代的组织方式。

**Bug triage。** 发现一种罕见状态会导致计算错误。先查该状态是否允许发生、是否应作为业务能力保留；可能选择禁止进入、删除无效分支，也可能需要修复算法。判断必须覆盖已存在数据和外部调用影响。

**维护。** 过去未引入队列，因为任务数量小、允许等待。若现在出现新的时效承诺或积压证据，读到对应 decision 的重新评估条件已触发，主动建议修订。

## 与 `grilling` 的边界

`grilling` 把成熟或未成熟的方案展开成决策分支，分轮关闭重要问题。PE 在其前后工作：决定是否值得展开、决策树从哪些边界出发；`grilling` 负责把选定范围内的决策完整展开，结论回到 PE 写入记忆。两者可独立使用。PE 不要求每个问题都进入全量 frontier。

## 项目记忆

### 归属

记忆存放在**对象项目**里，随项目提交，供所有宿主（codex、claude、grok、zcode）读取。workbench 中的 Skill 只定义记忆的结构和读写路径，不存储任何项目或用户的记忆。

### 结构

```text
docs/principal/
  entry.md               # 入口：按主题路由到 topic / decision，一条一行，控制总长度
  topics/<topic>.md      # PE 对某个领域的理解：约束、长期倾向、未决问题、指向来源的链接
  decisions/<YYMMDD>-<slug>.md  # 轻量决策：做到哪、为什么不做、何时重新评估
```

文件名用日期加 slug，不用顺序号，避免多分支并行写入撞号；`entry.md` 新增条目只追加行。topic 只在某个主题已有两条以上 decision 或反复需要同一组背景时才建，内容以指针为主，不复述长青文档。

目录用到时才创建。第一次进场且目录不存在时，不做全量初始化，只在第一条值得记的判断出现时建立 `entry.md` 和对应文件。

### 和长青文档、ADR 的关系

- **按粒度分工。** 难以撤销、没有背景会让后人意外、确有取舍的决定写 ADR（按 `domain-modeling` 的 ADR 约定，通常在 `docs/adr/`），PE 的 topic 和 decision 只链接过去。「这次先不做实时同步，订单量到 X 再议」这类轻量取舍写入 PE 自己的 `decisions/`。
- **消费长青文档，不复制内容。** topic 是摘要加指针，注明依据的文档及版本（路径 + 日期或 commit）。PRD、ARD、Spec、ADR 是事实源；记忆与它们冲突时以事实源为准，PE 标出冲突交 Owner 决定，不自行修改事实源。PRD / ARD 的修改继续由原有工作流处理。
- **已有维护机制可借鉴。** topic 的拆分、去重和入口路由规则，参照 hands-on knowledge 的 `entry-map.md` 整理方式。

### 一条 decision

可以只有一段话：问题、取舍、理由。以下按需补充，只写有内容的：

```text
状态 / 日期 / 确认人
不做什么、何时重新评估（这两项是 PE decision 区别于 ADR 的核心，有就写）
被放弃的选择
证据：关键数字与环境直接内联，不链接临时脚本
关联 ADR / 文档 / 代码
waiting-on：等待中的 BA 材料或 Probe（仅 Proposed）
```

**状态：** `Proposed`、`Accepted`、`Superseded by <id>`、`Withdrawn`。未经 Owner 确认的建议不能写成 Accepted；讨论中已明确确认的决定直接记 Accepted。推翻旧决定时建立替代关系，保留原始理由。证据不完整时标注为假设。等待业务答复的 Proposed 带 `waiting-on`，`entry.md` 标出未决项，换会话后可接续。

**和 ADR 的判据：** 改变它需要迁移数据、改外部接口或重做大块结构的，写 ADR；改变它只是「当初没做，现在补上」的，写 PE decision。

### 读写规则

- **读：** 进场先读 `entry.md`，按主题定位，不把全部历史灌进上下文。
- **写：** 只有在主会话中与 Owner 共同决策的 PE 写；子代理与其他 Skill 只读。默认门槛：Owner 已确认，且下次大概率会再被问到或会被重新提起。日常小决定留在任务记录中，不进记忆。
- **防过期：** 引用某条 decision 或 topic 前，核对它指向的文件是否还在、是否在记录日期后有实质变化；变了就当「待核实」处理，不直接当有效依据。碰到某个主题时，顺手检查其中的重新评估条件是否已触发。
- **其他 Skill 产出的回流：** BA 或 Probe 被 `grilling`、`req-align` 直接调用时，结果留在调用方的产物里；PE 下次进场碰到该主题时再决定是否收录。
- **整理：** Owner 要求时做一次全量整理：对照当前长青文档更新 topic、合并冗余、修正过期指针、精简 `entry.md`，保留有效的历史沿革。

## 输出形态

常规交互是自然对话，不强制表格或完整审查报告。需要留下明确决定时输出简短摘要：

> 建议 / 影响范围 / 承重理由 / 仍依赖的事实 / 重新评估条件

缺少信息时直接提出一个会改变判断的问题。用户要求落到实现，再交给 Spec、Plan 或 Coding 工作流。

## 吸收 `challenge-the-core`

「找承重假设」一节吸收了 `challenge-the-core` 的定义、A/B 两类扫描、「锁成了 1」的合取检查、替代方案要根本不同并写清前提；固定表格、中立呈现和长案例不迁入，案例压成一段放进 `references/`。PE 试用确认后删除 `skills/challenge-the-core/`，并清理引用它的位置（含 worktree 分支中 req-align decision sub-skill 的引用，合并时处理）。

## 第一版验收案例

1. **新需求过度设计**：用户要求引入实时通信。Skill 先问实际实时性要求，能够建议保留或裁剪，而不是直接写 WebSocket 架构。
2. **Triage 中的修复选择**：出现某个分支 bug。Skill 能区分「需要修」与「应该删除无效状态」，且保留数据安全约束。
3. **已有判断可复用**：Owner 只问一个具体选择，Skill 从记忆中引用已有决定直接判断，不重开整棵树。
4. **历史理由被推翻**：新约束出现后能检索旧决定，指出旧前提变化，明确建议修订并更新状态。
5. **承重假设**：拆分并行工作的任务能抓到约束合取锁死的数量，并给出写清前提的替代方案。
6. **主控转入**：主控要问 Owner 业务问题时进入 PE，结论写回 `docs/principal/`，下一次会话能读到。
7. **轻量问题**：局部实现无显著取舍时不制造额外工作流，也不写记忆。

观察指标：是否更早发现决定性约束；是否减少无价值实现；有无误删业务承诺；是否引用正确的历史依据；记忆是否保持精简且与事实源一致。
