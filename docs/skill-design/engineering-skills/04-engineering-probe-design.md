# Engineering Probe｜Skill 设计初稿

> 状态：探索性设计｜先做薄版本，依实际使用案例调整｜不是 `SKILL.md`

## 目标

把影响工程取舍、尚未验证的技术假设，转成低成本且有判别力的实验。用实际观察决定系统需要承担什么容量、容错或复杂度，再把证据交还工程决策。

这里的「原型」面向技术人员：可能是一段查询、一组模拟请求、一个故障注入脚本或一条真实技术链路。面向业务方沟通交互的网页原型归 Business Alignment。

## 何时值得做 Probe

同时满足三个条件时优先考虑：

1. 当前存在会影响系统范围、架构或技术责任的未知量；
2. 不同的观察结果会导致不同决策；
3. 能找到成本与决策风险相称的验证办法。

例如「现有数据库在目标订单量下是否已经足够」值得测试；「新框架会不会更优雅」如果没有决策标准，暂不值得构造实验。

不把 Probe 变成每个需求的前置关卡。若已有日志、监控、执行计划或可信数据足以支持判断，直接使用现有证据。

## 行为方式

### 明确要区分什么

接受来自 Principal Engineer 或开发者的一个工程问题。将其改写为可被证据区分的假设，并说明两种结果会分别导致什么选择。

例：在预期并发和目标延迟下，当前任务执行方式能否完成处理？若能，则暂不增加独立队列；若不能，则定位瓶颈并重新评估。

### 选择最便宜的有效验证

实验手段从现有信息出发，逐步增加投入：

- 查看已有运行日志、指标、代码和配置；
- 在隔离环境下做小规模测量或复现；
- 用脚本模拟负载、超时、重试、响应乱序或资源不足；
- 做只覆盖关键技术链路的 Spike；
- 在需要时提高真实性，验证系统边界。

这些是可选手段，不是固定步骤。能用一条数据库执行计划解决的问题，不应先搭建压力测试平台。

### 让实验足够接近真实约束

实验前明确哪些因素会改变结论，如数据分布、外部 API 限流、并发形态、状态共享、故障恢复、重试语义和资源限制。

当无法完全复现生产条件时，说明哪些观察仍然有效，哪些只能作为趋势。避免把 mock 响应测得的吞吐量当作真实端到端容量。

### 观察、解释并停止

按预设指标运行最小实验，记录主要结果和可复现方式。结果足以区分当前选项时立即结束；若没有区分能力，再决定是否补充实验。不要为了完整的 Benchmark 报告不断扩大范围。

## 第一版支持的 Probe 类型

| 类型 | 典型问题 | 最小产物 |
|---|---|---|
| 容量边界 | 现在的数据路径是否承受目标规模？ | 数据生成 + 查询／负载脚本 + 指标 |
| 故障行为 | 超时、重试、重复请求会破坏哪些不变量？ | 故障注入脚本 + 结果 |
| 技术可行性 | 某接口、权限机制、事务边界是否成立？ | 关键链路的技术 Spike |
| 设计选择 | 两种方案在哪个真实约束下表现不同？ | 对比实验 + 选择建议 |

不要预先建设一套统一的混沌工程平台。先从当前项目能直接运行的小实验积累案例。

## 示例：Agent 任务并发是否需要独立队列

**待决策事项：** 现有运行方式能否满足预期任务并发和可接受等待时间；是否值得增加队列、Worker 与任务恢复机制。

**先确认业务边界：** 目标并发指同时登录，还是同时执行耗时任务？最长可接受等待多久？失败后能否重试？这些输入由 Principal Engineer / Business Alignment 确认。

**Probe 提案：** 在隔离环境中使用与真实任务相似的执行路径，逐步增加并发；加入超时和失败重试。测量完成率、等待时间、P95 延迟、重复执行和资源消耗。

**关键真实性问题：** 如果瓶颈来自模型 API 限流，本地 fake API 只能测出应用内部瓶颈；涉及真实调用成本时，选择少量真实采样与模拟负载结合。

**决策回传：** 明确现有方案在何种条件下足够，何种条件下失败，以及是否已有证据需要更复杂的任务系统。

## 结果输出

优先短报告，可附脚本和必要观测文件。建议内容：

```text
待决策问题
实验前假设和改变决策的阈值
实验环境与真实性边界（必填：哪些条件与生产不同，结论因此只在什么范围内成立）
执行方法／脚本位置
关键观察结果
可以支持的结论
仍需判断的条件
```

如果实验没有得到有效结论，也直接说明原因；不强行给出推荐。

脚本应当尽量可丢弃、可复现，默认在隔离环境操作。会碰到共享环境（Staging、线上）、产生真实费用或修改外部状态的实验，先取得 Owner 同意；只读查看不受此限。

决策引用实验结果时，把关键数字、环境和真实性边界直接写进结论，不依赖临时脚本仍然存在。只有已经证明反复有用的实验能力，才考虑沉淀为回归测试或长期基础设施。

## 与其他 Skill 的关系

- **Principal Engineer**：提出需要证据的技术取舍，消费结果并作最终范围判断。
- **分界**：查资料、官方事实归 `research`；已经坏了或变慢了的诊断归 `diagnosing-bugs`；可重放的验收环境与种子数据归 `validation-harness`；UI 或状态模型的一次性原型归 `prototype`。Probe 只做「为了一个待决策取舍而获取技术证据」的实验。
- **Business Alignment**：确认负载目标、时间容忍度、业务后果等实验前提；它不负责技术实验。
- **PE 项目记忆**（对象项目的 `docs/principal/`）：由 PE 决定是否把对长期决策有价值的实验结论与证据引用写入；Probe 自己不写记忆，临时脚本也不进入记忆。开始实验前先查记忆中是否已有可用的证据。

## 第一版验收案例

1. 可以从模糊的「性能可能不够」收敛成影响决策的具体实验问题。
2. 不需要实验时会直接给出已有证据，不机械生成脚本。
3. 在同一问题上优先选择成本更低、区分力足够的验证方法。
4. 能识别实验与生产条件的关键差异，避免过度外推。
5. 输出能够直接用于「现在做／延后做／修改 scope」的选择。

## 第一版暂不规划

不预设统一执行引擎、仪表盘、固定实验类型或持续部署机制。先收集实际 Probe 的用途和失败案例，再决定有无必要做平台化。
