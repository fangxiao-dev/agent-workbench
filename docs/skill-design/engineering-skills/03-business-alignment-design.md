# Business Alignment｜Skill 设计初稿

> 状态：设计草案｜面向业务知识获取与决策对齐，不是 `SKILL.md`

## 目标

当工程决策依赖开发者尚未掌握的业务知识时，帮助开发者找到应该向业务方获取的输入，并将问题转换成对方能根据真实工作回答的内容。最终形成可追溯的业务依据，交还 Principal Engineer 或原任务流程。

典型对象包括老板、业务负责人、门店人员、税务师和客户。对齐媒介由问题性质和收件人决定，不预先绑定问卷格式。

## 什么时候介入

- Principal Engineer 发现关键业务假设尚未确认；
- 开发者正在定义新流程、角色职责、权限或异常规则，却缺少实际业务经验；
- 已有 Spec 中存在多个合理解释，需要业务方选择；
- 实施中出现业务冲突，需要确认哪种行为符合真实工作。

开始生成材料前先查已有业务文档、确认记录、PE 的项目记忆（`docs/principal/`）和项目知识；已经能够找到可靠答案时无需重复提问。

## 对齐策略

### 1. 从待解锁的工程决定倒推信息缺口

先确认「拿到回答后，哪个决定会改变」。例如：确认提交后的修改规则，是为了判断需要怎样的锁定、变更记录和重新审核责任。

提问不是为了列出完整业务百科。优先选择能影响当前功能边界、数据责任、角色行为的缺口。

### 2. 分清事实、偏好与授权

- **业务事实**：目前实际如何操作，是否有既定规则或外部要求。
- **业务偏好**：两种都可行，哪种体验或工作分工更合适。
- **业务决策**：某个角色是否愿意承担一项责任，是否正式确认改变流程。

事实适合以开放问题、真实案例或材料佐证获取；偏好可以比较场景；正式决策应能关联确认人、适用范围和日期。

### 3. 让对方判断真实场景

优先写「在什么情况下，谁现在做什么；如果发生例外，应该如何处理」。避免让业务方评价状态机、字段、接口、锁等实现概念。

示例：

> 企业已将本月工时资料提交给税务师，随后发现一名员工工时填错。现在实际怎么处理？如果税务师已经完成工资核算，做法是否不同？

这里可能产生两条业务规则，它们将影响系统是否需要退回、修订或更正流程。不要在业务方尚未解释现行实践前，把工程方案包装成唯一的多选题。

### 4. 选择对齐形式

表达形式服务于信息缺口：

| 缺口 | 适合的媒介 |
|---|---|
| 单一规则、负责人、期限 | 简短文字或聊天问题 |
| 正常与异常流程 | 场景描述、流程图 |
| 职责归属 | 角色操作矩阵 |
| 几个业务范围之间的取舍 | 对比卡片、决策问题 |
| 对界面和操作顺序理解不一致 | 交互 HTML 或业务演示 |
| 多人异步确认 | 可保存、可导出的对齐材料 |

HTML 可以承载发现式开放问题、交互场景或固定选项，Markdown 也可承载决策题。调用者可以直接指定格式；Skill 自行判断默认形式。

### 5. 收回答复并更新决策依据

保留问题与来源的对应关系，记录对方的实际答复及不确定项。必要时进行第二轮聚焦追问。把已确认规则回填到项目的适当事实源，并向 Principal Engineer 提供能改变工程判断的结果；由 PE 决定是否写入其项目记忆。

问卷或 HTML 的选择记录本身不自动等于最终业务规则；对于有冲突或含糊的答案，应保持「待确认」状态。

## `to-questionnaire` 的目标形态

现有实现位于 `agent-workbench/skills/to-questionnaire/`：`SKILL.md`（6 步流程 + Discovery 的 Markdown 模板）、`references/decision-mode.md`、`references/html-output.md` 和 `assets/decision-questionnaire.html`（约 380 行的单页问卷）。

**不整体迁移。** 现有实现把模式、格式和页面结构规定死了：Discovery 只能 Markdown，Decision 每题固定「现状 / 推荐 / 四选一」，HTML 是一个固定布局的页面。对齐形式有很多种，应由 Business Alignment 启发式选择、调用者决定成品，不再由一套模板主导。

保留的部分分两类：

- **启发式（并入 BA 的正文）**：
  - 只向用户追问「发给谁、回来后要能决定什么」；问题瞄准收件人知道而开发者不知道的差距；最重要的先问；
  - 写完核对覆盖：回来后要决定的每一项都有题；
  - 发出前筛题：常理可定的不问、重复的合并、技术参数不问非技术收件人、已有结论的不问；
  - 涉及法规、税务等需要专业人士确认的题，明确标出，答复不能由非专业收件人代定；
  - 给推荐时，推荐必须是开发者愿意直接落地的默认；
  - 从收件人视角派新 subagent 检查能否独立理解；
  - 答案按题号回填来源；题号永不复用，删题时旧答复保留；未答的题保持「待确认」，不按推荐默认处理。
- **可复用组件（作为例子放进 BA 的 `assets/` / `references/`）**：
  - 稳定题号与来源映射——异步对齐可追溯的基础；
  - 本机保存、复制 / 导出答复；
  - 改版时保留旧题号与 `storeKey`，旧答复可迁移；
  - 现有 Decision 问卷 HTML 与 Discovery Markdown 模板，降级为「某种情况下可以这样做」的样例。

这些组件是可选的，不构成固定字段要求或统一页面模板。新形式（场景切换、角色矩阵、流程演示等）由 BA 按缺口现场设计，可以借用上述组件，也可以不用。

**组织方式：** BA 吸收上述内容后删除 `skills/to-questionnaire/`，「已知问题快速出问卷」作为 BA 的一条快速路径保留。

删除前提：现有 HTML 与两份 reference 已原样存为 BA 的样例。删除清单：`skills/to-questionnaire/`、`registry/third-party-skills.md` 中的上游登记项（经 `import-third-party-skill` 处理）、`skills/ask-matt/SKILL.md` 中的引用，以及各宿主的链接。

**与原型类 Skill 的分界：** 面向业务方的交互 HTML 演示由 BA 决定要不要做、要确认什么；需要多方案比较的一次性 UI 原型交给 `prototype`，挂在真实应用壳里的预览交给 `preview-design`。

## 与其他能力的接口

**接收 Principal Engineer 的输入：** 当前决策、已知事实、关键缺口、缺口会改变的取舍，以及可能的业务负责人。

**向 Principal Engineer 返回：** 得到的业务事实、确认人、适用范围、证据、尚存分歧，以及哪些设计假设受到影响。

**与 `grilling` 协作：** `grilling` 在讨论中展开决策树时，遇到业务事实缺口可交给 Business Alignment；业务问题得到回答后，再继续未完成的 frontier。

## 第一版的对齐产物

默认优先小而可回答的材料。它至少应让业务方知道：为何需要自己回答、当前具体场景、应该回答什么、回答将影响哪项业务行为。

内部留存的每个重要问题可以用以下最小信息记录：

```text
问题 ID / 待确认业务场景
当前已知事实与未知项
目标收件人
为什么会影响当前决定
答复和证据来源
确认状态 / 后续问题
```

用于业务方的页面不用展示工程影响分析；该信息留给开发者和决策记录。

## 第一版验收案例

1. **不熟悉业务时**：开发者只能提出「要做工资准备」，Skill 能挖出需要确认的关键流程和责任，不要求开发者先给完整问题清单。
2. **多种对齐媒介**：同一组场景可以根据收件人和沟通方式，生成简短聊天问题、Markdown 或交互 HTML。
3. **事实与选择分离**：遇到既有业务事实时不会强行生成「同意推荐／以后再做」四选一。
4. **问卷可追溯**：答案能回到原业务问题，改版后保留可识别的旧回答。
5. **节制介入**：已有可靠答案或问题无决策价值时，不新增问卷。

## 待试点确定

- 现有 HTML 中保存、导出、迁移逻辑能否拆成独立可借用的片段，还是只能整页作为样例。
- 是否需要统一的中间问题模型；若有，应保持可扩展而非固定题型。
- Business Alignment 如何检索具体项目的业务资料并选择收件人。
