# Skills 优化方案：保留 SaaS 安全底线，扩大 Agent 的实施自主权

日期：2026-10-27
状态：建议方案，供 Owner 审阅；本文件落盘不代表其中的行为变更已经批准或实施。
范围：需求探索、Impl-Package 入口、执行与审查中的复用、知识吸收，以及相关规则的表达和验证。

## 1. 为什么现在讨论这件事

这次讨论起于对 Matt Pocock 最新 Skills 与本仓库的比较。我们并非原样安装上游工具箱，而是选取了一部分方法，并将其接入需求对齐、实施规划、多 Agent 协作、审查、验收和知识沉淀。因此，“上游有而本地没有同名 Skill”不能直接解释为能力缺失，“本地规则更多”也不能直接解释为工程能力更强。

Owner 提出了两个需要同时满足的要求：

- Skills 应帮助 Agent 做出更好的判断，不能逐渐成为限制其主动调查、实验和推进工作的束缚。
- 实际项目是重后端 SaaS，涉及多租户、权限、持久化数据、并发、外部系统和失败恢复；不能以追求轻量为由，放弃这些地方必需的细致设计与验证。

这两个要求并不矛盾。需要区分的是：哪些规则在保护产品承诺、数据与授权，哪些规则只是固定了 Agent 达成目标的路径。本方案的目标是让前者保持可靠，让后者具有足够的现场适应性。

本方案不以某个 Skills 框架是否流行作为判断依据，也不以减少文件数、字数或 Agent 数量作为成功标准。判断依据是：一项规则是否改善实际决策、阻止重要错误或帮助恢复；它带来的执行成本是否值得。

## 2. 现有体系为什么会变得细致

### 2.1 Matt 提供工程方法，我们增加了持续交付能力

Matt 的核心方法包括通过 grilling 澄清需求、通过领域语言减少理解偏差、通过测试反馈约束实现、通过深模块设计减少复杂度，以及从规范和需求两个视角独立审查。其工具强调小、可组合、可修改，由使用者选择流程。

本仓库保留了这些方法，并增加了复杂工作所需的控制：谁拥有需求语义，哪些工作可以并行，返回结果属于哪次派发，验收依据是否对应当前版本，暂停后如何恢复，以及什么证据足以支持完成声明。

这些控制有真实用途。例如：worker 的测试通过不代表整条业务路径接通；单个模块结果正确不代表跨租户读取正确；旧版本审查通过不能自动证明新版本安全。对此保持明确规则，是重后端 SaaS 的工程需要。

### 2.2 我们已经进行过减负，本轮应接续而非重来

[2026-09 的打薄记录](impl-package-astra-thinning-decisions-260906.md)和[核心执行 Skill 审查](three-core-skills-first-principles-review-260908.md)已经讨论过减少重复规则、按需读取、扩大合法并行、主控直接实施及运行时投影等问题。当前 Dispatcher 也已经强调按实际收益委派、按真实资源冲突隔离、局部阻塞只限制受影响工作。

这些历史材料解释规则形成的原因，不代表其中所有实现描述今天仍然成立。本轮以当前 Skill、引用合同和必要的代码检查为事实依据；历史决定用于避免把曾经解决过的问题重新引入。

### 2.3 本次比较需要纠正的两点

**retro 已被吸收。** [Knowledge Manager 的设计](knowledge-manager-system-design-260913.md)明确说明，其 environment lane 来源于 Matt 的 retro。它与实践经验、稳定业务语义分开，属于有意设计；无需新增独立 retro 入口。

**wayfinder 默认负责澄清路线。** 上游会创建决策问题、管理其依赖并安排研究，因此具有探索编排，但默认产出是决策，而不是实施交付。路线清楚后即交接；只有显式覆盖其默认范围才包含实施。它与我们的实施调度不是同一个职责，但整套引入仍可能增加重复的状态和入口。

## 4. 优化原则：严格约束结果与风险，允许自主选择路径

| 规则类型 | 为什么需要 | 推荐处理方式 |
| --- | --- | --- |
| 产品与安全不变量 | 错误可能造成越权、数据损坏或无法恢复的副作用 | 保留明确合同、针对性验证和必要阻断 |
| 事实与证据完整性 | Agent 可能把局部成功、旧证据或模拟结果误报为完成 | 保留版本归属、真实证据、独立审查及可信状态写入 |
| 实施策略 | 合适的调查、拆分、委派和执行顺序依赖现场信息 | 给出判断依据，允许 Agent 在授权范围内选择和调整 |
| 机械操作与派生信息 | 重复计算和人工同步容易出错并消耗注意力 | 优先复用现有工具计算；明确哪些输出只是派生展示 |
| 经验与提醒 | 有些提醒能防止已知误判，有些只是重复规则 | 保留有独特解释价值的提醒，按触发条件读取；删除重复含义 |

保留的底线包括租户隔离、权限、隐私、数据身份和权威来源、幂等、并发、失败恢复、共享合同，以及完成声明与证据相匹配。实现方法可调整，不意味着可以自行改变这些承诺。

工作量与风险分别判断。修改一行租户过滤逻辑仍需要针对性安全审查；跨越多个文件的机械重命名则未必需要完整任务包。流程负担应由真实协作需要和风险决定。

## 5. 推荐方案总览

推荐沿用现有体系，实施五项有明确落点的调整，并对一项运行机制先做核查。它们属于三批工作，不要求先建立新的统一管理层。

| 编号 | 建议 | 首要收益 | 决策性质 |
| --- | --- | --- | --- |
| P1 | 明确完整任务包的使用边界 | 普通工作无需承担整套流程；包内仍保持统一 | 需要明确入口政策，并校准旧文案 |
| P2 | 后续工作按变化复用合同、范围和证据 | 减少重复发现与重读，保留新风险发现能力 | 收紧既有复用语义，不削弱 required review |
| P3 | 吸收 wayfinder 的目标与未知管理 | 避免过早规划，也避免穷尽无关未来问题 | 调整探索完成边界，保留当前目标的实质决策完整性 |
| P4 | 让 Knowledge Manager 的执行与报告匹配材料规模 | 少量知识无需固定多 Agent 和大量零项输出 | 改变现有固定委派与报告规则，需明确批准 |
| P5 | 按真实触发条件整理主路径、提醒和重复定义 | 提高关键规则可见性，减少无关上下文 | 延续既有单一权威和渐进读取原则 |
| P6 | 核查机械记账是否被误当验收前提 | 找到可安全消除的流程故障 | 先调查消费者，不预先批准运行时改动 |

## 6. P1：先决定是否需要任务包

### 背景与问题

完整任务包用于持续实施、独立验收和跨会话恢复，它有真实价值。当前 [Composition Contract](../../plugin-marketplace/plugins/impl-package/references/impl-package-composition-contract.md)与 Impl-Package 偏好记录明确新包为 Ticket-only；但入口仍出现“可选 Ticket”，规划偏好中也残留“小型线性工作可无 Ticket”的表述。

这会使 Agent 不确定应当直接完成工作，还是创建一个最小任务包，甚至自行构造现行运行时并不支持的 no-ticket 组合。修复重点应是入口判断，而不是增加第二套包内状态模型。

### 推荐行为

主控先根据当前目标和上下文判断是否需要持久化的实施协调。明确沿用现有任务包的工作继续在原包内处理。独立、局部、可逆、合同已清楚且不需要持续协调的工作，可直接实现并进行相称的验证与审查。

当工作需要多个独立验收单元、跨会话实施恢复、复杂集成或迁移协调，或者 Owner 明确要求任务包时，使用完整任务包；创建后统一遵循 Ticket-only 合同。

业务语义尚未决定时先进入需求对齐。安全、数据或外部副作用风险决定需要哪些合同、验证、审查和授权，不能因“不创建 package”而被跳过；也不把“发现风险”机械等同于“必须创建大量文档”。入口应分别判断协调需要和风险控制需要。

### 落点与验证

主要落点是 `impl-package` 入口和 `req-align` 的 fast path，以及 `impl-planning` 的直接引用和偏好记录。现有 package runtime 保持单一路径。

验收至少覆盖：局部内部修复直接完成；一行权限修复仍接受相应安全控制；多租户数据迁移进入有明确合同和恢复安排的流程；既有包内修复不会借 fast path 绕过包内验收；发现未决业务语义时回到需求对齐而非猜测。

## 7. P2：建立一次依据，后续按变化核对

### 背景与问题

固定审查对象、确认合同来源和独立复核能阻止错误采信。当前 Plan/Ticket 已记录具体合同引用，ReviewRun 也固定来源和版本；后续若仍无差别重新搜索 tracker、文档和来源，会重复支付发现成本。

复用也有风险：已有引用可能漏掉新增消费者，环境或权限配置变化可能使旧测试失效。因此，简化应围绕变化及其影响，而非一律跳过检查。

### 推荐行为

首次工作建立所需依据。后续先读当前差异、已有 canonical 引用和明确的变更信号；范围、authority、配置或关键因果输入变化时，扩大到受影响来源。来源缺失、相互冲突或无法确认适用性时，再执行完整发现。

复用的是发现结果、仍有效的合同理解和证据，审查对象仍必须对应当前增量或最终版本。保留每次实际代码返回的独立 delta review、正式审查的风险准入、终审要求和已接受 Spec finding 的 source recheck。

### 落点与验证

落点为 `do-review` 的来源发现，以及 `req-align`、`impl-planning`、`execution-boundaries` 中同义的重新读取要求。各自只修改其拥有的规则，复用现有版本和引用机制。

验收覆盖：同合同下的局部修复无需重新宽搜；新增公开接口或修改权限会扩展检查；缺源不能被解释为无约束；无关文件变化不触发完整重验；环境关键输入改变时相关旧证据失效。

## 8. P3：吸收 wayfinder 的探索语义，保留现有实施入口

> 后续决定（2026-10-27）：Owner 已确认将探索方法独立为 `req-discover`，供用户单独使用及 req-align 按需调用。具体分工与产物以 [req-discover 设计](req-discover-design-261027.md)为准。本节“仅修改现有入口”的落点建议由该决定取代；其他优化项的状态不变。

### 背景与问题

较大的产品问题往往不能在一开始完整规划。过早写实施步骤会把猜测固化；反过来，要求“所有分支全部关闭”也可能使探索扩展到与当前目标无关的未来问题。

上游 wayfinder 的独特价值是明确目的地、当前能提出的问题以及尚不能准确描述的未知。它的 Issue 认领、依赖和会话规则是承载方式，不必随思想一起引入。

### 推荐行为

以现有需求讨论和 Decision 文档为载体。只有探索确实跨会话时，持久化当前目标、已接受方向、当前重要问题，以及因前置信息不足尚不能展开的区域；同会话即可解决的内容留在工作上下文。

研究与原型继续按现有 Dispatcher 和对应 Skill 执行。涉及真实产品取舍的问题由 Owner 决定；Agent 自行查清可获取的事实。探索产出进入现有 Decision/Spec，之后由现有规划与实施入口接手。

完成条件是当前范围内会改变方向、安全、共享合同和验收的实质问题已经解决，下一阶段无需发明这些语义。内部算法组织、局部实现选择及明确排除的未来范围不必提前穷尽。新证据改变已确认前提时，只重新打开受影响的决策。

### 落点与验证

落点为 `grilling` 的范围和完成条件，以及 `req-align` 的 Decision 子流程；不增加 wayfinder Skill、决策状态机或默认 Issue 发布流程。

验收覆盖：薄想法能逐步展开而不伪造完整计划；成熟方案聚焦当前缺口；多租户隔离或恢复语义未决时不能放行；内部实现选项不阻塞已清晰合同；跨会话续接可分辨待决问题、未来未知和已排除范围。

## 9. P4：Knowledge Manager 按材料规模选择执行方式

### 背景与问题

Knowledge Manager 将实践知识、稳定语义和环境改进分开，并由主控统一写入，这些边界有效避免了知识重复和越权修改。当前规则对有来源的知识 lane 固定派只读 worker，且最终报告必须逐 lane 展示大量精确计数，包括零项。

对多来源、大型任务包，这有助于覆盖和核对；对一两条清楚的经验，固定编排与输出可能比知识本身更重。

### 推荐行为

保留三类知识归属、当前事实校准、主控唯一写者，以及 environment 默认只给建议的授权边界。主控依据来源规模、判断独立性、上下文压力和交叉检查价值，选择直接核对或委派只读审计；不设置固定数量阈值。

常规报告给出来源范围、实际处理总量、变更结果、未解决项和验证结论。逐项保留重要候选的去向；零项分类可以合并表达。用户要求完整审计或存在复杂跨 lane 合并时，再展开现有完整分类统计。

环境建议优先检查已有工具是否可用、是否接入现有验证路径；可机械检测的错误优先提出检查改进。需要判断的约定继续由文档和 reviewer 承担。该建议仍不授权自动修改代码、CI、权限或宿主设置。

### 落点与验证

落点为 `knowledge-manager/SKILL.md`、其设计文档及 focused contract/eval。此项需要改变现有固定委派和完整计数要求，不属于单纯压缩文字。

验收覆盖：小来源能直接处理；复杂混合来源仍有足够覆盖；所有候选有去向；冲突只暂停受影响条目；会话不可读时其他知识 lane 可继续；环境建议不会自动变成环境修改。

## 10. P5：减少重复含义，保留真正影响判断的提醒

### 背景与问题

过去已确认“一条规则一个权威定义”和“条件分支按需读取”。但把重复内容移入 reference、再要求所有调用都读，并不会真正减负；只留下短规则而删掉独特的失败解释，也可能降低执行质量。

### 推荐行为

逐条按用途处理：通用主路径留在入口；条件分支通过具体触发指针读取；独特的误判原因跟随对应规则；纯重复定义删除；只服务回归验证的事故细节进入现有 eval。

同时核对实际调用中会注入的协议和工具输出。正文允许自主选择而运行时仍强制单一路径时，应报告运行机制冲突，不能用继续改写 Skill 文案冒充修复。既有历史文档只作为 provenance，避免在当前路径重复注入旧规则。

### 落点与验证

先覆盖 P1–P4 实际触及的文件及直接 references，不发起全仓同义改写。验证每个关键边界能从入口到达、条件分支不会普遍加载、删掉的是重复含义而非风险解释。

## 11. P6：先核查机械记账的消费者，再决定是否修改

### 背景与未决事实

当前 `do-review` 在形成 canonical ledger 后要求记录 `review.canonical_summary`，记录失败会使 canonicalization 不完整。相关记录既被进度统计读取，也被 `situation.py` 使用。仅凭名称不能将其认定为纯统计副本。

### 推荐调查与裁决方式

沿当前记录的生产者和直接消费者核查：哪个字段用于风险放行、完成判断、恢复或后续动作，哪个字段仅用于展示；失败时真实业务证据是否仍完整；是否存在可确定性重建的副本。

如果它是验收或合法性判断的必要输入，保留其可靠写入要求，优先改善已有命令的原子性或重试体验。如果确认只是可重建投影，则让其失败只影响投影新鲜度，由 canonical 数据恢复。调查结果不足时维持现状。

本项交付首先是一份消费者结论和最小建议。是否改 runtime、涉及哪些宿主和测试，由该结论确定；本方案没有预先批准移除阻断或新增异步系统。

## 12. 实施顺序与验证

### 第一批：入口与复用

实施 P1、P2，并在触及文件内执行 P5。先明确什么工作需要 package、什么风险控制始终适用，再减少重复发现。保留现行 Ticket runtime、审查拓扑、delta review 和 source recheck。

完成条件：局部工作可直接推进，风险变化仍触发对应控制；当前与历史入口文案一致；复用不会隐藏新合同或失效证据。

### 第二批：探索与知识吸收

实施 P3、P4，并执行相邻范围的 P5。重点验证决策停止边界和材料规模适配，避免为了轻量而漏掉关键选择或知识去向。

完成条件：当前目标的实质决策完整，未来细节不过早冻结；小规模知识吸收无需固定多 Agent；复杂来源保持覆盖和授权边界。

### 第三批：运行机制核查

完成 P6 后再确定是否存在值得实施的工具变更。若证据显示现有阻断有必要，保留现状也是合格结论。

### 验证方式

Skill 改动遵循仓库 L0/L1 边界：先运行改变 Skill 的 focused contract/static/validator，再运行直接引用与相邻路由的检查。运行机制若有跨模块影响，再按真实消费者扩大检查；不因本方案横跨多个主题就默认运行全仓测试。

静态检查之外，使用现有 eval 机制回放各提案列出的正反场景。重点观察 Agent 是否做出正确分流、能否继续无关工作、是否保留风险控制、是否出现漏验或错误完成声明。原有测试若只固定旧措辞，需让断言检查目标行为；不能通过删除失败断言宣称优化完成。

选取具有代表性的局部修复和跨模块 SaaS 变更，观察不必要的暂停、重复读取、重复产物，以及保留控制是否继续发现关键问题。只记录能支持裁决的证据，不新建常驻评分、遥测或流程管理系统。遇到明确回归时缩回受影响的调整，不扩大新规则来弥补未经理解的问题。

## 13. 本轮保留与暂缓的决定

以下机制本轮保留：每次实际代码返回的独立 delta review、正式审查风险准入、最终完整适用审查、accepted Spec finding 的源头复核、固定版本证据，以及已有 package 的 Ticket-only runtime。

强制从属 `contract-design.md` 暂不改变。当前规则允许 `not-required`，但已有详细合同不能因为本次只改措辞就降为不需要；任何改变默认结构的建议，都必须证明共享精确语义仍有唯一可靠位置。

不新建独立 retro 或 wayfinder 入口，不新增风险评分表、调度队列或第二套包状态。已有 source-of-truth、授权和宿主边界继续生效。

Owner 需要裁决的是：是否采纳 P1–P5 的目标行为，以及是否开展 P6 的限定核查。本文建议按三批推进；批准落方案文档不等于批准实施，也不把本提案自动升级为全局 Skill 偏好。
