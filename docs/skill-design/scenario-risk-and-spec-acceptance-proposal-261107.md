# 场景风险清单与 Spec 验收合同调整提案

状态：待评审（2026-11-07）
涉及技能：`impl-package:req-align`（Spec 子技能）、`impl-package:review-code-by-spec`、`run-acceptance`、`learn-lessons`
试点对象：KaiSpan `docs/implementations/2026-11-06-tenant-mailbox-inbound`（租户专属邮箱一期）

## 1. 结论先行

1. 新增一份**场景风险清单**。只记录启发式的“模式”，并从每次缺陷和审查发现中积累。req-align 的 grilling 和 Track C（合同审查）都读它。
2. 在 Spec 子技能内，把**验收合同（Journey、规则矩阵、套件）拆成独立的一步**：先冻结行为合同，再起草验收合同。两者仍然一起过同一个 Spec Gate。
3. **Journey 现有字段全部保留**，只加条件字段：步骤涉及权限或数据范围时，补“要读的数据”，并回答“换成变体执行者还能不能完成”。另外在模板注释里补一句：测试准备动作不写进“操作入口”。
4. **run-acceptance**：每条 Journey 至少用一个变体执行者真实走一遍；另把邮箱一期走查中暴露的执行问题写进走查手册，包括取证方法怎么选、在冻结的工作目录里走查、证据由主控统一登记等（见 §4.4）。
5. **规则集中放**：只写约定，暂不加机械检查。
   - **do-review**：终审通过后，提醒 Owner 是否要加一轮盲审 loop。不默认运行（§4.6）。
   - **impl-package CLI**：修复 amendment 的 `tickets` 字段被 `situation.py` 校验拒绝的问题（§4.7）。
6. 以下几项**保持不动**：Decision 与 Spec 的分工、contract-design 默认 `detailed`、Journey 归属 Spec。
7. 用邮箱包做**试金石**，验证第 1–4 条的效果，再决定是否推广。

## 2. 背景：为什么要改

### 2.1 邮箱一期暴露的问题

邮箱一期按 impl-package 完整流程走完：4 条 Journey、35 步、46 条规则、11 个套件。三轨终审（代码、合同、安全）之后，又加了 `discuss-ledger` 盲审 loop 作为第四轨。每张 Ticket 都过了 initial、finding-closure 和 terminal-final，之后仍然连续几轮发现新缺陷。有代表性的几类：

| 类别 | 例子 | 共同点 |
| --- | --- | --- |
| 同一判断写了多份 | 接管时“先查账单再释放认领”。保留清理和定时清扫各写了一份，都漏了这一步，会让已建单据与认领脱钩 | 规则散在多个流程里，每次修一处、漏一处 |
| 时间边界 | 测试写死“今天 09:00/10:00”，过点就失败；“加锁后复核”漏了保留期条件；地址历史用进程时钟，开关历史用数据库时钟 | 时间相关条件没有被系统性地追问 |
| 状态被别人改了 | 清理选中事件后，重投把它改回 open；邮件到期时认领还在进行中、原请求崩溃，认领从此永远停在 pending | 并发和中途状态变化 |
| 外部输入 | 正文含 NUL 导致永久失败；验签前就占用名额被饿死；多个 From 头 | 信任边界和异常输入 |

这些问题单独看，都能被现有审查找到，但都发现得很晚：要到终审或盲审才暴露，返工成本高。

### 2.2 一个邮箱之外的案例：代班

代班案例：店长把当天的代班任务委派给员工，委派只授予当天的权限。代班任务里要核对现金，而核对需要读取历史现金数目。被委派者没有历史日期的权限，任务无法完成。

这个案例说明了一个关键点：**每条规则单独看都正确**：
- 委派只授予当天权限：对；
- 读取现金需要对应日期的权限：对；
- 代班要核对现金：对。

出错的是三条规则在同一个场景里叠加：执行者完成任务所需的数据，超出了他被授予的范围。

规则写得再集中、标注得再好，也兜不住这类问题。这类问题需要有人站在“这个人此刻要完成这件事”的角度，把整条链走一遍。

### 2.3 讨论过、未采纳的方向

| 方向 | 为什么没采纳 |
| --- | --- |
| 统一规则引擎（平台级） | 现阶段没有第二个需要“发布、版本、按租户配置”的场景。财务的 Kontierung policy package 是专用的，保持现状 |
| 规则归属列，加函数标注 `@rule Rn`，加 CI 脚本检查一条规则只有一处实现 | 对当前阶段太细，spec 和代码都会变啰嗦；而且只能兜住局部规则，兜不住 §2.2 那类场景规则 |
| 把 Decision 和 Spec 合成一份短文档 | 两者定位不同。Decision 管承诺、方向、取舍和 blocking 判定，子技能明确禁止把 Spec 细节写进 Decision；Spec 管行为合同和验收怎么做 |
| contract-design 默认改为 `not-required` | 历史上默认 `not-required` 时容易偷懒，所以才改成默认 `detailed`。这不是重量的主要来源 |
| 精简 Journey 字段 | 逐列核对邮箱 35 步的实际用法后，没有哪一列是大概率没用的，见 §3.3 |

## 3. 现状核对（基于技能原文，不凭印象）

### 3.1 req-align 的结构

- `SKILL.md` 是路由入口，内容工作交给两个子技能，路径是 `sub-skills/decision/SUB-SKILL.md` 和 `sub-skills/spec/SUB-SKILL.md`。
- Decision 子技能负责 requirement inputs、Focused PRD、blocking triage、Core/Capability，以及 Decision Gate。它的完成条件里写明“没有把 Spec/Plan 细节写入 Decision”。
- Journey 已经在 Spec 子技能里：放在“设计与写入”的第 7 步，对应 spec 模板 §7 的 Journeys、Rule Matrix、Required Suites 三张表，随 Spec Gate 批准。Decision 阶段不碰它。

### 3.2 Spec 子技能重在哪里

Spec 子技能一个阶段里叠了三件性质不同的事，要求在同一个 Gate 里一次通过：

1. **行为合同**：设计范围、八个行为章节、contract coherence，命中触发条件时还要画结果矩阵（含“禁止残留”列）；
2. **精确结构**：contract-design，默认 `detailed`；
3. **验收合同**：Journey、规则矩阵、套件清单，再加上 `check-spec` 的章节覆盖要求。

验收合同和行为设计混在同一步骤序列里，起草 Journey 时行为合同可能还在变。邮箱一期的反复返工，大多出在这三件事的交叉处：合同一改，Journey、规则、套件和 Ticket 都要同步。

### 3.3 Journey 字段的实际用法（邮箱 35 步）

| 字段 | 实际情况 | 判断 |
| --- | --- | --- |
| 角色 | 每步都有。J2、J4 靠它区分用户 B 和 C、企业端和税务端 | 必要 |
| 入口类型 | 33 步是“页面”，2 步是“文件”（下载 `.eml`） | 写起来没成本，“文件”步决定取证方式，保留 |
| 控件 | 页面步都有具名控件，如 `导入账单`、`不是垃圾` | 必要，走查者靠它找按钮 |
| 操作入口 | 都有，写的是到达路径 | 必要。但混进了测试准备动作，如“回放 `.eml` 之后刷新”，按模板本应写在 `准备：` 行 |
| 观察表面、预期 | 都有 | 必要，是判定依据 |
| 承接 | 约一半的步骤用到（邮件 ID、附件 ID、单据 ID 等） | 必要，证据链的 `inputRef`/`outputRef` 靠它串起来 |

结论：Journey 之所以复杂，是早期太简单、后来逐步补字段的结果。现有字段都有实际用途。重量来自步骤数多，而不是列多。

## 4. 方案

### 4.1 场景风险清单（启发式、可积累）

**定位**：一份“反复出事的模式”清单，不是规则库，也不是检查表。

**每个模式的最小内容**
- 模式名，例如“临时、委派权限 × 历史数据”；
- 一两个真实案例，附出处；
- 设计时该问的问题，例如“换成只有当天权限的代班人，他完成这件事要读的数据，权限都覆盖了吗？”

**鼓励演化**

记录者如果发现现有写法装不下新问题，应主动提出新的字段或维度，例如“触发时机”“涉及的角色变体”“典型后果”。清单的格式本身也是可以积累的对象，不预先规定太多。

**积累机制**（参照 `improve-skill` 维护 rubric 的方式）
1. 每次修完一个缺陷，或审查得出一个 accepted finding，问一句：“这属于清单里的哪个模式？”
2. 对得上，就在该模式下追加案例；对不上，就提议新增模式，或提议新增记录维度。
3. 新增模式和新的记录形式，都经 Owner 确认后才入库，防止清单膨胀。
4. 入口建议挂在 `learn-lessons` 的流程里。它本来就负责从 findings 和调试材料中提炼经验，不必另起一套流程。

**使用位置**
- req-align：Spec 阶段起草验收合同时，以及风险驱动的 grilling 时，逐条问“这个需求里有没有这种情况”；
- Track C（`review-code-by-spec`）：对照清单看实现，作为启发式提示，不作为强制条目。

**第一批种子模式**（从邮箱一期和代班案例中提炼，入库前由 Owner 确认）

| 模式 | 案例 | 设计时问 |
| --- | --- | --- |
| 临时/委派权限 × 历史或跨范围数据 | 代班核对现金读不到历史数目 | 变体执行者完成这一步要读的数据，权限都覆盖了吗？ |
| 时间边界 | 测试写死当天时刻；进程时钟与数据库时钟混用；加锁后复核漏了保留期 | 这个判断依赖哪个时钟？跨天、跨月、过保留期时结果是什么？ |
| 状态在中途被别人改了 | 清理与重投竞争；到期时认领进行中且原请求崩溃 | 判断和执行之间，状态被改了怎么办？没有人再触发时，谁来收尾？ |
| 同一判断多处实现 | 接管、到期清理、定时清扫各写一份“查账单再释放” | 这条规则还有哪些流程会用到？是不是只有一份判断？ |
| 外部输入超出预期 | 正文含 NUL；多个 From 头；验签前占名额 | 输入合法但罕见时会怎样？未验证的请求会占用什么资源？ |

### 4.2 Spec 内拆出独立的“验收合同”一步

- 在 Spec 子技能里，把现在第 7 步的 Journey、Rule Matrix、Required Suites 拆到行为合同冻结之后，作为独立的一步，并配一份独立的参考文档，例如 `references/acceptance-contract.md`。
- 起草时的输入：Decision、调查材料、已冻结的行为合同、场景风险清单。
- 仍然由同一个 Spec Gate 一起批准，不新增 Gate，也不新增审批。
- 好处：
  - 起草 Journey 时上下文完整，Journey 不会随行为合同来回改；
  - Spec 子技能本身变短，每一步读的材料更聚焦；
  - 风险清单有了明确的使用时机。

### 4.3 Journey：保留全部字段，只加条件字段

**保留**：角色、入口类型、控件、操作入口、观察表面、预期、承接，以及 `准备：`、`取证：` 两行，格式不变。

**条件字段**：只对涉及权限或数据范围的步骤要求填写。
- **要读的数据**：完成这一步需要读到的全部数据，包括历史、跨门店和参考数据；
- **变体执行者**：列出会出现的变体（代班或临时委派、只读角色、刚被移出的人，以及跨月、跨门店的情况），逐个回答：换成他，这一步还能完成吗？缺什么？答不上来的，就是要 Owner 决定的产品问题。

**模板注释补一句**：测试脚手架做的事（回放邮件、造数据、刷新前的准备）写进 `准备：` 行或单独的前置动作，不写进“操作入口”。

**Spec Gate 补一条**：涉及权限或数据范围的步骤，条件字段必须填写；如果判断为不适用，要写一句理由。

### 4.4 run-acceptance：至少走一次变体执行者

**变体执行者走查**：每条 Journey 至少挑一个风险最高的变体执行者，真实走一遍，例如用代班身份完整走一次核对现金。前面各阶段漏掉的场景问题，会在这里直接暴露。变体执行者从 §4.3 的条件字段中选取。

**邮箱一期走查暴露的执行问题**：以下几条一并写进 run-acceptance 的走查手册。

| 问题 | 发生了什么 | 调整 |
| --- | --- | --- |
| 取证方法选错 | 某几步需要 Playwright，验收者就整轮改用 Playwright，速度慢了很多 | 先为每个测试点选方法，尺寸不是重点：默认用内置浏览器模仿真人操作，视口取它的技术上限（目前 1440×900，能更大就用更大）；只有内置浏览器测不到的步骤才用 Playwright，例如原生 confirm 会被自动取消、下载的文件不落盘、计时类测量 |
| 内置浏览器的已知限制 | 截图尺寸受面板大小限制，只有约 800×500；Claude 窗口不在前台时，画面不刷新，鼠标点击也不生效 | 手册里列出这些限制和变通办法：关键步骤另存局部放大截图；点击不生效时改用键盘操作，并在步骤备注里记录 |
| 走查期间代码变了 | 主控往验收者所用的工作目录合入了代码，API 热重载，后半程跑的是新代码，整轮证据作废 | 每轮走查在冻结的独立工作目录（detached HEAD）里进行；主控在走查期间不往该目录合代码 |
| 多个代理并发写状态文件 | 套件代理和走查代理同时调用 evidence CLI 写 `state.json`，后写的覆盖先写的，一条 amendment 因此丢失 | 验收者和套件执行者只写产物文件和 `records.json`，不调用 evidence CLI；由主控统一登记 |
| 测试准备一次跑不通 | `env:start` 重新生成 Prisma 时，seed 已经在加载它，导致冲突失败 | Harness setup 分两段执行：先等 API、web、tax-web 就绪，再跑 seed 和 precheck（这一条属于项目 harness，写在项目的 plan 模板或 start-env 里）|
| 页面触发不到服务端路径 | 重复导入时，界面已经禁用了勾选框，“服务端防重”这条路径没法从页面触发 | 这类步骤的预期写成“页面阻止再次提交”，服务端路径交给集成套件覆盖，避免走查者硬造操作 |

### 4.5 规则集中放：只写约定

在 KaiSpan 的 AGENTS.md 和架构文档里写明：
- 业务判断写成纯函数，集中放在模块的规则目录里，例如 `mailbox/rules/`；
- service 只负责编排：读数据、调规则、写结果、加锁、写审计。

审查时，Track C 顺带看一眼有没有重复实现。暂不加归属列、函数标注和 CI 检查脚本。等再出现“同一条规则写了两遍”的问题时，再加机械检查。

### 4.6 do-review：终审通过后，提醒是否加盲审 loop

邮箱一期在三轨终审全部 PASS 之后，按 Owner 的要求加了 `discuss-ledger` 盲审 loop 作为第四轨，codex 和 claude 两方独立审。之后连续几轮，每轮都找到新的有价值缺陷，例如：
- 暂存原文被并发覆盖，可能投到错误租户；
- 清理与重投竞争，导致原文丢失；
- 正文含 NUL 时邮件永久失败；
- 审计动作名与合同不一致。

做法：
- `do-review` 的 terminal-final 报告在全部 required track PASS 之后，加一句提醒，问 Owner 是否需要再加一轮盲审 loop。
- 不默认运行，也不作为 Gate 条件，由 Owner 决定。
- 提醒里说明代价（多方模型、多轮、修复后要重跑相关套件），并给出适用信号：触及租户隔离、外部输入、并发/幂等、跨存储写入，或者改动规模大。

### 4.7 impl-package CLI：amendment 的 `tickets` 字段被校验器拒绝

问题：
- `package amendment add --tickets` 会在 amendment 记录里写入 `tickets` 字段，`engine.py` 也接受这个字段。
- 但 `scripts/situation.py` 的 state 校验把 amendment 的允许字段写死为 `id, summary, affected, artifact, status`，外加 confirmed/created/affectedBlobs 几个字段，没有 `tickets`。
- 结果：只要登记过带 `--tickets` 的 amendment，`package validate` 就报 `acceptance.amendments[i] 字段/status 无效`，state 被判为缺失或无效，所有派发都被阻断。

修复：
- `situation.py` 的 amendment 字段校验已允许 `tickets`，见提交 `c01733c`。
- 还缺一个回归测试：登记带 `--tickets` 的 amendment 后，`package validate` 应通过。

## 5. 试金石：用邮箱包验证

邮箱一期过最终 Gate 之后，作为独立任务执行，不影响该包的 Gate。

1. 按 §4.2、§4.3 的新规则，重写邮箱 spec 的 §7：
   - 拆出验收合同；
   - 给涉及权限的步骤补条件字段，比如企业端只按显式上传权限才能看到门店邮箱、税务端的归属与协作者；
   - 把测试准备动作移出“操作入口”。
2. 用 §4.1 的种子模式，对邮箱需求做一次 grilling。
3. 对照这期审查和盲审实际找到的缺陷（§2.1 表），逐条统计：哪些能在 spec 阶段被问出来，哪些仍然只能靠审查。
4. 同时记录重写后 §7 的篇幅变化，以及起草时有没有返工。
5. 用代班案例做第二个样本：用新模板写它的 Journey，看能不能在 spec 阶段问出“代班读不到历史现金”。

**判定标准**（供评审讨论）
- §2.1 表中，至少一半的类别能在 spec 阶段被问出来；
- 代班案例能在 spec 阶段被问出来；
- §7 的篇幅增长不超过三成，条件字段只出现在涉及权限的步骤上。

达标就推广到新包；不达标，就按试点暴露的问题调整清单格式或条件字段。

## 6. 实施顺序

| 阶段 | 内容 | 位置 |
| --- | --- | --- |
| 1 | 建场景风险清单的格式说明和种子模式，Owner 确认种子 | agent-workbench（清单落点待评审，见 §7） |
