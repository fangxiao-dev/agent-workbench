# 场景风险清单与 Spec 验收合同调整提案

状态：已批准（2026-11-07）。本版已吸收 `discuss-ledger` 评审结论（盲审一轮、讨论两轮，16 条全部收敛），以及 Owner 的裁决。
涉及技能：`impl-package:req-align`（Spec 子技能）、`impl-package:review-code-by-spec`、`run-acceptance`、`learn-lessons`
评审记录：`docs/exchange/discuss/discuss-scenario-risk-proposal.md`
试点对象：KaiSpan `docs/implementations/2026-11-06-tenant-mailbox-inbound`（租户专属邮箱一期）

## 1. 结论先行

1. **场景风险清单**：新增一份清单，只记录启发式的“模式”，从缺陷和审查发现中机会性地积累。req-align 的风险审问和验收合同起草会读它；Track C 只拿它当线索。
2. **Spec 验收合同细则下沉**：现有步骤顺序不变，Journey、规则矩阵、套件仍是第 7 步。把第 7 步的长段细则移到 `references/acceptance-contract.md`，并在风险审问和验收合同起草两处引用风险清单。
3. **Journey 变体**：现有字段和表头全部保留。涉及权限或数据范围的步骤，以补充信息的形式写明“要读的数据”和“变体执行者”。每个变体写清预期结果（完成、部分可用、拒绝）和可观察的表现。另外在模板注释补一句：测试准备动作不写进“操作入口”。
4. **变体分两期支持**：
   - 本期 spec 支持变体，Gate 前由主控人工核对必验变体是否都已走过；
   - 工具（Journey 解析、证据格式、`gate pass`）在试点证明有用后再支持。
5. **run-acceptance**：
   - 包含条件字段步骤的 Journey，至少走一个已选变体，按该变体的预期结果判定；
   - 把邮箱一期暴露的执行问题，按现有规则收窄后写进手册（见 §4.4）。
6. **规则集中放**：只写约定，暂不加机械检查。
7. **impl-package CLI**：amendment 的 `tickets` 字段校验已修复（`c01733c`），补一个回归测试。
8. **以下保持不动**：
   - Decision 与 Spec 的分工；
   - contract-design 默认 `detailed`；
   - Journey 归属 Spec；
   - 不做统一规则引擎，也不加规则标注或 CI 检查；
   - do-review 不加盲审提醒。盲审如果导致代码或合同变更，HEAD 会变，现有 Gate 要求 terminal-final 锚定最终 HEAD，自然会拦住。
9. **试点只覆盖 Spec 和风险清单**（§5）。变体走查要到下一个适用的新包里单独评估。

## 2. 背景：为什么要改

### 2.1 邮箱一期暴露的问题

邮箱一期按 impl-package 完整流程走完：4 条 Journey、35 步、46 条规则、11 个套件。三轨终审（代码、合同、安全）全部通过后，又按 Owner 的要求加了 `discuss-ledger` 盲审 loop。之后连续几轮，每轮都找到新缺陷。有代表性的几类：

| 类别 | 例子 | 共同点 |
| --- | --- | --- |
| 同一判断写了多份 | 接管时会“先查账单再释放认领”，保留清理和定时清扫各写了一份，都漏了这一步，会让已建单据与认领脱钩 | 规则散在多个流程里，修一处漏一处 |
| 时间边界 | 测试写死“今天 09:00/10:00”，过点就失败；加锁后复核漏了保留期条件；地址历史用进程时钟，开关历史用数据库时钟 | 时间相关条件没有被系统性地追问 |
| 状态被别人改了 | 清理选中事件后，重投把它改回 open；邮件到期时认领还在进行中，原请求又崩溃，认领永远停在 pending | 并发和中途状态变化 |
| 外部输入 | 正文含 NUL 导致永久失败；验签前占名额，被匿名请求饿死；多个 From 头 | 信任边界和异常输入 |

这些问题都能被审查找到，但发现得太晚：要到终审或盲审才暴露，返工成本高。

### 2.2 一个邮箱之外的案例：代班

店长把当天的代班任务委派给员工，委派只授予当天的权限。代班任务里要核对现金，而核对需要读取历史现金数目。被委派者没有历史日期的权限，任务无法完成。

这三条规则单独看，每一条都正确：
- 委派只授予当天权限；
- 读取现金需要对应日期的权限；
- 代班要核对现金。

出错的是三条叠加在同一个场景里：执行者完成任务所需的数据，超出了他被授予的范围。规则写得再集中也兜不住这类问题，必须站在“这个人此刻要完成这件事”的角度，把整条链走一遍。

### 2.3 讨论过、未采纳的方向

| 方向 | 为什么没采纳 |
| --- | --- |
| 统一规则引擎（平台级） | 现阶段没有第二个需要“发布、版本、按租户配置”的场景。财务的 Kontierung policy package 是专用的，保持现状 |
| 规则归属列 + 函数标注 `@rule Rn` + CI 检查 | 对当前阶段太细；而且只能兜住局部规则，兜不住 §2.2 那类场景规则 |
| 把 Decision 和 Spec 合成一份短文档 | 两者定位不同：Decision 管承诺、方向、取舍和 blocking 判定；Spec 管行为合同和验收怎么做 |
| contract-design 默认改为 `not-required` | 历史上默认 `not-required` 时容易偷懒，所以才改成默认 `detailed`；它也不是重量的主要来源 |
| 精简 Journey 字段 | 逐列核对邮箱 35 步的实际用法，没有哪一列大概率没用（见 §3.3） |
| Spec 内新增独立的“验收合同”步骤 | 现有第 7 步本来就排在设计范围、contract-design、新 surface 回 Preflight、风险审问之后。想要的好处（子技能变短、清单有使用时机），把细则移到参考文档就能拿到。而且验收设计仍可能反过来要求修改行为合同，“Journey 不再来回改”的说法不成立（评审 D7、D13） |
| do-review 在终审后提醒是否加盲审 | 盲审导致的变更会改变 HEAD，现有 Gate 要求 terminal-final 锚定最终 HEAD，会拦住（Owner 裁决） |

## 3. 现状核对（基于技能原文）

### 3.1 req-align 的结构

- `SKILL.md` 是路由入口，内容工作交给 `sub-skills/decision/SUB-SKILL.md` 和 `sub-skills/spec/SUB-SKILL.md`。
- Decision 子技能负责 requirement inputs、Focused PRD、blocking triage、Core/Capability 和 Decision Gate，完成条件里写明“没有把 Spec/Plan 细节写入 Decision”。
- Journey 在 Spec 子技能“设计与写入”的第 7 步，对应 spec 模板 §7 的 Journeys、Rule Matrix、Required Suites 三张表，随 Spec Gate 一起批准。

### 3.2 Spec 子技能重在哪里

一个阶段里叠了三件性质不同的事，要在同一个 Gate 里一起通过：
- **行为合同**：设计范围、八个行为章节、contract coherence，需要时还要画结果矩阵；
- **精确结构**：contract-design，默认 `detailed`；
- **验收合同**：Journey、规则矩阵、套件，加上 `check-spec` 的章节覆盖要求。

Spec Gate 第 5 条同时检验行为章节和验收合同。第 7 步的细则全部写在子技能正文里，读起来长。邮箱一期的返工大多出在这几件事的交叉处：合同一改，Journey、规则、套件和 Ticket 都要同步。

### 3.3 Journey 字段的实际用法（邮箱 35 步）

| 字段 | 实际情况 | 判断 |
| --- | --- | --- |
| 角色 | 每步都有；J2、J4 靠它区分用户 B 和 C、企业端和税务端 | 必要 |
| 入口类型 | 33 步“页面”，2 步“文件”（下载 `.eml`） | 写起来没成本；“文件”决定取证方式，保留 |
| 控件 | 页面步都有具名控件 | 必要 |
| 操作入口 | 都有，写到达路径；但混进了“回放 `.eml` 之后刷新”这类测试准备动作 | 必要；准备动作应写在 `准备：` 行 |
| 观察表面、预期 | 都有 | 必要，是判定依据 |
| 承接 | 约一半的步骤用到 | 必要，证据链的 `inputRef`/`outputRef` 靠它串起来 |

Journey 的复杂度是早期太简单、后来逐步补字段的结果。重量来自步骤数多，不是列多。

### 3.4 运行时如何识别 Journey

impl-package 运行时按固定的 Journey 表解析步骤编号，表头由引擎硬校验（`engine.py` 与 `impl-package-current-state.md`）。每走一步登记一条步骤证据，`gate pass` 检查最终 HEAD 上是否有一次从首步走到末步的完整连续 run。运行时只认步骤编号，不认执行者，所以无法判断一次 run 是由主路径执行者走的，还是由变体执行者走的。

## 4. 方案

### 4.1 场景风险清单（启发式、可积累）

**定位**：一份“反复出事的模式”清单，不是规则库，也不是检查表。

**每个模式的最小内容**
- 模式名；
- 一两个真实案例，附出处；
- 设计时该问的问题。

**鼓励演化**：记录者发现现有写法装不下新问题时，应主动提出新的字段或维度，例如“触发时机”“涉及的角色变体”“典型后果”。清单格式本身也是积累的对象，不预先规定太多。

**积累机制**（参照 `improve-skill` 维护 rubric 的方式）
1. 由 `learn-lessons` 在它正常的发现和回刷流程中提出候选。第一版是机会性积累，不宣称覆盖每一个 accepted finding。
2. 新案例如果能归入已有模式，且符合证据要求和文档治理，可以直接追加。
3. 新增模式或新的记录维度，可以攒一批再提交 Owner 确认。确认前不算已入库。
4. 试点后，用“accepted finding 中有多少能映射到清单模式”这个比例，决定要不要另设收集点。

**存放位置**
- 跨项目的模式和匿名化案例放在 agent-workbench；
- 项目特有的细节留在项目资料里，用受控引用关联；
- 引用不可达时，在 workbench 侧保留一段非敏感的场景摘要。

**使用位置**
- **req-align**：风险驱动的审问时，以及起草验收合同时，逐条问“这个需求里有没有这种情况”。
- **Track C**（`review-code-by-spec`）：可以用清单寻找合同遗漏或需要核实的风险，但清单不是独立的合同来源：
  - 只有同时具备适用的稳定合同来源和 diff 证据，才作为 Spec finding；
  - 缺合同依据时，记为待裁决的合同缺口（evidence gap 或 UNCERTAIN），或转交适用的审查轨道。

**第一批种子模式**（入库前由 Owner 确认；试点时按 §5 的时间切分使用）

| 模式 | 案例 | 设计时问 |
| --- | --- | --- |
| 临时/委派权限 × 历史或跨范围数据 | 代班核对现金读不到历史数目 | 变体执行者完成这一步要读的数据，权限都覆盖了吗？ |
| 时间边界 | 测试写死当天时刻；进程时钟与数据库时钟混用；加锁后复核漏了保留期 | 这个判断依赖哪个时钟？跨天、跨月、过保留期时结果是什么？ |
| 状态在中途被别人改了 | 清理与重投竞争；到期时认领进行中且原请求崩溃 | 判断与执行之间状态被改了怎么办？没有人再触发时，谁来收尾？ |
| 同一判断多处实现 | 接管、到期清理、定时清扫各写一份“查账单再释放” | 这条规则还有哪些流程会用到？是不是只有一份判断？ |
| 外部输入超出预期 | 正文含 NUL；多个 From 头；验签前占名额 | 输入合法但罕见时会怎样？未验证的请求会占用什么资源？ |

### 4.2 Spec 子技能：第 7 步细则下沉

- 保留现有步骤顺序和 Spec Gate 结构。
- 第 7 步（Journeys、Rule Matrix、Required Suites）的细则移到新文件 `references/acceptance-contract.md`。第 7 步正文只保留：一句指向该文件、读风险清单、给涉及权限或数据范围的步骤补条件信息。
- 第 6 步的风险审问中，加一句引用风险清单。
- 先形成稳定的行为合同草稿，再起草验收合同。起草验收合同时如果发现缺口，回到行为合同修改，并同步 Journey、矩阵和套件，最后仍然一起过同一个 Spec Gate。

### 4.3 Journey：保留全部字段，补充变体信息

**保留**：角色、入口类型、控件、操作入口、观察表面、预期、承接，以及 `准备：`、`取证：` 两行。表头和步骤格式不变。

**补充信息**：只对涉及权限或数据范围的步骤，关联到对应的 Journey 或步骤编号，不改表头。
- **要读的数据**：完成这一步需要读到的全部数据，包括历史数据、跨门店数据和参考数据。
- **变体执行者**：按实际风险选取适用的身份或上下文，例如代班、临时委派、只读角色、刚被移出的人、跨月、跨门店。每个变体写明三件事：
  - 预期结果：完成、部分可用或应拒绝；
  - 可观察的表现；
  - 是否必验。
- 没有适用变体的 Journey，写“不适用”加一句理由，不虚构变体。
- 触发词（委派、临时、只读、历史、跨门店、跨月）只是提示示例，不是穷举，也不机械触发。

示例（代班核对现金）：

| 变体 | 预期 | 可观察表现 | 必验 |
| --- | --- | --- | --- |
| 代班员工（当天委派） | 完成 | 能看到昨日结余并完成核对 | 是 |
| 只读角色 | 部分可用 | 能看，“确认核对”不可用 | 否 |
| 刚被移出门店的人 | 拒绝 | 打不开页面或提示无权限 | 否 |

**必验与探索**
- **必验变体**：Spec 中列为必验的变体是验收合同的一部分。失败或缺证时，整包不能判 PASS。
- **探索性抽查**：走查者临时增加的身份算探索性抽查。抽查发现问题时，先对照合同分诊：属于实现缺陷就修；属于合同缺口或新增行为，就走修订和 Owner 裁决流程，不直接当成隐含的 Gate 条件。

**模板注释补一句**：测试脚手架做的事（回放邮件、造数据、刷新前的准备）写进 `准备：` 行或单独的前置动作，不写进“操作入口”。

**Spec Gate 补一条**：涉及权限或数据范围的步骤，必须有补充信息；判定“不适用”时，要写一句理由。

**分两期支持**
- **本期**：spec 支持变体；主控在 Gate 前对照 spec 里的必验变体清单，人工核对每一个都有对应的走查证据。提案和技能里写明这一点，不宣称现有 Gate 能自动证明变体已覆盖。
- **后续**：试点证明变体确有价值后，再让工具支持：Journey 解析和走查证据带上执行者，`gate pass` 自动拦住漏走的必验变体。这一步涉及固定表格格式、证据格式和旧包兼容，单独立项。

### 4.4 run-acceptance

**变体走查**
- 含补充信息步骤的 Journey，至少走一个已选变体，按该变体的预期结果判定。
- 主控可以按影响沿用证据，但只限完整、未被中断的 run。run 中途修过数据或代码，或者合同要求连续的 Journey，必须在最终 HEAD 上用新 run 从首步重走。变体走查同样适用。

**邮箱一期暴露的执行问题**：按现有规则收窄后写进手册。

| 问题 | 发生了什么 | 调整 |
| --- | --- | --- |
| 取证方法选错 | 少数几步需要 Playwright，验收者就整轮改用 Playwright | 现有规则（SKILL.md 的取证规则）已经写明：取证方式在 Journey 的 `取证：` 行确定，内置浏览器做不到的单步才用 Playwright 补位并写明原因，其余步骤仍然走查。这次是违反了既有规则，手册加一句提醒，指向该规则 |
| 宿主浏览器的表现 | 截图尺寸受面板大小限制；窗口不在前台时点击不生效 | 具体数值是特定宿主的当前表现，不进通用手册，需要的话放进宿主使用备注。通用手册只保留：截图要拍全通过标准依赖的元素，拍不全就局部放大或补位，并记录原因 |
| 走查期间代码变了 | 主控往验收现场的工作目录合入代码，API 热重载，后半程跑的是新代码 | 每轮锁定受验 HEAD。验收现场与主控集成分支使用不同的工作目录，合入只走现有的集成窗口，窗口内停服或重启，并说明数据库、端口和服务的隔离边界。HEAD 变化后按上面的沿用规则处理。这次事故的根源是违反了现有集成窗口 |
| 多个代理并发写共享状态 | 套件代理和走查代理同时写 `state.json`，一条 amendment 被覆盖 | 约束：共享 state 只能串行写入，产物文件必须唯一命名。若改为由主控统一登记，须同步修改 verifier 和走查记录模板中验收者的登记职责，并规定交接时的核对方式。`records.json` 是邮箱一期的临时做法，不是既有约定 |
| 测试准备一次跑不通 | `env:start` 重新生成 Prisma 时，seed 已在加载它 | Harness setup 分两段：先等服务就绪，再跑 seed 和 precheck。这属于项目 harness，写进 KaiSpan 的 start-env 或 plan 模板 |
| 页面触发不到服务端路径 | 重复导入时界面已禁用勾选框，服务端防重无法从页面触发 | 这类步骤的预期写成“页面阻止再次提交”，服务端路径由集成套件覆盖 |

### 4.5 规则集中放：只写约定

在 KaiSpan 的 AGENTS.md 和架构文档里写明：
- 业务判断写成纯函数，集中放在模块的规则目录（例如 `mailbox/rules/`）；
- service 只负责编排：读数据、调规则、写结果、加锁、写审计。

Track C 审查时顺带看一眼有没有重复实现。机械检查等再出现“同一条规则写了两遍”时再加。

### 4.6 impl-package CLI：amendment 的 `tickets` 字段

- **问题**：`package amendment add --tickets` 写入 `tickets` 字段，`engine.py` 接受它，但 `situation.py` 的 state 校验当时不允许这个字段。结果是登记过带 `--tickets` 的 amendment 后，`package validate` 判 state 无效，所有派发都被阻断。
- **修复**：已在 `c01733c` 中修复。
- **待补**：回归测试——登记带 `--tickets` 的 amendment 后，`package validate` 应通过。

## 5. 试点：验证 Spec 与风险清单

试点只覆盖 Spec 和风险清单（§4.1–§4.3 中 Spec 侧的部分）。变体走查（§4.4）在下一个适用的新包验收时单独评估，不能用 Spec 试点的结果代替走查证据。

**防止样本污染**
1. 种子模式和评分样本必须分开。按时间切分邮箱一期的缺陷：前半段用来提炼种子，后半段用来评分；或者改用另一个没有参与种子整理的包来评分。
2. 冻结当时可得的输入材料、预期答案和评分口径。由没有参与种子整理的独立执行者，分别按现有流程和按清单盲测比较；评估者独立核对命中情况和耗时。
3. 如果找不到未被污染的案例，或不具备独立执行的条件，邮箱和代班两个样本只作可用性演练，结果标注“无法判断增量效果”。

**报告口径**（不设命中率阈值）
- 逐项报告：命中、待核实的提问（不直接记为误报）、投入时间、返工情况。
- 篇幅基线：写明重写前 §7 的行数和条数，再对比重写后的数字。
- 验收阶段才暴露的问题，单独列出并分三类归因：
  - 当时的输入里已有信息，且清单有对应模式：记为漏项；
  - 当时的输入里没有这些信息：记为合同缺口，不算 Spec 失败；
  - 属于新增行为：走修订流程。

  归因以当时可得的材料为准，由没有参与该包 Spec 起草的评估者判定。
- 结论只写“继续试点 / 调整格式 / 停止”。单对样本不推断增量效果，也不自动推广。
