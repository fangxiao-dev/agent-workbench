# Session Sidecar 看板方案

状态：方向已确认；本文是方案，不是实施合同或已批准的详细实施计划。  
日期：2026-11-26

## 1. 目标

提供独立于 Claude Desktop 的本地看板，聚合多个 session 的状态和近期进展。用户扫一眼即可知道哪些任务有变化、哪些可能需要关注，并通过链接进入原 session 继续沟通。

任务继续由各自的 session、harness 和 skill 执行；可能使用 impl-package，也可能只是小型调研。看板不要求它们主动上报，不负责派发任务、控制阶段或在看板内 steer。

关键原则：**原生 session 是事实来源，看板 item 是用户的工作对象，AI 摘要是基于来源和用户面的可再生成解释。**

## 2. 用户看到的样子

看板默认每个 session 一个 item，展示：

- session 标题、项目或其他可确认的来源信息；
- 原生运行状态及最后活动时间；无法可靠判断时显示未知；
- 用户设置的 item 状态、分组、备注或关注程度；
- 近期进展，以及自上次从看板打开后的变化；
- AI 识别到的可能需要关注事项，标明为分析而非确定事实；
- 数据最近同步时间、摘要生成时间，以及可用时的 Desktop 跳转链接。

例如：

```text
员工门户补件                         原生状态：运行中
我的状态：进行中                     最后活动：2 分钟前
自上次从看板打开后：完成退回重交修复，正在验收。
可能需要关注：合同失效后的处理规则需要确认。
                                      [打开 Desktop session]
```

看板优先突出待关注和最近有变化的 item。用户可以修改自己的状态和备注、归组、隐藏或移除 item；这些动作不修改原生 session。原 session 是否运行、结束、归档，与 item 是否标记完成相互独立。

## 3. 日常工作流

1. 用户照常使用 Claude Desktop 创建和推进 session；也可以在 session 中继续派发二级 session。
2. 独立启动的 sidecar 发现 session，读取新事件并更新来源信息。
3. 小模型结合原生新增内容和必要的看板上下文，生成简短进展与关注提示；没有新内容时复用已有摘要。
4. 用户查看看板，按自己的习惯设置 item 状态、分组和备注。
5. 用户从看板打开原 session，在 Desktop 里查看详情、补充业务背景或继续下指令。
6. 看板记录这次打开的已读基准，之后展示该基准之后的进展。第一版仅承诺“自上次从看板打开后”，不假设能知道用户直接在 Desktop 中的阅读行为。

## 4. 抽象和职责

```text
原生 session ──只读──> 来源适配 ──> 原生事实与事件
                                       │
                                ┌──────┴──────┐
                                ▼             ▼
                        看板数据与用户操作   AI 分析
                                └──────┬──────┘
                                       ▼
                            本地看板 → Desktop
```

### 4.1 原生来源适配层

负责发现来源、读取元数据与增量事件，并转换为看板内部可消费的记录。来源的原生标识与 Desktop session 标识必须显式关联，不能假定所有标识天然相同。

来源层只读，不控制 session、不改原生文件，也不规定 session 内部使用什么流程。第一版以本机 Claude session 为目标，其他 harness 或远程 session 的适配不属于已验证范围。

### 4.2 看板数据层

看板维护独立于来源的持久数据：

| 数据 | 权属和更新方式 |
| --- | --- |
| 来源标识、观察到的运行状态、最后活动 | 从原生数据采集；不确定时标记未知 |
| item 的用户状态、分组、备注、关注程度 | 由用户在看板维护；同步和模型不得覆盖 |
| 看板打开时间与已读位置 | 由看板操作维护，具体确认机制待验证 |
| 来源读取位置、同步时间、错误状态 | 由采集器维护 |
| 摘要、依据范围和生成时间 | 由分析器生成，可覆盖或重建；旧结果须标记新鲜度 |
| 隐藏或移除标记 | 看板持久保存，阻止同一来源被自动重新创建；可由用户恢复 |

同步器、摘要器和用户操作各自拥有不同字段，更新时不能覆盖其他方的数据。删除或移除看板 item 不得删除、关闭或修改原生 session。

第一版推荐一个 item 关联一个 session，多 item 通过分组聚合。一个 item 关联多个 session 可作为后续演进，但不预设实现。

### 4.3 AI 分析层

小模型读取有变化的原生内容，以及生成摘要必需的用户面上下文，例如 item 标题、用户备注与已读基准。输出简短进展和可能需要关注的事项，附生成时间与可追溯的来源范围；依据不足时明确表示不确定。

模型只更新分析字段。它不得自动修改用户状态、分组、备注、已读位置或原生 session，也不能仅凭 session 空闲就断言任务已完成。

模型可替换，候选包括 DeepSeek；尚未选定提供方和部署方式。发送外部模型前需要明确选择哪些数据、是否脱敏、数据流向及用户授权。模型不可用时应保留并标明上次摘要的时间和失败状态；采集与看板的用户操作继续可用。

### 4.4 展示层

本地看板从看板数据层读取信息并提供整理操作。原生事实、用户状态和 AI 推断需要清楚区分；没有可靠链接时，显示不可用而不是构造未经验证的跳转。

## 5. 建议的实现方式

使用一个可独立启动的本地 sidecar，负责定时采集和按需调用摘要模型；本地持久层保存来源引用、读取游标、用户数据和摘要；本地界面负责浏览、整理和跳转。

SQLite 是当前建议的持久化选项，技术栈和具体进程启动方式尚未确定。定时刷新频率、来源纳入规则和模型配置留待实现设计确定，不把“每一轮结束后立即刷新”作为已验证的实时保证。

增量处理需要满足：

- 按来源保存读取位置，通常只读取新增数据；仅处理完整事件，未写完的记录留待后续读取。
- 检测读取失败、文件替换或截断，并在恢复时核对和去重，避免静默漏数据或重复分析；具体标识和恢复策略需基于来源格式验证。
- 对短时间内的密集更新合并分析，避免每条消息都调用模型；没有值得处理的新内容时不调用。
- 看板显示最后成功同步时间与错误，不把过期信息当成当前状态。
- 进程退出或重启后，保留用户整理、已读位置和同步进度，继续追踪。

## 6. 探针证据与限制

2026-11-26 的最小只读实验在本机 Windows 环境中观察到：

- 独立 Python 进程能发现本地 session JSONL；当时扫描到 710 个记录文件、122 个项目目录。这是文件数量，不等于 Desktop session 数量或完整覆盖率。
- 进程解析一个已知实验 session 的 240 条记录，找到此前已知的 hook 拦截内容和文件名。
- 对正在运行的当前 session，从先前记录的字节偏移读取到 6,759 字节、9 条完整新增记录，证明一次增量读取可行。
- 当前运行中 session 的本机元数据可关联到其 Desktop 标识、底层标识、工作目录和 `busy` 状态；这只证明该实例，不证明所有会话的映射和生命周期状态。

本地 JSONL 与元数据格式尚未证明是公开稳定接口。文件可能含有用户消息、工具结果及敏感上下文；不应把整份原始记录默认交给模型。上次 Stop hook 实验不再是本方案的前提，本方案不要求注册全局 hook。

## 7. 分阶段交付

### 阶段 1：来源适配和只读看板

发现本机 Claude session，显示可确认的基本信息、最近活动和可用的运行状态；实现增量读取、同步错误提示和重启恢复；验证 Desktop 链接能否取得并打开。

验收：新建 session、产生新消息、完成一轮和重启 sidecar 后，看板能反映可确认的变化，不重复处理；无法判断的状态或链接明确显示未知或不可用。

### 阶段 2：看板用户面

加入 item 状态、分组、备注、隐藏或移除，以及从看板打开后的已读基准。移除标记防止来源再次被自动添加，并提供恢复途径。

验收：session 继续产生事件时，用户设置不被覆盖；移除 item 不影响原 session；从看板打开后能按已验证的基准展示后续变化。

### 阶段 3：小模型分析

接入可配置的小模型，只针对有变化的来源生成简短进展及可能的关注事项。记录摘要依据和时间，处理模型失败、过期与不确定性。

验收：以多条真实 session 的新增内容核对摘要是否抓住变化；检查模型没有把空闲误判为完成、没有覆盖用户状态，并观察实际开销和失败行为。

### 阶段 4：按实际使用完善

根据使用反馈决定搜索、通知、开机启动、更多 harness、多 session 对应一个 item 或跨机器能力。均不作为当前已承诺范围。

## 8. 仍需解决的问题

1. 独立进程能否可靠取得完整 Desktop session 清单、标题、归档信息以及可用跳转链接；结束和归档会话如何映射。
2. 原生运行状态在进程结束、异常退出、Desktop 关闭及远程会话等情况下的可用性和可信度。
3. 看板点击打开时如何记录准确的事件基准，打开失败、并发新增事件时如何避免错误标记已读。
4. Claude Code TUI 的离开后总结是否可从独立进程复用，以及数据来源和适用范围。
5. 默认纳入哪些 session、数据留存期限、摘要输入的筛选脱敏方式，以及接入外部模型前的数据流向授权。
6. 本地数据格式变更、部分记录、截断和重启恢复的实际行为；当前只有单次增量读取证据。
