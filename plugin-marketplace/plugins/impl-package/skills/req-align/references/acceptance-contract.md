# 验收合同：Journeys、Journey 变体、Rule Matrix、Required Suites

Spec 子技能第 7 步读取，用于新 package 的 `spec.md §7`。表结构以 [Spec Template](../assets/templates/spec.md) 为准，runtime 解析规则见 composition contract §7。

## 起草顺序

先稳定行为合同（§1–§6、§8 与 contract-design），再起草验收合同。起草时拿 [场景风险清单](../../../references/scenario-risk-patterns.md) 逐条提问；发现行为缺口就回到对应章节修改，再同步 Journey、变体、矩阵与套件，一起过 Spec Gate。

## Journeys

- Journey 用 Owner 语言按终态定义。每步写角色、入口类型（页面/文件/记录）、控件、操作入口、观察表面、预期和承接（上一步交来的业务对象，无则 `—`）。入口与表面要具体到执行者能在页面上照做，而不是只写“用户完成 X”。
- 步骤只含用户亲手做或亲自收到的事；用户看不到的行为（并发、幂等、回滚、租户隔离）归规则矩阵与套件。页面已阻止、服务端路径无法从页面触发时，该步预期写页面可见的阻止表现。
- 每条 Journey 只有一行 `准备：`，写 run 前可预置的账号、权限、种子与脚手架；必须发生在步骤之间的脚手架写在该步操作入口开头，标“（先：…）”。
- `准备：` 下一行 `取证：`：默认 `浏览器走查`；只有浏览器给不了的精确测量（响应时间、延迟阈值、动画时长）才写 `Playwright（理由：<点名 step 与测量量>）`。

## Journey 变体

涉及权限或数据范围的步骤，要问：换一个人或换一个上下文（代班、临时委派、只读角色、刚被移出的人、跨月、跨门店）来做这一步，他要读到的数据都读得到吗？结果应该是什么？

写在与 `### Journeys` 同级的 `### Journey 变体` 小节，runtime 不解析，Journey 表与 step id 不变。每个这样的步骤一个 `#### J<n>-S<m> <步骤简述>`：

- **要读的数据**：完成这一步要读到的全部数据，含历史、跨门店和参考数据。
- **变体表**：每个变体写前置（账号、授权状态、前置动作；只写在这里，不进 `准备：`）、预期 `完成 | 部分 | 拒绝`、可观察表现、必验 `是 | 否`。

没有适用变体时写 `- J<n>-S<m>：不适用（理由：…）`，整条 Journey 可写 `- J<n>：不适用（理由：…）`，理由点名各步的角色与数据范围。按真实风险选变体，不为凑格式虚构。

必验变体是验收合同的一部分：验收时必验全部走，有变体的 Journey 至少走一个，按预期判定，在 `run-acceptance` 收口核对。

## Rule Matrix 与 Required Suites

- 规则逐条写 Source（Spec 章节引用）、挂到一个套件并给出 oracle；不需要验收的章节列在“无需验收的章节”行。
- 包级 safety 套件按风险声明：触及 tenant、RBAC/privacy、幂等或数据完整性时必须有，未触及时写明理由。
- 套件清单是合同，由 Owner 在 Spec Gate 批准，Plan 之后不再补造。
