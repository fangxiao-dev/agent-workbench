# 验收合同：Journeys、Journey 变体、Rule Matrix、Required Suites

Spec 子技能第 7 步读取。只用于新 package 的 `spec.md §7`；表结构以 [Spec Template](../assets/templates/spec.md) 为准，runtime 解析规则见 composition contract §7 与 current-state。

## 起草顺序

先形成稳定的行为合同草稿（§1–§6、§8 与 contract-design），再起草验收合同。起草时逐条读 [场景风险清单](../../../references/scenario-risk-patterns.md)（清单目前均为候选，只作提问线索，引用时注明），问“这个需求里有没有这种情况”；清单是提问线索，不是合同来源。发现行为合同缺口时回到对应章节修改，并同步 Journey、变体、矩阵与套件，最后仍一起过同一个 Spec Gate。

## Journeys

- Journey 用 Owner 语言按终态定义。每步写角色、入口类型（页面/文件/记录）、控件、操作入口、观察表面、预期和承接（上一步交来的业务对象，无则 `—`）。
- 步骤只含用户亲手做或亲自收到的事。用户看不到的行为（并发、幂等、回滚、租户隔离）归规则矩阵与套件。
- 账号、权限、种子账套写在 Journey 的 `准备：` 行。测试脚手架做的事（回放邮件、造数据、刷新前的准备）也写进 `准备：` 行或单独的前置动作，不写进“操作入口”；操作入口只写用户到达该控件的路径。
- `准备：` 下一行 `取证：` 在此刻定取证方式：默认 `浏览器走查`；只有响应时间、延迟阈值、动画时长这类浏览器走查给不了的精确测量，才写 `Playwright（理由：<点名 step 与测量量>）`。
- 页面无法触发的服务端路径（例如界面已禁用重复提交），该步预期写成页面可见的阻止表现，服务端路径归规则矩阵与集成套件。
- 常见误判：步骤只写“用户完成 X”而没有入口与表面，执行者只能用 API 重放代替页面。

## Journey 变体

只对涉及权限或数据范围的步骤补充，写在与 `### Journeys` 同级的 `### Journey 变体` 小节（放进 Journeys 内会被 runtime 当作 Journey 解析而报错），每个关联步骤一个小标题 `#### J<n>-S<m> <步骤简述>`，其下写“要读的数据”与变体表。Journey 表头、步骤格式与 step id 不变；变体不另起 step。

每个关联步骤写：
- **要读的数据**：完成这一步需要读到的全部数据，包括历史数据、跨门店数据和参考数据。
- **变体执行者**：按实际风险选取适用的身份或上下文，例如代班、临时委派、只读角色、刚被移出的人、跨月、跨门店。每个变体写三件事：
  - 预期：`完成 | 部分 | 拒绝`；
  - 可观察表现；
  - 是否必验：`是 | 否`。
- **前置**：每个变体所需的账号、授权状态（如当天委派、刚被移出）与前置动作，写进对应 Journey 的 `准备：` 行，或注明由哪个 harness 步骤预置。

规则：
- 涉及权限或数据范围但没有适用变体的步骤写一行 `- J<n>-S<m>：不适用（理由：…）`；整条 Journey 都不适用时可写 `- J<n>：不适用（理由：…）`。不虚构变体。
- 触发词（委派、临时、只读、历史、跨门店、跨月）只是提示示例，不是穷举，也不机械触发；按“这个人此刻要完成这件事，要读到什么”判断。
- 必验变体是验收合同的一部分，失败或缺证时整包不能判 PASS。
- Spec Gate 只检查补充信息是否齐全。必验变体是否走过属于验收 Gate：本期由主控在最终 `gate pass` 前按 `run-acceptance` 的收口条件人工核对走查记录；runtime 只认 step id，不识别执行者，`gate pass` 不会自动拦住漏走的必验变体。
- 常见误判：只给主路径角色写 Journey，权限单看都对，叠加在委派或跨范围场景里任务却完不成。

## Rule Matrix 与 Required Suites

- 规则逐条写 Source（Spec 章节引用）、挂到一个套件并给出 oracle；不需要验收的章节列在“无需验收的章节”行。
- 包级 safety 套件按风险声明：触及 tenant、RBAC/privacy、幂等或数据完整性时必须有，未触及时写明理由。
- 套件清单是合同，由 Owner 在 Spec Gate 批准，Plan 之后不再补造。
- 常见误判：套件清单留给 Plan，Gate 时才发现规则没有 oracle。
