# 业务规则层：为什么与怎么核对

仅当项目声明了业务规则层（在项目指令或文档里写明规则分册、规则层目录或 Business Rule Layer 原则）时适用；未声明的项目跳过本文。

## 为什么

目标是让业务逻辑**收束到规则层**：

- 每个业务值只由规则层里的一处实现产出；
- 规则先写成文字，带稳定编号；
- 页面、导出、待办、AI 查询等交付层只交付，不自带判断与计算；
- 改规则时能从编号找到全部实现。

不收束，同一条规则会在多个调用方各写一份，口径悄悄分叉，改规则时漏改。

`@rule <编号>` 标注与项目提供的确定性检查只是**追溯手段**：它们证明改到的规则函数能追溯到一条成文规则，证明不了逻辑已经收束（规则层之外是否还有同样的计算）。收束要靠设计时落点、审查时核对。

设计或实现时说不出某段逻辑落实哪条规则，说明逻辑放错了地方或规则还没成文：先补规则，或把逻辑挪进规则层。**不得为通过检查编造或硬套编号。**

## 规则层落点（Spec 填写）

对本次涉及的每个业务值写明：

- 落实哪条规则（编号）；没有就先在规则分册补规则；
- 由规则层哪个模块产出；
- 哪些交付层读取它（它们只读结论，不重算）；
- 涉及“现在/今天”时：从项目的哪个时钟入口取；
- 涉及可见性/权限时：走哪个共用判定。

## 审查时核对

- Spec 的规则层落点是否覆盖本次所有业务值，是否有业务值没有规则来源；
- 计划或 diff 是否在交付层另写判断、阈值、日期推算或权限分支；
- 标注编号与函数实际行为是否一致，是否有为过检查而硬套的标注；
- 项目登记的确定性检查（如标注检查、架构守护）是否被 Ticket 验收引用并通过。
